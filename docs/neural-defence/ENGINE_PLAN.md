# Neural Defence: core engine plan

Status: proposed architecture and acceptance plan. No engine or playable game is implemented by this draft. Gameplay decisions are in [GAMEPLAY.md](GAMEPLAY.md); numeric settings must remain experimental until measured.

## Reuse the platform, isolate the rules

Create `games/neural-defence/` as a workspace exporting a headless TypeScript library. The engine owns hex geometry, map validation, commands, simulation, bots, canonical state and validation. It imports nothing from networking, DOM, rendering or another game. A thin online adapter implements the existing `RollbackGame` contract; the app composes the existing room transport and UI. The simulation must run identically in Node and browsers.

Proposed layout (these paths do not exist yet):

| Path under `games/neural-defence/` | Responsibility                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `src/engine/`                      | State, integer hex graph, command guards, ordered tick pipeline, seeded RNG, view and checkpoint rules |
| `src/engine/bots/`                 | Deterministic agents emitting ordinary player commands from permitted observations                     |
| `src/online/game.ts`               | `RollbackGame` adapter, management fold, room clock, seating and scope                                 |
| `src/online/runtime.ts`            | Typed command methods over `RoomRuntime.append` and `sendPackets`                                      |
| `src/render/`                      | Read-only world views and cosmetic particle animation                                                  |
| `src/app/`                         | Lobby, game page, board input, phone controller and shared display                                     |
| `src/platform.ts`                  | Game registration and confirmed match facts                                                            |
| `tests/`, `scripts/`               | Replay fixtures, invariants, network integration and batch balance runner                              |

The existing [`scripts/new-game.ts`](../../scripts/new-game.ts) copies Pig, including its turn rules. Use its workspace/app wiring as a reference or scaffold, then replace those rules; do not evolve Pig's turn model into an RTS. The engine's public entrypoint should expose `createMatch`, `step`, `observe`, state codec/hash and bot policy interfaces without importing the app. Proposed `step(state, commands)` advances exactly one fixed tick and returns gameplay facts. No wall-clock waits, global mutable bot state or unseeded randomness.

## Simulation contract

Start with one simulation step per existing 50 ms log tick (20 Hz; [`clock.ts`](../../packages/fuse-netcode/src/clock.ts)). Headless acceleration repeatedly calls the identical step, without sleeping; it does not multiply damage or skip ticks. Rendering may interpolate but cannot advance construction, projectiles or resource extraction.

Use axial integer hex coordinates with a canonical tile index and six fixed neighbor directions. Use integer/fixed-point HP, resources, charge and rates; persist remainder accumulators for fractional yields. All multiplication must stay within explicitly validated safe-integer bounds. Graph traversals, entity enumeration, event order and equal-cost routing use canonical ordering, never object insertion order or locale sorting. Maps, rules version, seed and settings are part of state compatibility. Hash and encode every authoritative field, including routing remainders, cooldowns and RNG state.

A first map format contains traversable cells, blockers, non-buildable resource deposits, tower sites and 2–4 brain spawn slots. Deposits mine only through their traversable neighboring cells; six owned neighbors give maximum output for an interior deposit. Initial maps should give deposits six usable neighboring cells. Validate bounded dimensions, unique coordinates, valid spawns, reachable expansion areas and tower-site ring geometry. Distinguish connectivity validity from balance: a connected map can still favor a spawn. Start with mirrored two-player maps and four-corner maps matched by graph distance, chokepoint width and resource access. A hex lattice does not have square fourfold symmetry: rotate spawn assignments and measure outcomes, including three-player and asymmetric maps, rather than claim equal-looking corners are fair.

Each command names its match/round, actor, target and relevant entity generation. Commands include queued growth/cancel, growth mode, node priority, tower build and research choice. The online fold takes actor identity from the member stream and current logged seat/generation, never a user-supplied player ID; this preserves the existing trusted-peer model, not a new anti-cheat guarantee. Limit payload size, queue length, targets and accepted actions per tick. Validate shape at ingress, then ownership, connectivity, phase, prerequisites and affordability at application. UI validation is only feedback. Invalid/stale commands are deterministic no-ops with observable rejection reasons.

### Proposed tick pipeline

1. Fold shared room management; determine active roster and match scope. During play, loss of presence does not pause the world or eliminate a brain. Autonomous jobs continue; new human orders require a valid current stream. Never silently replace an absent player with a new bot.
2. Snapshot tick-start eligibility, connected components, balances and completed upgrades. Fold player intentions in stream sequence order; bots use the same command path. A player's queued spending order is explicit. Reserve costs against tick-start balances, so simultaneous orders cannot overspend.
3. Resolve neutral growth claims as a batch. If multiple owners claim one tile on this tick, reject all competing claims and release reservations. Stable IDs order processing but never win contested land. No charge for a rejected claim; auto-growth backs off before retrying. Existing jobs advance with integer progress. New jobs and newly completed tiles become operational next tick, so a tick cannot grow a chain recursively.
4. Extract resources from tick-start connected neighboring ownership. A deposit has a fixed per-neighbor rate: each of its six owned adjacent cells earns one sixth of maximum output for its owner. Unowned shares remain unmined; two owners cannot each extract the whole deposit. Credit after this tick's reservations, available next tick. Insight's small brain trickle follows the same accounting.
5. Mature scheduled particle recovery and deliver previously scheduled transit. Derive flow requests from the eligible neural graph and current priority targets. Allocate each source, each link's bounded capacity and each destination's unreserved storage once, then commit transfers together. Every in-flight unit reserves one destination slot until delivery or recovery; `nodeCharge + incomingReservations <= nodeCapacity` always. Release reservations when a target dies/disconnects and move the corresponding charge to recovery atomically; never clip an arriving packet to capacity or redirect it without transferring its reservation. New transfers cannot be forwarded again during this tick.
6. Choose legal local attacks, tower pulses and repair from the same pre-combat state. Reserve the finite local particle availability across these actions; a unit committed to attack cannot also shield or repair this tick. Base structural resistance remains separate. Record damage/repair intents without mutating targets during enumeration.
7. Resolve damage simultaneously, then destruction and graph cuts together. A neuron that fired before lethal damage still fired. Destroyed/disconnected node particles and affected transit move to recovery exactly once. Construction/tower-ring legality uses tick-start eligibility; combat can subsequently destroy its support. A completed disconnected structure remains inactive.
8. Resolve brain deaths together. One survivor wins; no survivors is a draw, never an iteration-order winner. Eliminated players stop orders, economy and combat. Account for all their particles in a terminal retired compartment before clearing board ownership. Record facts, advance the clock and assert invariants.

The precise phase order is a versioned rule. A repair in phase 6 cannot resurrect a structure already destroyed in an earlier tick. Repair applies only if no incoming raw damage was committed against that target this tick; otherwise release its repair reservations. For an eligible target, HP becomes `min(maxHP, startHP + repair)`; a damaged target loses post-shield damage and is destroyed at zero. Research completed this tick applies next tick. No rendered animation completion controls an engine outcome.

Use **Biomass** for growth/construction/repair and **Insight** for research. Accepted construction spends its reserved cost once. A construction site is exclusive, damageable and non-operational, with explicit builder ownership distinct from completed tile ownership. Losing its brain connection pauses progress; it does not refund the purchase. Cancelling an unstarted queue item costs nothing; cancelling a started site or losing it to attack gives no refund in the first prototype. This avoids cancellation being free temporary territorial denial. New claims cannot target an existing site. Towers require their centre site and all six surrounding cells to be owned and brain-connected at placement; losing the ring later does not remove the tower, while losing its own brain connection disables it. Publish these distinctions in the view contract so a ghost preview cannot be mistaken for acquired territory.

### First combat contract

Use the following symbolic rules before tuning numerical values. Every connected completed neuron/brain automatically pulses on its cooldown when an adjacent hostile neuron, brain, tower or construction site exists. Its attack budget is `A = min(pulseCap, max(0, localCharge - defensiveReserve))`. Divide `A` evenly across adjacent hostile targets, rotating integer leftovers with a checkpointed counter. Commit those units to recovery and emit `damagePerCharge * assignedCharge` damage intents. Zero available attack charge means no attack. Setting a priority changes supply; it does not choose a damage multiplier. Construction sites do not fire.

A tower uses this same local particle budget and cooldown system but fires at one nearest hostile target within hex distance two. Equal-distance targets rotate in canonical order. Terrain blockers intersecting a deterministic supercover hex line block the shot; friendly neurons do not. Range two is necessary to reach beyond the required friendly ring. Shots resolve in their firing tick: the renderer may draw a pulse, but no independent projectile physics or animation delay affects hits. Future projectile travel would be a separately versioned rule.

After all attack intents are collected, each target computes `D = max(0, sum(rawDamage) - structuralArmor)` once per tick, then `S = min(uncommittedLocalCharge, shieldAbsorptionCap, D)`. Move `S` shielding particles to recovery and subtract `D - S` from HP. The cap applies per node per tick; the proposed Insulation research raises this cap, while Conduction raises link throughput. Neither creates particles. This defines base defence and active shields without applying armor repeatedly for many small attackers. Uncommitted charge includes the defensive reserve, which can be depleted; it is not invulnerability. All eligible attackers emit before any death is committed, so mutual destruction is valid. Disconnected nodes have structural armor and HP but no active shield after their charge entered recovery.

Optional repair is a bounded automatic action on connected damaged nodes with zero incoming raw damage, after attack and shield reservations: spend a configured integer Biomass cost and particle cost for a configured HP increment, capped at missing HP. Affordability is reserved across the player's repairs in a rotating canonical node order. This avoids free regeneration, spending the same charge twice, and permanent repair under fire. If the first prototype is too broad, defer repair entirely rather than add a separate healing clock.

## A particle field without a physics simulation

Use a bounded aggregate flow network, not thousands of individually simulated bodies or an unbounded electrical solver. The authoritative units are integer particle counts; visible sparks illustrate those counts. This makes charge competition, supply paths, bottlenecks and travel time testable at high speed.

For each player, the MVP invariant after every phase is:

`startingPool = nodeCharge + inTransit + recovering + brainReserve + retired`

Every term is nonnegative; every transfer subtracts and adds the same integer once. `retired` is zero until elimination. There is no passive particle creation, disappearance or capacity research in the first prototype. Attacking or active repair moves committed particles to recovery; damage does not mint or permanently steal them. Shielding uses only uncommitted charge. Recovery returns charge to the brain after a cooldown plus at least its saved pre-cut graph-distance travel time; persist that distance in a recovery record. This is an explicit gameplay abstraction with a tunable penalty. There is no player command to flush charge into recovery; voluntary reallocation travels the graph. Test whether deliberately sacrificing remote sites still creates a beneficial transport shortcut under congestion before accepting the rule.

Disconnected neurons retain ownership and HP but cannot mine, grow, fire or repair. Their charge and charge destined for them recover to the brain; reconnecting restores function but does not refill them instantly. Destroying an enemy neuron leaves an empty tile, which must be grown into normally. Specify how every packet is handled when its source/destination dies and test it: it must be delivered, remain in transit, or enter recovery, never two of these.

Prototype routing as deterministic weighted demand: priorities select target shares of the fixed pool, desired deficits pull through shortest connected paths, and shared links limit movement. Default policy reserves a small local defensive floor before allocating surplus; the UI must make an explicit aggressive override visible. If the pool cannot cover every floor, share it proportionally instead of inventing charge. A node has bounded storage, each edge bounded per-tick throughput, and transfers take at least one tick per edge. Nodes above their target share can supply deficits elsewhere, permitting retreat/reallocation. Stable path ties are acceptable for reproducibility but must be tested for directional bias. Use rotating integer remainder allocation to avoid starving small positive demands; persist that state for rollback. Saturated/unreachable demand must not create charge or occupy unbounded queues. This is a candidate algorithm to compare in the headless prototype, not a settled promise of optimal routing.

Bound routing by map size and aggregate quantities, never particle count: at most one breadth-first traversal per candidate sink and one bounded allocation pass per source/sink pair per tick; no iterative convergence loop. Cache only derivable paths against topology revisions. Coalesce transit/recovery records sharing endpoints and due tick; map size, transit horizon, recovery horizon and command queues have hard validated caps. Set initial caps from prototype measurements, then include maximum-size/cap-rejection tests before networking acceptance.

A priority change therefore changes allocation goals, not damage multipliers or instantaneous particle location. The tests must demonstrate both effects: a concentrated front becomes stronger, and the depleted rear becomes vulnerable. Measure recovery shortcuts, rapid priority oscillation, cyclic routing, disconnected fragments and high-priority idle stockpiles before declaring this system viable.

## Existing netcode integration

[`packages/fuse-netcode/src/game.ts`](../../packages/fuse-netcode/src/game.ts) is the actual interface. Implement `id: "neural-defence"`, a new rules identifier such as `neural-defence-1`, `createRoom`, `createTicker`, `scope`, `clock`, `steps`, `maxSteps`, `view`, `hash`, `checkpoint`, `members`, `seat`, `stage`, `settings`, `seating`, `text`, and `isEntry`; add `ordinal` only if the command design needs its extra per-stream monotonic identifier. Set `steps: () => 1` and `maxSteps: 1` initially. `Room.tick` advances exactly once per log tick, including lobby/result ticks.

Use [`management.ts`](../../packages/fuse-netcode/src/management.ts) through the adapter, following the real fold in [`games/dice/src/game/rules.ts`](../../games/dice/src/game/rules.ts). Preserve creator/delegate permissions, current/retired stream generations, seat ownership, presence and ready/start behavior. Four player seats are separate from watchers/display members. One real-time match can occupy one round; rematches get a new gameplay scope. Bots are deterministic input producers evaluated on every replica, with all persistent decision state in the checkpoint.

The existing [`RoomRuntime`](../../packages/fuse-netcode/src/room-runtime.ts), [`rollback.ts`](../../packages/fuse-netcode/src/rollback.ts), [`stream.ts`](../../packages/fuse-netcode/src/stream.ts) and [`snapshot.ts`](../../packages/fuse-netcode/src/snapshot.ts) already own transport coordination, repair, rollback and snapshot transfer. Reuse them without a simulation server or gameplay relay. Model typed commands after [`games/dice/src/app/runtime.ts`](../../games/dice/src/app/runtime.ts), but validate again in the engine. Networking confirmation, not a successful local enqueue, establishes applied state.

Checkpoint decoding must reject invalid ownership, impossible references, map/rules mismatch, impossible particle totals, negative/overflowing balances, invalid clocks, oversized queues and contradictory lifecycle state. Decode into a new fully validated state before installation. A retained snapshot must include jobs, charge compartments, all cooldowns/remainders, research, bot state and connectivity inputs. Derived caches must be recomputable and discarded on rollback; no ticker closure may retain uncheckpointed authoritative decisions.

The contract emits an event at most once per `(matchId, round, log tick, index)`, even if rollback changes its meaning. Consequently ownership, HP, progress, elimination and results render from corrected views; events only drive disposable effects. Never settle persistent match results from a speculative animation/event alone.

Vite already discovers `games/<id>/index.html` and emits `/<id>/` ([config](../../vite.config.ts)). Later integration must add the workspace manifest/lockfile, its Docker manifest copy, and registration in [`service/history.ts`](../../service/history.ts). `EXTRA_GAME_IDS` controls non-default production games; a local registration is not publication. App work must make the game reachable through menus, with real shared-screen and controller flows, rather than only a hidden development URL.

## Visibility and trust

Start with full information, including shared TV play. A future individual-device fog mode filters `observe(state, viewer)` and the rendering view, with bots receiving the same allowed observations. This is casual-play fog only: every peer in the current architecture receives enough state to simulate the entire match. A modified client can inspect hidden enemies. Secure competitive fog would require a different trust/authority architecture and is outside this foundation. Do not promise security from a visibility shader or filtered HUD.

## Headless balance laboratory

Run the same engine and bots without browser, network, rendering or sleeps. Batch configuration records source revision, rules/settings hash, map hash, seeds, policies, player/spawn permutations and maximum simulation ticks. Persist a compact JSON summary plus replay inputs and hashes for failures/outliers. Parallel workers may run separate matches, never parallelize the mutation of one match.

Begin with expansion/economy, concentrated rush, fortified choke and reroute/flank policies. Policies receive ordinary observations, obey the same resource/command limits and use the same action application as humans. Rotate seats and mirror maps; use paired seeds when comparing tuning revisions. Track win/draw rate with uncertainty, game duration, first contact, extraction shares, unspent currencies, particle travel/recovery/idle fractions, territory swings, cut/reconnect events, priority changes and income-to-victory correlation. Report node-ticks per second and memory on a named machine/workload rather than inventing a speed target from an empty board.

Declare and report timeouts as draws/unresolved outcomes, not invisible discarded matches. Include a deterministic draw ceiling in automated experiments; an in-game anti-stalemate rule is a separate gameplay choice. Bot dominance is evidence about those policies, not proof that humans have no counter. Human playtesting remains necessary for readability, control burden, fun and perceived fairness.

## Implementation stages and acceptance

1. **Pure growth/economy skeleton.** Validated maps and commands, fixed ticks, 2–4 slots, two currencies, manual/auto queues, adjacency mining and connectivity. Unit/property tests establish conservation, no overspending, conflicting growth, canonical command ordering and seed reproducibility. No web app required.
2. **Supply/combat prototype.** Priorities, bounded aggregate routing, one tower type, local attack/defence, repair, minimal research, simultaneous destruction and brain elimination. AI-vs-AI CLI produces reproducible summaries/replays. Show a flank counter to concentration and a topology counter to a defended front before adding content.
3. **Replay/room adapter.** Implement and test the real `RollbackGame` contract. Replaying uninterrupted versus checkpoint-resumed or late-input rollback yields identical hashes. Cover duplicate/reordered/dropped commands, stale scope and generation, manager departure, reconnect, invalid snapshots, draw and rematch. Verify both peers' applied worlds, not just transport sends.
4. **Readable web slice.** Real lobby-to-match flow; pointer/touch node selection, resource and charge feedback, visible supply cuts, settings and results; shared TV plus phones. Browser smoke exercises actual two-client play and recovery, captures screenshots and checks narrow screens. Keep cosmetics outside authority.
5. **Measured tuning.** Fixed experiment matrix and human playtest notes; compare alternatives instead of freezing initial numbers. Add fog, powerups, more research or tower types only when the core decisions work. Production activation/deployment is a separate authorized step.

For each engine change, maintain an independent neural-defence rules version and deterministic replay fixture; do not bump Fuse Riders' rules for an unrelated game. Run focused checks while iterating and the repository's required full checks before delivery. This planning-only PR requires document/link/diff validation, not a claim that any of those future engine/browser gates have passed.
