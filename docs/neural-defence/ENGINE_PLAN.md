# Neural Defence: core engine plan

Status: proposed architecture and acceptance plan. No engine or playable game is implemented by this draft. The [Phase 0 plan](PHASE_0.md) defines the next implementation scope for user review and takes precedence over the high-level staging below. Gameplay decisions are in [GAMEPLAY.md](GAMEPLAY.md); numeric settings must remain experimental until measured.

## Reuse the platform, isolate the rules

Create `games/neural-defence/` as a workspace exporting a headless TypeScript library. The engine owns hex geometry, map validation, commands, simulation, bots, canonical state and validation. It imports nothing from networking, DOM, rendering or another game. A thin online adapter implements the existing `RollbackGame` contract; the app composes the existing room transport and UI. The simulation must run identically in Node and browsers.

Proposed layout (these paths do not exist yet):

| Path under `games/neural-defence/` | Responsibility                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `src/engine/`                      | State, integer hex graph, command guards, ordered tick pipeline, seeded RNG, view and checkpoint rules |
| `src/engine/bots/`                 | Deterministic agents emitting ordinary player commands from permitted observations                     |
| `src/online/game.ts`               | `RollbackGame` adapter, management fold, room clock, seating and scope                                 |
| `src/online/runtime.ts`            | Typed command methods over `RoomRuntime.append` and `sendPackets`                                      |
| `src/render/`                      | Read-only world views and cosmetic particle animation                                                  |
| `src/app/`                         | Lobby, game page, board input, phone controller and shared display                                     |
| `src/platform.ts`                  | Game registration and confirmed match facts                                                            |
| `tests/`, `scripts/`               | Replay fixtures, invariants, network integration and batch balance runner                              |

The existing [`scripts/new-game.ts`](../../scripts/new-game.ts) copies Pig, including its turn rules. Use its workspace/app wiring as a reference or scaffold, then replace those rules; do not evolve Pig's turn model into an RTS. The engine's public entrypoint should expose `createMatch`, `step`, `observe`, state codec/hash and bot policy interfaces without importing the app. Proposed `step(state, commands)` advances exactly one fixed tick and returns gameplay facts. No wall-clock waits, global mutable bot state or unseeded randomness.

## Simulation contract

Start with one simulation step per existing 50 ms log tick (20 Hz; [`clock.ts`](../../packages/fuse-netcode/src/clock.ts)). Headless acceleration repeatedly calls the identical step, without sleeping; it does not multiply damage or skip ticks. Rendering may interpolate but cannot advance construction, projectiles or resource extraction.

Use axial integer hex coordinates with a canonical tile index and six fixed neighbor directions. Use integer/fixed-point HP, resources, charge and rates; persist remainder accumulators for fractional yields. All multiplication must stay within explicitly validated safe-integer bounds. Graph traversals, entity enumeration, event order and equal-cost routing use canonical ordering, never object insertion order or locale sorting. Maps, rules version, seed and settings are part of state compatibility. Hash and encode every authoritative field, including routing remainders, cooldowns and RNG state.

A first map is a versioned `.json` file describing traversable cells, blockers, non-buildable resource deposits, tower sites and up to four brain spawn slots. Start at **12 columns × 12 rows (144 cells)**, with configurable bounded width and height. Use an `odd-r` offset rectangle: row-major index is `row * width + column`; canonical axial coordinates are `q = column - floor(row / 2)`, `r = row`. This conversion is an engine map contract, not dependent on rendering.

The initial JSON shape is `{ schemaVersion: 1, id, width: 12, height: 12, layout: "odd-r", cells, spawns }`. `cells` contains exactly `width * height` row-major entries with a terrain enum (`open`, `blocked`, `deposit`), a `resourceKind` (`biomass` or `insight`) only for deposits, and an optional `towerSite` flag only on open terrain. `spawns` contains unique `{ slot, cellIndex }` entries on open non-tower cells. Keep `schemaVersion` separate from gameplay `rulesVersion`. A pure `loadMap(unknown)` validates and returns a canonical `MapDefinition`; the app/CLI reads files, never the engine. Hash canonical map content, not paths, JSON whitespace or object-key order. No embedded scripts or assets. A later map editor must import/export this same schema and use the same public validator; no editor is needed now.

Validate integer dimensions and caps, exact cell count, enums/field combinations, unique valid spawn slots/cells, reachable expansion areas and tower-site ring geometry. Deposits mine only through their traversable neighboring cells; initial maps must give each deposit six usable neighbors. Distinguish connectivity validity from balance: a connected map can still favor a spawn. Begin with a sparse hand-authored map; test opposite-corner two-player starts and four-corner configurations by graph distance, chokepoint width and resource access. A hex lattice does not have square fourfold symmetry: rotate spawn assignments and measure outcomes, including three-player and asymmetric maps, rather than claim equal-looking corners are fair.

Match settings explicitly distinguish `sandbox` (one human, zero bots, no automatic victory/time cap or career settlement) from `competitive` (2–4 participants). Local session statistics may later be collected in either mode, with sandbox/debug runs clearly labelled. The same engine supports both; solo does not create a fake opponent. For offline sandbox setup, the app parses `?debug` into `instantConstruction` and `instantResearch` settings. These settings are validated, snapshotted and hashed; `step` never reads a URL or browser state. They retain costs, prerequisites and connectivity checks. Any generous starting stocks must be a separate explicit bounded setup value, not an implicit unlimited-resource cheat. Show debug status visibly and exclude sandbox/debug runs from career results and competitive balance aggregates. Initially reject debug options outside offline solo sandbox; network clients cannot enable them unilaterally.

Each command names its match/round, actor, target and relevant entity generation. Commands include queued neuron construction/cancel, node priority, tower build and research choice; automatic expansion is deferred. One active neuron job per player consumes a bounded explicit destination queue. Validate each destination when starting it: insufficient funds waits, while illegal or obsolete entries are skipped with reasons; unstarted entries reserve neither tiles nor money. The online fold takes actor identity from the member stream and current logged seat/generation, never a user-supplied player ID; this preserves the existing trusted-peer model, not a new anti-cheat guarantee. Limit payload size, queue length, targets and accepted actions per tick. Validate shape at ingress, then ownership, connectivity, phase, prerequisites and affordability at application. UI validation is only feedback. Invalid/stale commands are deterministic no-ops with observable rejection reasons.

### Proposed tick pipeline

1. Fold shared room management; determine active roster and match scope. During play, loss of presence does not pause the world or eliminate a brain. Autonomous jobs continue; new human orders require a valid current stream. Never silently replace an absent player with a new bot.
2. Snapshot tick-start eligibility, connected components, balances and completed upgrades. Fold player intentions in stream sequence order; bots use the same command path. A player's queued spending order is explicit. Reserve costs against tick-start balances, so simultaneous orders cannot overspend.
3. Resolve neutral growth claims as a batch. If multiple owners claim one tile on this tick, reject all competing claims and release reservations. Stable IDs order processing but never win contested land. No charge for a rejected claim. Advance construction and research with integer progress; an instant-duration job, including one accepted this tick, completes in this phase. Completed structures/upgrades become operational next tick. Consider at most one new neuron job per player per tick, never draining a queue recursively through same-tick completions.
4. Extract resources from tick-start connected neighboring ownership. A deposit has a fixed per-neighbor rate: each of its six owned adjacent cells earns one sixth of maximum output for its owner. Unowned shares remain unmined; two owners cannot each extract the whole deposit. Credit after this tick's reservations, available next tick. Insight's small brain trickle follows the same accounting.
5. Mature scheduled particle recovery and deliver previously scheduled transit. Derive flow requests from the eligible neural graph and current priority targets. Allocate each source, each link's bounded capacity and each destination's unreserved storage once, then commit transfers together. Every in-flight unit reserves one destination slot until delivery or recovery; `nodeCharge + incomingReservations <= nodeCapacity` always. Release reservations when a target dies/disconnects and move the corresponding charge to recovery atomically; never clip an arriving packet to capacity or redirect it without transferring its reservation. New transfers cannot be forwarded again during this tick.
6. Choose legal local attacks, tower pulses and repair from the same pre-combat state. Reserve the finite local particle availability across these actions; a unit committed to attack cannot also shield or repair this tick. Base structural resistance remains separate. Record damage/repair intents without mutating targets during enumeration.
7. Resolve damage simultaneously, then destruction and graph cuts together. A neuron that fired before lethal damage still fired. Destroyed/disconnected node particles and affected transit move to recovery exactly once. Construction/tower-ring legality uses tick-start eligibility; combat can subsequently destroy its support. A completed disconnected structure remains inactive.
8. Resolve brain deaths together. In competitive mode, one survivor wins; no survivors is a draw, never an iteration-order winner. Sandbox skips victory evaluation. Eliminated players stop orders, economy and combat. Account for all their particles in a terminal retired compartment before clearing board ownership. Record facts, advance the clock and assert invariants.

The precise phase order is a versioned rule. A repair in phase 6 cannot resurrect a structure already destroyed in an earlier tick. Repair applies only if no incoming raw damage was committed against that target this tick; otherwise release its repair reservations. For an eligible target, HP becomes `min(maxHP, startHP + repair)`; a damaged target loses post-shield damage and is destroyed at zero. Research completed this tick applies next tick. No rendered animation completion controls an engine outcome.

Use **Biomass** for growth/construction/repair and **Insight** for research. Accepted construction spends its reserved cost once. A construction site is exclusive, damageable and non-operational, with explicit builder ownership distinct from completed tile ownership. Losing its brain connection pauses progress; it does not refund the purchase. Cancelling an unstarted queue item costs nothing; cancelling a started site or losing it to attack gives no refund in the first prototype. This avoids cancellation being free temporary territorial denial. New claims cannot target an existing site. Towers require their centre site and all six surrounding cells to be owned and brain-connected at placement; losing the ring later does not remove the tower, while losing its own brain connection disables it. Publish these distinctions in the view contract so a ghost preview cannot be mistaken for acquired territory.

### First combat contract

The authoritative first prototype contract is in [PHASE_0.md](PHASE_0.md). A player simultaneously owns assault and guard particles, with distinct attack/protection properties. Connected completed neurons/brains commit bounded local particles to adjacent attacks; uncommitted local particles can defend. Damage is derived from actual committed types and their immutable research profiles, not a homogeneous charge count or a cosmetic field. Research, dispatch, target selection, attack/defence reservation and simultaneous destruction all have explicit tick ordering there. Construction sites do not fire. Particle-powered attack/defence is required in Phase 0, even while human online matches remain deferred.

A tower uses this same local particle budget and cooldown system but fires at one nearest hostile target within hex distance two. Equal-distance targets rotate in canonical order. Terrain blockers intersecting a deterministic supercover hex line block the shot; friendly neurons do not. Range two is necessary to reach beyond the required friendly ring. Shots resolve in their firing tick: the renderer may draw a pulse, but no independent projectile physics or animation delay affects hits. Future projectile travel would be a separately versioned rule.

All eligible attackers emit before any death is committed, so mutual destruction is valid. Armour and shielding follow the type-aware damage accounting in the Phase 0 contract: a stronger defensive particle can absorb more damage without becoming multiple particles, and a particle committed to attack cannot also defend. Disconnected nodes retain structural HP but lose operational flow/combat according to the cut policy. Later tower and repair rules must preserve these same accounting semantics.

Optional repair is a bounded automatic action on connected damaged nodes with zero incoming raw damage, after attack and shield reservations: spend a configured integer Biomass cost and particle cost for a configured HP increment, capped at missing HP. Affordability is reserved across the player's repairs in a rotating canonical node order. This avoids free regeneration, spending the same charge twice, and permanent repair under fire. If the first prototype is too broad, defer repair entirely rather than add a separate healing clock.

## Heterogeneous particles on a flow network

Simulate discrete typed particles moving through the neural graph. A bounded aggregate representation groups only identical particles: owner, type, immutable research profile, location/route intent and travel/arrival state must match. Splitting a cohort partitions its count; merging unlike types or properties is forbidden. This is an optimization of particle gameplay, not a continuous field approximation. Visible particles illustrate real type counts, positions and travel progress; their cosmetic paths do not determine damage. The flow simulator is a Phase 0 requirement.

For each player, the MVP invariant after every phase is:

`startingPool = storedParticles + inTransit + recovering + brainReserve + refitting + retired`

Every term is nonnegative; every transfer subtracts and adds the same integer once. Track each compartment by particle type/profile, with explicit refit conversions at the brain when composition changes; those conversions preserve the player's total pool. There is no passive particle creation or capacity research in the first prototype. Combat spends particles into delayed recovery, never silently deletes them or awards them to another owner. Recovery/refit cannot teleport a new type or upgraded property into a frontline cohort. The Phase 0 contract fixes recovery delay, saved return-distance accounting, bounded refit work and immutable in-flight timing. Test intentional sacrifice and rapid refit/priority changes for shortcuts before accepting the model.

Disconnected neurons retain ownership and HP but cannot mine, grow, fire or repair. Their charge and charge destined for them recover to the brain; reconnecting restores function but does not refill them instantly. Destroying an enemy neuron leaves an empty tile, which must be grown into normally. Specify how every packet is handled when its source/destination dies and test it: it must be delivered, remain in transit, or enter recovery, never two of these.

The Phase 0 routing contract defines per-type demand, storage reservations, shared edge capacity and finite hop latency. Distinguish **speed** (time to cross a link), **throughput** (particles admitted per tick) and **storage** (particles held at a neuron). A future speed upgrade must not silently increase the other two. Existing transit keeps its recorded arrival time when research completes; new dispatch uses the allowed profile version. Reallocation physically travels links. All allocation is simultaneous and bounded, with deterministic ties and checkpointed fairness state. Test this candidate algorithm for congestion, cyclic routes, starvation and directional bias rather than assuming optimality.

Bound routing by map size, active destinations and validated particle/cohort limits; no iterative convergence loop. Cache only derivable paths against topology revisions. Coalesce only records with matching type/profile and all route/timing semantics. Map size, active profiles, transit/recovery horizon and command queues have hard validated caps. Backpressure delays particles rather than clipping or losing them. Measure maximum-size mixed-type scenarios before networking acceptance.

A priority change therefore changes allocation goals, not damage multipliers or instantaneous particle location. The tests must demonstrate both effects: a concentrated front becomes stronger, and the depleted rear becomes vulnerable. Measure recovery shortcuts, rapid priority oscillation, cyclic routing, disconnected fragments and high-priority idle stockpiles before declaring this system viable.

## Existing netcode integration

[`packages/fuse-netcode/src/game.ts`](../../packages/fuse-netcode/src/game.ts) is the actual interface. Implement `id: "neural-defence"`, a new rules identifier such as `neural-defence-1`, `createRoom`, `createTicker`, `scope`, `clock`, `steps`, `maxSteps`, `view`, `hash`, `checkpoint`, `members`, `seat`, `stage`, `settings`, `seating`, `text`, and `isEntry`; add `ordinal` only if the command design needs its extra per-stream monotonic identifier. Set `steps: () => 1` and `maxSteps: 1` initially. `Room.tick` advances exactly once per log tick, including lobby/result ticks.

Use [`management.ts`](../../packages/fuse-netcode/src/management.ts) through the adapter, following the real fold in [`games/dice/src/game/rules.ts`](../../games/dice/src/game/rules.ts). Preserve creator/delegate permissions, current/retired stream generations, seat ownership, presence and ready/start behavior. Four player seats are separate from watchers/display members. One real-time match can occupy one round; rematches get a new gameplay scope. Bots are deterministic input producers evaluated on every replica, with all persistent decision state in the checkpoint.

There is a concrete solo integration gap: `RoomRuntime` describes solo bots as at least one, although its loop accepts zero, and its start/rematch guards currently require two connected players. Add a scoped per-game, settings-aware minimum-participant capability (default two, Neural Defence sandbox one), honored both by runtime guards and the authoritative game fold. Permit zero bots for this sandbox without globally relaxing other games or inserting a temporary fake bot.

The existing [`RoomRuntime`](../../packages/fuse-netcode/src/room-runtime.ts), [`rollback.ts`](../../packages/fuse-netcode/src/rollback.ts), [`stream.ts`](../../packages/fuse-netcode/src/stream.ts) and [`snapshot.ts`](../../packages/fuse-netcode/src/snapshot.ts) already own transport coordination, repair, rollback and snapshot transfer. Reuse them without a simulation server or gameplay relay. Model typed commands after [`games/dice/src/app/runtime.ts`](../../games/dice/src/app/runtime.ts), but validate again in the engine. Networking confirmation, not a successful local enqueue, establishes applied state.

Checkpoint decoding must reject invalid ownership, impossible references, map/rules mismatch, impossible particle totals, negative/overflowing balances, invalid clocks, oversized queues and contradictory lifecycle state. Decode into a new fully validated state before installation. A retained snapshot must include jobs, charge compartments, all cooldowns/remainders, research, bot state and connectivity inputs. Derived caches must be recomputable and discarded on rollback; no ticker closure may retain uncheckpointed authoritative decisions.

The contract emits an event at most once per `(matchId, round, log tick, index)`, even if rollback changes its meaning. Consequently ownership, HP, progress, elimination and results render from corrected views; events only drive disposable effects. Never settle persistent match results from a speculative animation/event alone.

Vite already discovers `games/<id>/index.html` and emits `/<id>/` ([config](../../vite.config.ts)). Later integration must add the workspace manifest/lockfile, its Docker manifest copy, and registration in [`service/history.ts`](../../service/history.ts). `EXTRA_GAME_IDS` controls non-default production games; a local registration is not publication. App work must make the game reachable through menus, with real shared-screen and controller flows, rather than only a hidden development URL.

## Visibility and trust

Start with full information, including shared TV play. A future individual-device fog mode filters `observe(state, viewer)` and the rendering view, with bots receiving the same allowed observations. This is casual-play fog only: every peer in the current architecture receives enough state to simulate the entire match. A modified client can inspect hidden enemies. Secure competitive fog would require a different trust/authority architecture and is outside this foundation. Do not promise security from a visibility shader or filtered HUD.

## Headless balance laboratory

Run the same engine and bots without browser, network, rendering or sleeps. Batch configuration records source revision, rules/settings hash, map hash, seeds, policies, player/spawn permutations and maximum simulation ticks. Persist a compact JSON summary plus replay inputs and hashes for failures/outliers. Parallel workers may run separate matches, never parallelize the mutation of one match.

Begin with expansion/economy, concentrated rush, fortified choke and reroute/flank policies. Policies receive ordinary observations, obey the same resource/command limits and use the same action application as humans. Rotate seats and mirror maps; use paired seeds when comparing tuning revisions. Track win/draw rate with uncertainty, game duration, first contact, extraction shares, unspent currencies, particle travel/recovery/idle fractions, territory swings, cut/reconnect events, priority changes and income-to-victory correlation. Report node-ticks per second and memory on a named machine/workload rather than inventing a speed target from an empty board.

Declare and report timeouts as draws/unresolved outcomes, not invisible discarded matches. Include a deterministic draw ceiling in automated experiments; an in-game anti-stalemate rule is a separate gameplay choice. Bot dominance is evidence about those policies, not proof that humans have no counter. Human playtesting remains necessary for readability, control burden, fun and perceived fairness.

## Session statistics and future graphs

Preserve a path to useful end-of-session graphs without making a statistics dashboard a Phase 0 requirement. **Phase 0 supplies only the semantic foundation:** stable player IDs, canonical simulation ticks, read-only state inspection and typed step outcomes describing actual resource credits/debits and construction/research transitions. These facts must identify their player, resource, amount and reason where applicable; a balance difference cannot distinguish income from spending in the same tick. Facts describe committed rule effects, not attempted commands. The pure engine performs no file, database or upload operations.

A later observer outside authoritative state builds per-player series and timelines for every participant, including eliminated players. Its public typed input and injected output sink support strongly typed in-memory fakes; a missing, slow or failed sink cannot change simulation outcomes. Keep stock, flow and event semantics explicit:

| Record                                 | Initial economy/construction coverage                                                                                                                                           | Later combat coverage                                                             |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Stocks sampled at a tick               | Biomass/Insight balances; owned connected and disconnected completed tile counts; construction-site counts separately                                                           | Particle compartments, surviving structures and HP                                |
| Flows accumulated over a tick interval | Actual earned/spent totals by currency and reason; mining income by resource type separated from brain income; mining rate derived from interval income and simulation duration | Damage dealt/received, attack/defence expenditure and particle transfers/recovery |
| Timeline facts at exact ticks          | Construction started/completed/cancelled; research started/completed/cancelled; connection loss/restoration                                                                     | Destruction, elimination and match outcome                                        |

Use ticks as the time axis, optionally displaying seconds using the recorded tick duration; never use wall-clock timestamps to measure gameplay. A report records its schema version, room/match/round scope, map identity and content hash, rules version, settings (including debug), seed, participant IDs/display labels/spawns, and ending tick/reason/outcome. Leaving a solo sandbox creates a stopped session, not a fabricated victory. Graphs distinguish unavailable data from zero.

Only confirmed applied ticks contribute durable totals and final reports. If provisional live graphs are offered, keep their suffix replaceable: rollback truncates/recomputes affected samples and facts, and duplicate delivery cannot count a tick twice. Rebuild from canonical state/replayed typed step outcomes, **not** the adapter's positional animation events, whose `(matchId, round, log tick, index)` deduplication can suppress corrected facts. Finalization waits for the confirmed end tick, freezes one immutable report per scope, and resets observer state on reset/rematch/room change so data cannot leak into the next session. Offline runs must define their equivalent committed-tick boundary explicitly.

The collector implementation must define validated numeric limits for sampling interval, retained samples, timeline records and any replay buffer before it ships. Compact/downsample older history deterministically while preserving exact aggregate totals; record retained tick ranges, gaps and truncation flags instead of silently presenting incomplete history as a full match. Reconnect can restore an optional versioned, validated aggregate/sample snapshot anchored to a confirmed tick and scope, or replay available history. Without either, mark earlier history unavailable. These optional statistics snapshots are separate from authoritative gameplay checkpoints and cannot affect hashes or play. Collector, persistence, graph UI and career-result integration remain later work; Phase 0 does not require them.

## Implementation stages and acceptance

1. **Phase 0: particle gameplay foundation.** Follow [PHASE_0.md](PHASE_0.md): menu, validated JSON maps, four-player-ready state, solo sandbox, economy/construction/research, typed particle transport with real latency and mixed-type attack/defence. The same headless rules power a minimal combat assay and the existing offline room adapter. Typed tests cover conservation, capacity/backpressure, research profiles/refit, simultaneous damage, replay and action validation. Polished art, towers and a map editor wait; the flow/combat simulator does not.
2. **Strategy and content iteration.** Expand scenarios and policies using [RTS_PLAYBOOK.md](RTS_PLAYBOOK.md), add one tower type and selected technologies, and measure positional/composition counters. AI-vs-AI experiments produce reproducible summaries/replays. Prove plausible responses to concentration, economic expansion and fortification before adding a larger catalogue.
3. **Replay/room adapter.** Implement and test the real `RollbackGame` contract. Replaying uninterrupted versus checkpoint-resumed or late-input rollback yields identical hashes. Cover duplicate/reordered/dropped commands, stale scope and generation, manager departure, reconnect, invalid snapshots, draw and rematch. Verify both peers' applied worlds, not just transport sends.
4. **Readable web slice.** Real lobby-to-match flow; solo sandbox without AI, pointer/touch node selection, resource and charge feedback, visible supply cuts, settings and results; shared TV plus phones. Browser smoke covers zero-bot start/rematch, normal and debug sandbox with visible debug status and no career settlement, plus actual two-client play and recovery. Capture screenshots and check narrow screens. Keep cosmetics outside authority.
5. **Measured tuning.** Fixed experiment matrix and human playtest notes; compare alternatives instead of freezing initial numbers. Consider automatic expansion, a map editor, fog, powerups, more research or tower types only when the core decisions work. Production activation/deployment is a separate authorized step.

For each engine change, maintain an independent neural-defence rules version and deterministic replay fixture; do not bump Fuse Riders' rules for an unrelated game. Run focused checks while iterating and the repository's required full checks before delivery. This planning-only PR requires document/link/diff validation, not a claim that any of those future engine/browser gates have passed.
