# Phase 0: build, mine and fight through a particle network

Status: **implementation proposal for user review; nothing below is implemented**. This is the bounded first milestone of [ENGINE_PLAN.md](ENGINE_PLAN.md), not permission to begin implementation. The wider game remains in [GAMEPLAY.md](GAMEPLAY.md).

## What the player can do

Open Neural Defence from the game menu, choose a small JSON map and start an offline, one-player sandbox with no AI. Construct neurons, mine Biomass and Insight, research, and redistribute a finite mixture of assault and guard particles through the growing network. Travel takes real simulation time. Particles are the attack and defence mechanism, not decoration over a separate damage system. Time advances continuously during visible play; there are no turns or automatic solo victory. `?debug` makes construction and research instant while retaining costs and legality; particle travel and combat still take time.

The core includes actual transport, redistribution, attack, defence, branch cuts and brain destruction. A separate deterministic combat-lab preset supplies an opposing network and scripted commands, not AI; two- and four-player headless scenarios exercise those same rules. Keep the empty solo sandbox available independently. This establishes a testable combat hypothesis, not proven balance. Defer towers, repairs, AI policies, automatic expansion, fog, powerups, map editing, online rooms, career settlement and production deployment. Tower-site metadata may be validated/displayed but cannot construct a tower yet.

## Engine and dependency boundaries

Create `games/neural-defence/` with a public headless engine entrypoint. Keep map validation/geometry, state, commands, economy, jobs, research, observation and state codec/hash in `src/engine/`; app, rendering and the thin room adapter remain outside it. The engine imports no DOM, networking, file system, other game, timer or application module. Do not introduce an ECS, plugin framework or DI container for this slice.

- `loadMap(raw: unknown)` returns a validated canonical definition or structured errors with field paths. `createMatch(map, settings, roster)` returns validated initial state with explicit player/slot assignments. `step(state, commands)` advances exactly one simulation tick. `observe(state)` returns read-only presentation data; encode/decode/hash cover all authority.
- The engine receives explicit immutable map/rules/settings and validated commands. State holds every mutable gameplay decision: tick, scope, ownership, balances, accrual remainders, bounded queues, active jobs, research, particle cohorts/transit/reservations/recovery/refits, routing cursors and command cursors. Helpers may mutate an exclusively owned working state, but stepping cannot mutate caller-owned maps, commands or retained checkpoints.
- Inject side effects at composition boundaries. Reuse `RuntimeDependencies` in [`room-runtime.ts`](../../packages/fuse-netcode/src/room-runtime.ts): `now`, `hidden`, `token`, `generation`, `schedule`, `onVisibilityChange`. Inject the existing transport dependency separately; solo must never construct a transport. Add only a narrow typed `MapRepository` port for async catalog/map loading, with browser-fetch and in-memory fake implementations. No generic service locator.
- Tests use interface-conforming fakes with controllable time, scheduled callbacks, visibility and map-loader outcomes. No `as any`, private-field mutation, global timer/fetch monkeypatches or sleeps. Do not mock the rules being tested. Test pure engine steps directly; use boundary fakes for app/runtime integration.
- No RNG is needed for the authored Phase 0 map. Later randomized rules use explicit seeded state stored in checkpoints; an injected mutable RNG closure must never hide authoritative state from replay.

Reuse the existing `RoomRuntime` solo path and `TickClock` at 50 ms per tick (20 Hz), through a minimal `RollbackGame` adapter in Phase 0. Set `steps = 1`, `maxSteps = 1`; the adapter folds commands into the same engine used headlessly. Rendering consumes views and interpolation only. Do not introduce a second application simulation interval or a temporary local-only rules implementation.

The existing runtime requires two participants when starting/rematching. Add a narrowly scoped optional per-game/settings minimum-participant capability, defaulting to two, and permit zero configured solo bots. Neural Defence offline sandbox selects one; both runtime guards and its authoritative management fold enforce that choice. Existing games retain their defaults. Completing the local adapter now does not include opening online rooms or claiming network qualification.

The current runtime pauses solo time while the page is hidden. Retain this explicit sandbox convenience, show paused/resumed status where appropriate, and test it; visible play never waits for input. Headless runs always advance exactly the requested ticks without sleeping. Online continuous-time and reconnect behavior remain later work.

## Four-player foundations from the first state model

The Phase 0 UI launches one player, but the headless world, commands, codec and economy must already handle four independent players. `createMatch` takes an explicit roster and slot assignments; core fixtures may contain 1–4 players while the sandbox app/adapter enforces exactly one human. Four is the first supported capacity, not a pair of hard-coded sides. Keep capacity in a named validated rules/configuration limit, so extending it later does not require replacing ownership representations.

| Data                  | Required ownership and scope                                                                                                                                                                                |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Static map cell       | Terrain/resource/tower-site metadata only; no local-player ownership baked into the JSON                                                                                                                    |
| Runtime cell occupant | A discriminated empty, construction-site or completed-structure value; every occupied variant carries a stable `ownerId` referencing the roster and an entity identity/generation                           |
| Player state          | Keyed by stable player ID: assigned spawn/slot, brain reference, currency balances, construction queue/job, research job/completions and command cursor; no singleton player balance or global upgrade flag |
| Connectivity          | Resolve each player's graph through their own completed structures; adjacent foreign structures never supply connectivity, construction eligibility or mining                                               |
| Deposit economy       | Deposits stay neutral; calculate connected neighboring contributions and fractional remainders separately for every owner, including three or four owners sharing one deposit                               |
| Commands/views        | Actor identity and explicit target ownership checks in the engine; selected/local player belongs to app/view context, never defines world ownership                                                         |

Player ID, spawn slot and display colour are distinct concepts. Do not encode cells as `isMine`/`isEnemy`, and do not assume there is exactly one opponent. Keep player iteration canonical and serialized ownership references validated. Render ownership using a palette keyed by slot plus an independent shape/pattern; changing the viewed player cannot alter simulation state. Future elimination may mark a roster member inactive, but must not renumber surviving IDs or reassign historical statistics.

Four-player headless fixtures are required despite multiplayer UI/network play being deferred. Verify isolated economies, particle pools/profiles/priorities and research, foreign-ownership rejection, shared mining, checkpoint round-trips, simultaneous construction conflicts and multi-owner combat. Player-local UI is never an authority shortcut.

## Authored map contract

Ship `games/neural-defence/maps/sandbox-12.json`, with a small explicit catalog describing its id, title and filename. The catalog is presentation data; the map file is authoritative input. The app loads the selected file through `MapRepository`, validates before launch, and retains its canonical content/hash for checkpoints. Use Vite-emitted map assets (for example `?url` imports), so built previews fetch real emitted files rather than development-only source paths. The repository adapter owns URLs; the engine sees only parsed input. File paths are never gameplay identity.

The first schema is the existing proposed shape, made concrete:

```ts
type MapFileV1 = {
  schemaVersion: 1;
  id: string;
  width: number;
  height: number;
  layout: "odd-r";
  cells: Array<
    | { terrain: "open"; towerSite?: boolean }
    | { terrain: "blocked" }
    | { terrain: "deposit"; resourceKind: "biomass" | "insight" }
  >;
  spawns: Array<{ slot: number; cellIndex: number }>;
};
```

`cells` is exactly `width * height` entries, ordered by row then column; no sparse holes. Tile index is `row * width + column`. Axial coordinates are `q = column - floor(row / 2)`, `r = row`; six neighbors follow fixed engine directions, never visual proximity. Deposit cells and blockers cannot be occupied. Resource rates belong to versioned rules, not duplicated per deposit. A future editor imports/exports this format and calls the same public validator; no editor-specific second schema.

Initial bounds: each dimension 1–64, at most 4,096 cells, map JSON at most 256 KiB before parsing, id 1–64 lowercase letters/digits/hyphens, and 1–4 unique spawn slots in 0–3 on distinct open non-tower cells. Reject unsupported versions, unknown keys, non-integers, out-of-range references, malformed field combinations and oversized data. Every spawn needs an expansion neighbor and a traversable route to a neighboring cell of each resource kind; every deposit and tower site needs six open neighboring cells. All open cells must belong to one traversable component for this initial map format. Report structural validity separately from map fairness.

The shipped map is 12 × 12, sparse blockers, both resource kinds, four spawn slots, and at least one route of at most three new neurons from each spawn to each resource kind. Solo chooses one spawn; unused spawn cells behave as ordinary open cells. The engine supports four-player headless fixtures from Phase 0; the playable launch accepts exactly one human. Multiplayer play and map fairness assessment are deferred.

Keep `schemaVersion`, Neural Defence `rulesVersion` and checkpoint format version distinct. Canonical map hashing includes all validated gameplay content and ignores JSON whitespace/object-key order. Snapshots include canonical map content, settings and rules identity; decoding must validate everything into a fresh state before installation. A same-id map edit changes its content hash and cannot silently resume an incompatible snapshot. Unsupported versions fail visibly; no speculative migration framework is needed.

## Concrete first economy and research

These are testable starting values, not balanced commitments. Store resources in integer milli-units (1,000 = one displayed unit), with a bank cap of 1,000,000 displayed units per currency and validated safe-integer intermediates.

| Item                       | Phase 0 proposal                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------ |
| Initial state              | One completed brain; 60 Biomass, 0 Insight; no other owned cells                     |
| Brain income               | 1 Biomass/second and 0.5 Insight/second                                              |
| Neuron construction        | 20 Biomass; 120 ticks (6 seconds); one active job per player                         |
| Biomass deposit            | 6 Biomass/second at six connected owned neighbors                                    |
| Insight deposit            | 3 Insight/second at six connected owned neighbors                                    |
| Growth Efficiency research | One tier; 10 Insight; 400 ticks (20 seconds); one research job per player            |
| Research effect            | Neurons started after activation take 80 ticks (4 seconds), still costing 20 Biomass |

Three neurons can reach a deposit using starting Biomass; baseline income prevents a permanent economic dead end after cancellation or poor routing. Insight trickle funds research after 20 seconds without a deposit, while reaching an Insight deposit accelerates it. Deposits never deplete. After Growth Efficiency and one combat specialization complete, Insight may accumulate without a further sink; this deliberate prototype limit is not a finished economy.

Growth Efficiency remains an economic option, separate from the combat specialization below. It changes only subsequently started construction durations. Add a mutually exclusive one-tier choice: **Excitation** raises assault attack from 2 to 3; **Insulation** raises guard absorption from 2 to 3. Each costs 10 Insight and takes 400 ticks, sharing the single research job. UI previews the property changed and which particles will receive it. These typed definitions are deliberately small; no broad research-tree framework is needed. The electricity naming describes particle properties, not an additional field solver.

For a deposit with maximum integer milli-unit rate `R` per second and `n` eligible neighbors, accrue `R * n` into a per-player/per-deposit remainder each tick; divide by `6 * 20` to obtain whole milli-units and retain the remainder. Brain income uses denominator 20. This preserves fractional income, grants nothing for unowned sides and supports later shared deposits without multiplying total production. A completed, brain-connected brain/neuron counts; queued destinations and construction sites do not. At the bank cap discard excess whole income, retaining only the proper fractional remainder; do not store an overflow payout.

## Particle transport and combat: the core hypothesis

All numbers here are initial test parameters. Each player owns exactly **128 reusable particle units**, initially 64 assault and 64 guard in the brain reservoir. Assault has attack 2 / absorption 1; guard has attack 1 / absorption 2. Both types coexist, travel over the same links and compete for their capacity. The player chooses composition and per-type destination priorities. No neutral resource deposit creates particles and more territory does not automatically increase this pool.

Represent integer cohorts keyed by owner, type, immutable property-profile ID, destination, location/edge and timing. Merge only identical keys; never average unlike types or profiles. Profiles carry attack, absorption and ticks-per-edge, with validated integer bounds. Base speed is four ticks per edge; speed upgrades come later and must remain separate from throughput and storage. No authoritative moving sprites, unbounded particle objects, continuous solver or render-dependent collision physics.

- **State and capacities:** each completed neuron retains at most 32 units for deployment; the brain retains 128. A separate relay buffer is capped at 128 units per node, bounded also by the player's total pool. Relay units cannot fight. Each physical friendly edge shares an eight-unit/tick launch budget and 32-unit transit cap across both directions and both types. Allocate competing requests by checkpointed rotating canonical order. Track departure/arrival ticks, next-node buffer reservations and ultimate-target demand reservations explicitly. A large bounded relay buffer prevents a full combat store from permanently blocking through traffic; all physical locations still participate in the same conservation sum.
- **Routing:** allow at most eight positive-priority destinations/player, each with assault/guard weights 0–3. Brain reservoir is the fallback for unallocated units. Compute joint quotas from available counts by type (reservoir + deployed + relay + transit; exclude recovery/refit). Starting with zero assigned quotas, allocate one unit to the eligible `(destination,type)` pair with smallest `(assigned + 1) / weight`, comparing integer cross-products; ties use stable canonical pair order. A pair is eligible only if its type has unallocated stock and its node has free shared capacity across both types. Stop when no pair is eligible; excess stays allocated to the brain. This reference allocator takes at most 128 assignments/player; an optimized equivalent must produce identical quotas. Identical inputs always give identical quotas: never rotate quota remainders merely because another tick passed. Count committed transit toward its destination, so it is not dispatched twice. Supply is stored stock above its quota; demand is quota minus stored/committed stock. Match surplus to deficits by shortest friendly-hop distance, with a checkpointed tie cursor advanced only on actual allocation, then route over a canonical shortest path. Cache distance maps per destination/topology, never as hidden authority. Changed priorities redistribute existing frontline stock through real edges. Test a settled unchanged network produces no further transfers and capped excess is offered to other eligible pairs without type over-allocation.
- **Latency/backpressure:** reserve receive capacity before departure; capacity failure leaves a cohort at its current node. Departures use a frozen candidate set and cannot traverse multiple edges in one tick. Arrivals may fight this tick but forward no earlier than the next tick. Priority changes never alter the current edge or arrival time; reconsider destination after arrival, releasing/replacing its demand reservation atomically. Intermediate relay buffers may only forward or return particles, never create local combat strength. Final delivery converts relay to deployed stock subject to its reserved storage slot.
- **Composition:** `setParticleMix` sets desired assault count 0–128; guard is the complement. Refit up to eight idle brain-reservoir units in one 20-tick job, automatically repeating toward that target while suitable idle stock exists. Refitting temporarily removes units from supply, preserves total count, and converts type only on completion. It costs time and unavailable strength, not currency in this prototype. No frontline or in-flight type conversion. An accepted refit locks its input/output types and count and completes even if the desired mix changes; new settings affect only the next job. At completion, recompute the remaining difference from counts in every compartment, including recovery, before starting another bounded job next tick. Thus a reversal can temporarily miss the new target, but never cancels progress for free or double-converts stock. Test rapid target reversals, exact completion and eventual convergence once suitable stock returns.
- **Research timing:** research activates next tick. Existing deployed/transit cohorts retain their complete immutable profile. Units dispatched from the brain after activation latch the new profile; returned/recovered units may receive it on redispatch. At most two property revisions per type exist in this slice (base and researched); type IDs and research revisions are distinct. Future speed research also latches on dispatch: an in-flight edge's arrival tick never changes. Research therefore has a visible mobilization delay beyond its purchase timer.
- **Disconnection:** branch cuts remove income, job progress, routing and combat eligibility at the next tick. Stranded cohorts become inert and return through an explicit unavailable recovery process lasting 120 ticks plus their saved last-connected brain distance × their profile's ticks-per-edge. Destroyed endpoints invalidate transit/reservations and trigger the same recovery. Store that distance before severing the route; do not invent a zero-length route across a cut. The front receives no instant replacement. Reconnection does not cancel recovery already started.

**Minimal combat resolution.** Completed brains have 240 HP, neurons 60 HP; construction sites begin with 20 HP, cannot fire or store particles, and are valid targets. On ticks divisible by 20, each connected completed node may commit up to four deployed particles against one adjacent enemy structure/site. Choose lowest HP target, then resolve ties in canonical neighbor direction order starting at that node's checkpointed firing-decision cursor; after an actual attack, advance the cursor to the direction after the chosen target. Never derive this rotation from absolute tick, which can alias the firing cadence; test six tied neighbors across repeated attacks. Do not prefer a fixed player ID. Choose attacker cohorts by descending attack, then profile/type ID. This makes assault useful for pressure while exposing the cost of sending guards forward. Destroying a site cancels its paid job with no refund; construction cannot complete after its site dies that tick. A surviving site completes at `60 - (20 - remainingSiteHp)` HP, preserving prior damage. No ranged towers, terrain piercing or projectiles in empty space yet; these are future rules, not implied behavior.

Freeze all firing decisions before applying any damage. Remove committed attack units; sum `count * attack` per target from all owners. Remaining deployed units defend, ordered by descending absorption then profile/type ID. Each consumed defender absorbs up to its profile's absorption value; consume `min(count, ceil(remainingDamage / absorption))`, clamp residual damage at zero and discard unused absorption. Residual damage reduces HP; apply all HP changes/destructions simultaneously. A node destroyed this tick still performs its already committed attack. These integer rules make composition and arrival timing consequential without claiming a balanced counter matrix.

Every spent attacker/defender enters recovery: ready tick = combat tick + 120 + saved brain distance × profile ticks-per-edge. Destroyed-node survivors use the disconnection rule. Recovery places units only in the living brain reservoir, never a frontline node; subsequent transport still takes time. The conservation invariant for a living player is `reservoir + deployed + relay + transit + refitting + recovering = 128`, independently tracked by type except explicit refits. A brain destroyed in combat eliminates its owner at tick end, cancels its jobs and removes its structures/cohorts into an explicit eliminated accounting total; identities/history remain. Resolve simultaneous brain deaths as a draw if none remain. Competitive headless/lab mode wins with one surviving player; sandbox never auto-wins merely because it started alone.

This yields a falsifiable loop: mine to grow, choose the particle mix, route scarce strength to a front, absorb or break pressure, and cut supply branches. Test attack concentration against guard concentration, redistribution against multi-front pressure, and expansion against cuts. Stronger research must not erase latency, capacity or the finite-pool opportunity cost. Balance experiments rotate spawns and retain commands, rules/map hashes, outcomes and timing rather than asserting strategy superiority from one match.

New neurons begin empty with priority zero; growth does not silently divert another front's particles. The UI makes “allocate assault/guard here” immediately available. Brain reservoir units are eligible for brain defence/attack unless reserved for departure or refit; they remain counted only in the reservoir compartment, never again in deployed stock. Priority quotas may draw them out, visibly exposing the brain. Research refreshes profile only on a later brain departure; never silently changes an already deployed defender, including at the brain.

## Commands, jobs and exact tick order

### Actions are a public engine/network contract

Define an exported discriminated union, with no browser callbacks, wall-clock timestamps or arbitrary object payloads. Proposed Phase 0 action bodies are:

| Action                     | Typed payload and purpose                                                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `enqueueConstruction`      | A bounded ordered list of validated tile IDs; creates queue items with stable IDs derived from the accepted command identity and item index |
| `cancelQueuedConstruction` | A stable queue-item ID, never a shifting list index                                                                                         |
| `cancelConstruction`       | An active job ID/generation; cannot accidentally cancel a replacement job                                                                   |
| `beginResearch`            | A research ID from the versioned supported enum                                                                                             |
| `cancelResearch`           | The active research job ID/generation                                                                                                       |
| `setNodePriority`          | Owned completed entity ID/generation, particle type and integer weight 0–3; bounded to eight positive-priority destinations/player          |
| `setParticleMix`           | Desired assault count 0–128; starts only the bounded brain refit process, never rewrites field inventories                                  |

Keep these bodies separate from a typed command context containing match/round scope, actor ID, current stream generation, sequence and application tick. The adapter derives actor identity from the member stream and logged seat; wire payloads cannot impersonate another actor. Headless test drivers construct the same context and use the same guards/rule application. Administrative start/settings/roster commands remain in existing room management, not a second parallel management protocol.

`NeuralEntry` must satisfy the real `LogEntry` tuple prefix `[seq, tick, ...body]` in `fuse-netcode`; define explicit versioned encode/decode and `isEntry(unknown)` guards, with a lossless mapping between wire bodies and engine actions. Reuse the netcode's ordering, stream repair and generation rules. Per-stream sequence starts again in a new generation: command identity and checkpointed cursors must include `(matchId, round, actorId, generation)`, not just player ID. Fold eligible retired/current streams according to the authoritative management timeline; do not blindly accept stale generations or reject historical entries required by rollback. A command targeting an old round/entity is a deterministic no-op. `ordinal` is unnecessary unless a later action introduces an identity independent of stream sequence.

The Phase 0 offline `RollbackGame` adapter must implement the existing contract completely, including scope, clocks, settings/seating, view, hash and checkpoint codec. Late input replay restores a checkpoint and reapplies the same actions at their recorded ticks; presentation never invents state corrections. Views are authoritative for queue, balances, research and result state. Cosmetic events may be deduplicated by the runtime, so they must not serve as the source of economic statistics.

Validate shape/bounds at the wire boundary and legality/ownership/affordability again at tick application. Rejections are bounded typed results, separate from facts about actual state changes. Initial caps: 32 queued destinations per player and eight action commands per player per tick, processed in accepted actor sequence order across eligible generations; excess commands receive an explicit limit rejection. Duplicates must not spend twice, and insertion/network arrival order must not determine replay outcome.

Phase 0 acceptance includes action encode/decode round trips, unknown opcode/oversized payload rejection, spoofed actor and foreign-job rejection, new-generation sequence reuse, duplicate/stale scope rejection, and identical hashes for an on-time action versus the same late action after rollback through the existing world/runtime machinery. Use typed in-memory streams and fake time; real WebRTC rooms, recovery qualification and multiplayer browser play remain later work.

### Job rules

A queue is an ordered route intention, not terrain ownership. Reserve neither tiles nor money before a job starts. Reject duplicate destinations; check current legality when starting each entry. A legal but unaffordable head waits and blocks later entries. Illegal/obsolete entries are removed with reasons in a bounded scan of at most 32 entries; at most one valid new neuron job may start per player per tick. A future route segment can become legal after its predecessor completes. Occupied, blocked, deposit or unconnected targets cannot start construction.

1. Capture tick-start connected completed nodes, balances and active research effects. Fold all commands in accepted actor sequence order, including cancellations, queue edits and research starts. A research start atomically checks eligibility, deducts its cost and creates its job; insufficient funding rejects rather than silently queues it. Reject already-active/completed research. Canceling queued construction is free; canceling started construction or research loses its paid cost. Thus begin-research then cancel costs Insight and leaves no job, while cancel then begin may start a new paid job. Started-site cancellation makes that tile claimable next tick, preventing same-tick site cancel/restart.
2. After the command fold, each player's construction queue proposes at most one valid start, including newly enqueued work. Resolve competing destinations as a batch across all owners before atomically reserving accepted destinations, deducting costs once and creating sites/jobs. Earlier accepted spending remains deducted; this tick's income is unavailable. An enqueue followed by its queue cancellation in the same tick costs nothing. Construction and research use separate currencies and can progress concurrently.
3. Resolve prior-tick cuts and invalid reservations; release due recovered/refitted cohorts to the brain. Compute quotas and routing from tick-start eligible stock/topology and post-command priorities. Commit bounded departures with reservations; deliver previously scheduled arrivals. Arrivals cannot depart again this tick. New research/structures remain unavailable until next tick.
4. On combat cadence ticks, allocate every attack from the common pre-combat view, consume attackers, resolve defence from remaining deployed stock, and apply all damage/destruction together. Use the explicit cohort/profile ordering above. Record branch cuts for next tick and brain elimination/results at this tick end. No command or player iteration order gives a first strike.
5. Advance eligible construction/research/refit jobs using tick-start connectivity. Latch construction duration at job start; acceptance counts as first progress tick. Debug zero-duration jobs complete here, never recursively starting another. Disconnected construction pauses. Credit income using tick-start ownership/connectivity, including the last productive tick of a branch destroyed now; eliminated players receive no post-elimination job completion or income. Completions activate next tick, so a neuron finishing now cannot mine, route, fight or support further construction this tick.
6. Advance the tick, publish bounded authoritative outcomes/view and assert invariants. Evaluate victory only in competitive headless/lab mode. Clear transient results after consumption; keep no unbounded event history in state.

Connectivity is derived from completed ownership; combat can actually sever it in Phase 0. In step 2, prepare each player's construction claim independently against tick-start eligibility and remaining balance. Competing owners claiming the same empty tile all fail without payment, remove that queue head with an explicit conflict reason, and cannot start a replacement until next tick. Unique claims commit normally. No player-iteration ownership advantage. Test construction, transit arrival and branch destruction together; online delivery remains later work.

`?debug` is parsed only by the app, into validated snapshotted `instantConstruction`/`instantResearch` settings for offline sandbox. Costs, placement, queue limits and prerequisites remain unchanged. Show a persistent Debug badge; do not accept a network URL as a rules override. Initial resources remain 60/0 in both modes, so instant research still requires earning 10 Insight. Debug is a timing aid, not an unlimited-money mode.
