# Online protocol contract v2 (proposed review amendment)

> **Status (2026-09-15): superseded for gameplay.** Online rooms now run the peer-to-peer input log recorded in [ADR 047](../adr/047-p2p-input-log-lockstep-rollback.md) (history and measurements in [P2P-INPUT-LOG-BRIEF.md](P2P-INPUT-LOG-BRIEF.md)): every device simulates locally from one shared log over a full WebRTC mesh, with one MessagePack packet per tick per link, rollback, and snapshots from any peer. The host-star sections below (the lease as gameplay authority, the input schedule and ledger, gesture receipts, world replication with keyframes and deltas) are historical. The service parts still apply: room codes and membership, the lease that fences duplicate creator tabs, the signalling payload boundary, STUN-only ICE, link restarts, link diagnostics and the NAT limits.

This appendix makes ADRs 028–032 concrete. It is a design contract, not a claim that v1 prototype packets implement it. One owner integrates the protocol. No authority, receiver or gesture counters are inferred from arrival order. All integer fields below are safe nonnegative integers; runtime validation is mandatory.

## Peer stream ingest contract (#258 N7)

This section is current: it describes the peer-to-peer input log, not the host-star design below. Every rule here is an ingest-side refusal of input an unmodified client never sends, so it changes nothing an honest replica simulates, needs no `RULES` bump, and leaves clients on an older build of the same rules unaffected.

**`through` is a promise about later seqs.** A packet declaring `through = T` together with `lastSeq = S` promises that every entry its sender issues with seq > S is stamped with a tick > T. It says nothing about entries up to S, which may sit at or before T and may still be in flight: they are retransmitted by rotation and nack and are accepted whenever they arrive, and a repeat of an entry a replica already holds is always a harmless no-op. The sender keeps the promise by construction: it stamps an own entry `max(floor(clock) + 1, lastOwnTick)`, its clock never steps back, a snapshot install raises `lastOwnTick` past the installed tick, and it declares `max(own through, floor(clock))`, so an entry may ride in the very packet whose `through` has already reached its tick, because that packet's `lastSeq` names it.

A replica enforces the promise per stream generation. It remembers the highest `T` declared with any `S` its contiguous prefix has reached, plus the pairs whose `S` is still past a gap, and refuses a packet carrying a new entry `seq` stamped at or before any `T` declared with `S < seq`. That was the two-second lookahead cheat: declare completeness 40 ticks ahead so nobody stalls or predicts, watch the others, then commit input inside ticks every replica already held final, which also falsified `completeTick()` (hash exchange, snapshot serving, the analytics `confirmedTick()`). The check reads only sender-side facts, so no loss, duplication or reordering of an honest stream can trip it: a packet declaring a higher `through` may overtake the packet carrying entries below it, and those entries still fold because the overtaking packet's `lastSeq` covers them. A generation change or a snapshot install starts a fresh stream whose floor is its base tick; the existing rule that an entry at or before the base is `unrepairable` takes precedence there. What cannot be detected without a protocol change: a sender may pre-announce a seq (`lastSeq = S + 1`) and deliver that entry up to the rollback window late, which is indistinguishable from loss. That variant is not silent, though: the announced seq is a gap, so the stream's confirmed tick stops, hashes pause and nacks flow for as long as the entry is withheld.

**`lastSeq` is bounded.** A packet whose `lastSeq` exceeds the stream's contiguous prefix by more than `SEQ_AHEAD` (4,096) is refused whole and declares nothing, so an inflated value opens no gap. An honest stream can get there: a replica cut off from a busy rider for minutes on the same page and generation. No nack can repair that distance, so the refusal flags the stream `ahead` and the replica takes the existing stalled-gap path without the nack: one snapshot request per `STALLED_GAP_MS`, never one per packet, until a packet is taken again (the rebuilt stream starts at the serving peer's base seq, which is within reach). This does not stop a deliberate griefer, who can withhold a single announced seq forever and hold a real gap open (hash comparison paused, a resync each `STALLED_GAP_MS`); closing that needs a rule for abandoning an unrepairable gap, which belongs with partial-mesh recovery (#258 N3), not here.

**Which refusals cost a member its liveness.** Every refusal rejects the whole packet; link measurements (RTT echo, clock reading) are still taken from any well-formed packet. A refusal is one of two kinds. A `violation` is something no unmodified client sends: a malformed entry, an entry past the packet's own `lastSeq`, a changed entry under a known seq, ticks or gestures out of order, a broken `through` promise, a packet for a generation with no stream. It does not refresh the sender's last-heard time, so a member that sends nothing else is marked absent by the creator after `DISCONNECT_MS` like a silent one, and the room plays on instead of stalling on completeness it will never accept. A `window` refusal is the receiver's own limit and says nothing about the sender: `lastSeq` out of reach (`SEQ_AHEAD`), more than `BUFFERED_ENTRIES` waiting behind an unrepaired gap, or an entry stamped more than `FUTURE_TICKS` past the receiver's clock (a receiver whose clock froze through a suspend). The sender stays heard while the usual recovery runs, as it did before this section existed, but only for `WINDOW_GRACE_MS` (10 s) counted from the first such refusal since a packet was last taken; after that it is treated as silent too, and the `ahead` resync backs off to one request per `WINDOW_GRACE_MS`. It never stops, and a request that could not go out (no link fit to carry it) does not use up the wait, so a replica whose links were unusable for the whole grace still resyncs on the first tick one can carry the request. Without that limit an inflated `lastSeq` would stall the room on its sender for good and resync every replica forever, which is worse than the gap it replaced.

**`RULES` mismatch refuses the peer.** A `hello` announcing different `RULES` marks that member refused until a matching `hello` arrives: its fast packets are dropped before anything is read from them (no liveness, no stream, no clock sample), its `join` is answered with an `error` and not seated, its snapshot requests are not served, it is never asked for a snapshot or a seat, and **nothing is sent to it on the fast channel**. That last rule protects tabs that predate the refusal: a creator that reloads onto later rules opens its own world under the same room hash, and an old tab would otherwise take that creator's clock (tick 0) and entries for its own room's. Seeing a silent creator, the old room succeeds it after `CREATOR_SILENCE_MS` and plays on. A creator with no world treats refused members as nobody when deciding whether to open a fresh room. When both sides run this code the result is a benign partition: two worlds under one room code, split by version, neither folding the other. The status names the side that is behind, by the number in `fuse-p2p-N`: the stale page reads `This page is out of date — reload this page`; a current page with a world reads `A rider is on an older game version — they must reload` (a notice, nothing for this page to do); a current page that can get no world because the room is older reads `This room is on an older game version — start a new room, or have its riders reload`, and that line or the stale one stays up as the recurring status rather than expiring with the notice. With several refused members the line is one verdict for all of them, independent of arrival order: any build ahead of this page makes this page the stale one. Only the stale page's line says `reload this page`, which the header turns into a reload button; `start a new room` was added to the header's and the boot card's actionable phrases so the older-room line is shown verbatim (the boot card would otherwise replace it with its network hint) without a reload button that does nothing. `hello` is a claim, not proof: this keeps an honest stale build out of the fold; a modified client can announce whatever it likes, as it can send whatever entries it likes.

**Presence forgery (open, owner decision).** `permitted()` accepts `presence(x, false)` from any connected rider about anyone ahead of it in the succession order, and re-evaluates the order after every entry. One packet from the last rider in the order can therefore mark the creator and every rider ahead absent, which makes the sender the delegate while the creator is absent, and carry any management entry behind them in the same tick. With a `lobby` action the reset also drops every rider just marked absent, so the honest riders lose their seats (`games/fuse-riders/tests/net-hardening.test.ts` pins this). The creator re-asserts presence within 500 ms, which bounds nothing: the damage is done in one tick and the forgery can be repeated. Absence is each replica's local observation and the log carries no evidence of it, so there is no ingest-side or reducer-side rule that refuses the forgery while still accepting an honest successor's identical entry during a real partition; any fix (a grace period before delegation takes effect, limiting what a delegate may log, or pausing until the creator returns) is part of the succession decision in #258 N5 and a `RULES` change.

## Authority and connection scope

Service state: `{ incarnation: random128, epoch, holderConnection, grantId, validFromMs, expiresAtMs }`. Room initialization creates a new incarnation. Each authenticated socket receives a fresh random connection ID; peer identity is stable separately. Service operations serialize grant allocation/renewal. A renewal names exact incarnation/epoch/grantId/holderConnection and only succeeds if still current and not expired. An obsolete renewal cannot extend a grant.

Lease duration 10 seconds; the creator asks to renew with every `time` heartbeat, every 2 seconds (`PeerTransport.connect`), and the service writes the renewal once half the lease is used ([heartbeat write cost](../design/heartbeat-write-cost.md)). Replacement reserves epoch+1 but validFrom is no earlier than previous expiresAt plus 250 ms uncertainty guard. It cannot advance or publish accepted state before validFrom. A replacement never renews the old grant. Delayed socket close only affects that socket connection ID. Peers learn grant/connection identities directly from authenticated WSS, not host assertions. A reserved replacement is not an active grant.

Clock mapping uses service ping samples with local monotonic send/receive timestamps and service time. Offset interval is bounded by the entire measured RTT; retain valid bounds without assuming symmetric delay. A peer accepts a grant only when the entire estimated service-now interval lies inside [validFrom, expiresAt). If uncertainty exceeds 250 ms, pause until a fresh sample; this is explicit degradation. Use elapsed monotonic time, recheck after suspension and before every simulation step/frame acceptance. A peer missing renewal stops at its older expiry (safe early pause). Signalling partition therefore cannot overlap old and replacement authorized intervals. Browser host is trusted; this prevents accidental split authority, not malicious modified clients.

`Scope = { incarnation, authorityEpoch, receiverConnection, controlEpoch, matchId, round }`. Host and guest reconnect reset controls and allocate a new service connection scope. Within an unchanged scope counters never reset. Scope changes require neutral handshake and baseline; checkpoint rewind is permitted only as an explicit new-authority discontinuity.

## Input schedule and ledger

Snapshot tick T is state AFTER step T. On host step T+1, consume eligible samples received before the step begins. A sample is `{ scope, seq, intendedTick, left, right, aim? }`. intendedTick is floor(estimated host tick)+1. Reject intendedTick < currentTick-4 or > currentTick+4; reject prior scope. Future samples wait for their intended tick, but a queued sample with a lower sequence than an eligible one is eligible in the same step: sequence order dominates intended tick, so a fire edge stamped from a stale clock estimate is never skipped by a later hold sample whose fresher estimate named an earlier tick (#43). Among eligible samples the greatest sequence wins; acknowledge superseded movement samples explicitly. Movement outcomes do not acknowledge fire transitions: eligible bomb edges are independently processed in sequence order within the step. No rewind. Hold last applied controls until nextTick - lastAppliedTick >= 10 without fresh eligible input, then neutralize. A fresh connection starts neutral. Bomb transitions are not movement samples.

Snapshot includes held controls, lastAppliedSeq and lastAppliedTick, plus application results `{seq, result: applied|superseded|expired, appliedTick?}` for pending samples. Retain results for 100 ticks; client acknowledges exact result sequence IDs (at most 128 per acknowledgement; no cumulative highwater) and host resends until ack or scope expiry. Bounded 128 outstanding samples; overflow forces neutral resync, not silent history loss. Host scheduling results are authoritative. Predictor restores snapshot T, retains authoritative held controls and replays its tick-indexed record after T, correcting assignments when results arrive. This includes fully acknowledged held turns. Prediction lead cap is four ticks; uncertainty or stale snapshot freezes advancement, never grows an unbounded backlog. Partial-tick preview is cosmetic. The client never pre-rejects a sample because its clock is uncertain or its snapshot lags (#15): it always sends `floor(estimate)+1` and only the host window decides, so a slow link yields explicit `expired` results rather than certain local loss. A sample the transport refuses is discarded from the client record (#20); records behind the host window are pruned on every accepted snapshot; client overflow at 128 drops the stale backlog and keeps sending. The solo runtime's authority is in-process: `LocalRuntime` stamps every input with the authority's next tick before admission, because a stalled main thread lets the wall-clock extrapolated estimate run ahead of the clamped 100 ms catch-up and the sample would otherwise be refused as future (#43).

Kernel state includes x/y/angle, previous drunk offset, drunk start/end/seed inputs, movement speed/turn rate, tick and known boundary/portal context. Unknown portal/obstacle changes remain explicit authoritative corrections. Test two opposing samples at one tick, future/late samples, missing results, drift, host pause and 300 ms snapshots using real scheduler results.

## Fire and management actions

**Current accepted direct-only scope:** [ADR030 amendment](../adr/030-online-delivery-and-replication.md#reviewed-direct-only-action-amendment-2026-09-14) uses the one ordered reliable RTC channel, scheduled/scoped sequence validation, no replay of old fire edges, ten-tick cancellation watchdog and a persistent notice on known press/release failure. Movement outcomes are not gesture outcomes. The full terminal gesture protocol below is a deferred alternative for guaranteed per-gesture receipts or multiple gameplay carriers, not an implemented direct-only release promise.

### Deferred terminal gesture alternative

A gesture is `{ scope, gestureId, transitionSeq, kind: press|aim|release|cancel, startTick?, releaseTick?, aim? }`. IDs increase within control scope. Each gesture state is absent, charging, applied, cancelled or rejected. Last three are terminal; repeated messages return the identical terminal acknowledgement. Cancel before release terminates; cancel after applied cannot undo a shot. A release received before press produces a minimum-charge shot if legal (no invented charge history). Later press cannot resurrect a terminal gesture. Aim updates never resurrect or fire.

For known press, charge begins at its host application tick. Claimed release/start ticks must lie in the input age/future window, start<=release, and same scope. Charge is bounded by host-observed elapsed ticks and existing game charge cap; client metadata cannot grant extra charge. Invalid metadata is terminal rejected. Cooldown, powerup and alive checks use current authoritative game state. New round/control epoch cancels outstanding gestures.

Retry nonterminal transitions every 150 ms for at most 750 ms; preserve IDs across carriers. No global gap wait: independent gestures/management actions cannot block each other. Retain up to 128 terminal gestures for 5 seconds; rate limit to 20 new gestures/sec. Older wire actions are rejected by tick/scope checks even after eviction. If capacity is exhausted, reject new gestures explicitly until history expires. Management has independent action ID/ack, 3-second retry deadline, 10-second terminal retention and 5/sec limit; validate scope/privileges. Transport retry success is not action success.

## World replication

World identity is `{incarnation,authorityEpoch,receiverConnection}`. Host maintains increasing generation per identity, sequence per generation. Keyframe includes full state, tick, schema version, rules revision, generation and optional resync request ID. Counter reset requires fresh identity. Within identity accepted tick cannot decrease, including keyframes. Validate entire candidate before swapping state/trails/generation. Invalid higher generation cannot retire healthy state. Decoder returns accepted/stale/needsBaseline/invalid.

The former host-star snapshot and replay gates are historical. For the current peer-to-peer snapshot format and compatibility contract, see [ADR 047](../adr/047-p2p-input-log-lockstep-rollback.md). The live compatibility identifier is `RULES` in [`games/fuse-riders/src/engine/apply-tick.ts`](../../games/fuse-riders/src/engine/apply-tick.ts); peers must match it exactly. Both snapshot chunk assembly and decoded snapshot payloads independently reject foreign rules in [`packages/fuse-netcode/src/snapshot.ts`](../../packages/fuse-netcode/src/snapshot.ts). Refresh every peer together when rules change, and start fresh rooms after a rollback.

One resync request in flight per receiver; retry after 500 ms, max 2/sec. Latest request ID binds response; obsolete responses are stale. Encoder generation increments when a stream is replaced or an encoded send cannot be retained. Coalescing applies only before encoding; never drop a delta then encode a dependent successor. On queue overflow terminate generation, discard its pending output and create fresh baseline. Delayed packets from terminated generations cannot supersede the new committed baseline. Periodic keyframe remains in generation and preserves tick order. The shipped direct-only path (ADR030 amendment: one ordered reliable channel) sends no periodic keyframe: only a fresh encoder baselines, since a chained delta stream cannot drift there and a broken chain already resyncs (#61).

## Recovery and evidence

Warm WSS remains available for fallback. Probe direct every 200 ms; three missing application probe acknowledgements triggers fallback, target <=750 ms from first lost probe to fresh input/current baseline acceptance. Probe responses are path-specific (WSS cannot prove RTC healthy). Direct recovery requires two consecutive bidirectional probes plus baseline/application ack, with minimum two-second dwell to prevent flapping. ICE restart uses bounded 1/2/4/8-second backoff. Same-authority recovery after a three-second outage targets <=2 seconds from restored connectivity. Host replacement has a separate bound: remaining lease +250 ms guard +2 seconds handshake; never bypass fencing to meet the path-only budget.

Benchmark cohort is five active riders plus TV for 30 minutes, excluding lobby/countdown from traffic averages and explicitly marking discontinuities. Normal correction profile: 80 ms RTT, 20 ms jitter, 0% loss, alternating steering and held turns, p95 <=7 units; report unknown-obstacle corrections separately, never discard them from the overall report. TV nearby profile: 40 ms RTT, 10 ms jitter, 0% loss. Other ADR 032 impairment/degradation profiles remain required. Version, seed, raw samples, environment and all exclusions are recorded. Preview and public-ready are distinct labels; morning timing does not waive release gates.

## Final review amendments (required for implementation)

Every fire and management transition carries required issuedTick, checked independently against current scope and age before terminal-history lookup or execution. Gesture creationTick is immutable across transitions/retries. Reject future actions rather than executing early; retry can occur when eligible. One charging gesture owns each player at a time; a competing press is explicitly rejected. Expired actions cannot recreate charging state after dedup eviction. Movement result acknowledgement is the highest contiguous resolved sequence, never maximum seen across holes.

Clock uncertainty widens by 1000 ppm elapsed time after each sample (conservative engineering bound), with a maximum sample age of 4 seconds. Sample RTT above 500 ms cannot authorize simulation. Visibility resume, bfcache or detected scheduler gap over 500 ms invalidates clock mapping and requires a fresh service sample. Expiry checks alone do not certify a suspended clock. Bounds and suspension are tested with independent injected service and local clocks. These amendments satisfy the independent design review's remaining conditions; implementation and release reviews remain required. A non-permitted clock pauses advancing, sending and receiving at once; seat control scopes are rotated only after 2.5 s of continuous non-permission (one 2 s sample period plus the 500 ms maximum round trip) or on an actual authority change, so one stalled or uncertain sample does not reset controls (#48).

## Room service credentials (issue #256 S3)

A room token is a bearer capability (a member token names a seat; the creator's also ends the room) and never appears in a URL, because request URLs are recorded by Cloud Run and by proxies. HTTP routes take it as `Authorization: Bearer <token>`: `GET /api/rooms/{code}/ice`, `POST /api/rooms/{code}/end` and the game's `POST /api/rooms/{code}/results`. A token in a query string authenticates nothing. The room WebSocket `GET /api/rooms/{code}/ws` is upgraded on an allowed Origin and a well-formed code alone, and the socket then authenticates with its **first frame**, `{"type":"auth","token":"<64 hex>"}`, a text frame of at most 256 bytes due within 2 seconds. Until then nothing else is read: any other first frame, or a late, binary, oversized or malformed one, closes the socket with `4401` and spends the address's hourly admission failure budget, and a valid `auth` frame arriving second does not rescue it. Leaving before authenticating frees the slot and is not charged; a refused socket that does not answer the close frame is terminated after 3 seconds. The whole handshake holds one admission slot, so unauthenticated sockets share the pending-admission bounds (4 per address — an IPv4 address or an IPv6 /64 — and 128 per gateway; `429` before the upgrade beyond that). Those counts, not the failure budget, are what bounds slot holding: a slot held to the deadline and then validly authenticated costs nothing. After `auth` the gateway admits as before and answers `welcome`; `welcome.protocol` is still `2` and every later frame is unchanged. A room with no free seat closes with `4029` (`CLOSE_ROOM_FULL`), which is not charged and is terminal for the page: it stops retrying and shows the service's wording with RETRY. The client retries `4401` and every other non-terminal close with jittered exponential backoff (1.5 s doubling to 30 s; to 5 minutes while `4401` repeats, so one refused page cannot spend its address's budget alone), reset by a `welcome`. Invite links carry the room code only. Rationale, the rejected `Sec-WebSocket-Protocol` alternative, the deprecated `?token=` acceptance window that only the Cloud Run entry enables, and the deploy order are in [TOKEN-TRANSPORT.md](TOKEN-TRANSPORT.md).

## Games on one room service (`gameId`)

One room service and one history backend serve every game, and a room serves one game. A `gameId` is 1–32 characters of `[a-z0-9-]`, starting with a letter or digit (`validGameId` in `fuse-network-protocol`). `POST /api/rooms?gameId=<id>` creates a room for that game; the query rather than a body keeps creation a simple request with no CORS preflight. The room record stores the id. The room socket's first frame may name the game, `{"type":"auth","token":"<64 hex>","gameId":"<id>"}` (still under the 256-byte cap); a socket naming another game than its room's is refused like a missing room, closing with `4004` (`CLOSE_ROOM_ENDED`) and the reason `Room is for another game`, and the admission is charged like a wrong code. A malformed `gameId` makes the frame malformed (`4401`). The service is configured with the games it hosts (`gameIds`); creating a room for any other, or a malformed id, is `400 Unknown game`. History routes take the game as a path prefix: `/api/games/<id>/rooms/<CODE>/results`, `…/round-results`, `/api/games/<id>/me/round-results`, `/api/games/<id>/leaderboard`, `/api/games/<id>/me` and `/api/games/<id>/me/matches`; an unregistered game is `404 Unknown game`, and a report for a room of another game is `404 Room is for another game`. `/api/me` (`PUT` sets the username) is the shared account under either form.

**Compatibility, both directions.** An absent `gameId` means `fuse-riders` (`LEGACY_GAME_ID`) everywhere: at room creation, in the auth frame, on a stored room and on a stored match record, and the unprefixed history routes are Fuse Riders'. A client from before games therefore creates and joins Fuse Riders rooms on a new service unchanged. A new Fuse Riders client sends `gameId: "fuse-riders"` in the creation query and the auth frame, which a service from before games ignores (it reads only `type` and `token`, and never the query), so the client works against either service and deploy order does not matter. Room and history wire shapes are otherwise unchanged; `welcome.protocol` stays `2`, and the fold rules do not move.

## Direct link establishment, diagnostics and NAT limits (issues #12, #27)

ICE configuration: `/api/rooms/{code}/ice` (members only, token as `Authorization: Bearer`; fetched with a 3-second bound; a hung fetch falls back to the defaults) returns STUN only (`stun:stun.cloudflare.com:3478` and `stun:stun.l.google.com:19302`, `relayConfigured:false`). The client validates the list at its boundary and uses the same two STUN servers when the fetch fails or returns nothing; every `RTCPeerConnection` waits for that fetch, so no offer or answer is negotiated without STUN. Signalling carries `{description:{type,sdp}}` or `{candidate:{candidate,sdpMid,sdpMLineIndex,usernameFragment}}` only; one `RoomGateway` applies the `validSignal` boundary in both Cloud Run and the local room service (empty-string end-of-candidates, null fields and mDNS `.local` host candidates pass). Trickle candidates that arrive before their description, while one is being applied, or whose ufrag names a later ICE generation wait in a bounded 64-entry buffer per link and are applied after the matching description; candidates from an earlier generation are parked and never poison the new attempt.

Signalling rate: the gateway allows each connection 80 signal frames per target member, refilled at 10 a second, inside 400 frames and 256 kB of any kind a second, and each room 512 kB of cross-gateway publishes refilled at 51.2 kB a second; a full-room rejoin at 64 candidates a link is 335 ([arithmetic](../design/signalling-abuse-isolation.md#signalling-rate-limit)). A frame over a limit is dropped and the socket stays open: a close would make the page reconnect and negotiate every link again. The sender receives `{type:"notice",notice:"signal-throttled",dropped}` at most once a second, `dropped` counting frames since the previous notice; clients that do not know the frame ignore it. A dropped candidate needs no recovery; a dropped offer or answer is recovered by the restart path below after eight unhealthy seconds. Only a sustained flood of refused frames closes the socket (`1008 "Signalling flood"`), and for the next 60 s that member's connections to the same gateway start without the negotiation burst.

Recovery: the link's initiator (the member with the smaller id; every pair of members has a link in the mesh) issues bounded ICE restarts on the existing connection (`createOffer({iceRestart:true})`, at most four per link, one per eight unhealthy seconds, budget restored by fresh probe health). The answerer recognises a restart by the unchanged DTLS fingerprint and answers on its existing connection; a changed fingerprint means a new connection and replaces the link. A link whose send gate has drained (terminal pc/ICE failure, channel closed, peer retired by the service) cannot be restarted in place because the gate is monotonic; that attempt replaces the RTCPeerConnection and gate instead, carrying the same restart budget. Restart attempts are only issued while the room socket is open. After the budget is exhausted the link stays failed and says so.

Diagnostics: **ROOM → LINK DIAGNOSTICS** shows, per link, local and remote candidate types gathered, the selected candidate pair types, ICE gathering/connection state, peer connection, signalling and data-channel state, DTLS and SCTP state, signalling counts (offers, answers, candidates up/down, applied/buffered/rejected/dropped), restart budget, link age and the last failure name. Chrome stops gathering once a candidate pair connects, so a link that connected quickly on the same network legitimately shows host candidates only; the STUN verdict is only given for links that never connected. No addresses, tokens or invite links appear; the same text is exported as `#app[data-link-diagnostics]` for smoke scripts. The header shows the first missing step instead of a generic retry, for example `no reflexive candidate from STUN`, `signalling never delivered the answer`, or `candidates exchanged, ICE failed — likely symmetric NAT/CGNAT on one side`.

Limitation: ADR035 provisions no TURN relay. When both peers gather server-reflexive candidates and exchange them but ICE still fails, at least one side is behind a symmetric NAT or carrier-grade NAT (common on cellular). Direct WebRTC cannot traverse that combination; the status and this document say so rather than retrying forever. Joining the host's Wi-Fi, or using a network with endpoint-independent NAT, is the only remedy without a relay.

### Power progression (#201)

Fold rules `fuse-p2p-9` introduced the following behavior, retained in rule 11 except for the restored Fuse pickup below. Eliminated riders retain their remaining trails until the next round: elimination sets each surviving segment’s `expiresAtTick` to `Number.MAX_SAFE_INTEGER`, including the final contact segment. This finite deadline survives snapshots and checkpoint validation and keeps bots, collision checks and both renderers using the same obstacle lifetime. Blasts, bullets and closing walls can still cut these trails. Every Power pickup contributes to the diminishing-return weapon curve, replacing the five-pickup level thresholds of rule 7. The curve reaches half its available improvement at 30 pickups; collection does not rewrite existing bombs or running reloads. Power replaces Blast/Fuse pickups: every rider carries required `powerPickups` (round total) and `reloadDurationTicks` (captured at the most recent launch), replacing `blastLevel`/`fuseLevel`. Public snapshots carry both fields; match statistics use `powerPickups` instead of `blastPickups`. Checkpoint validation bounds pickup totals, reload durations and board pickup count using the shared tuning constants. Single-drop scheduling scales with living riders (including bots), and collection remains in seeded fixed-tick simulation, so rollback restores both the pickup total and the active reload exactly. Rule 5/6/7/8 peers cannot join this ruleset; refresh all peers together and use fresh rooms after rollback. There is no conversion of running games. Changes to simulation tuning require another rules bump before mixing builds in online rooms.

### Extra Bomb progression (#208)

Fold rules `fuse-p2p-10` introduced Extra Bomb. Riders and presentation snapshots require `extraBombs`, an integer from 0 through 8. Checkpoint decoding rejects missing, fractional, negative or excessive counts before installation. The pickup type is `extraBomb`; the counter resets with round state and is included in state hashes and peer snapshots. Ordinary volleys use `1 + extraBombs` bombs, plus the existing temporary Triple/Five bonus; special Target/Shell/Cannon launches preserve it. The peer handshake and snapshot rule equality reject older clients. Refresh all peers together when releasing this change; rollback requires fresh rooms. No room-service or transport format change is needed.

### Restored shorter fuse

Fold rules `fuse-p2p-11` restored Shorter Fuse. The `stopwatch` pickup is enabled by default again and raises the required rider/snapshot `fuseLevel` from 0 to a cap of 2, resetting each round. Checkpoints reject missing, fractional, negative or excessive levels before installation. Ordinary bomb launches capture a 40/30/20-tick fuse; collection cannot change bombs already in flight. Volleys and Singularity use that fuse, while Target/Shell/Cannon behavior and Power reloads are unchanged. This changes deterministic rules and checkpoint state: rule equality rejects older peers and snapshots. Refresh all peers together; rollback requires fresh rooms. Room-service and transport envelopes are unchanged.

## Nitro and Snail speed pickups

Fold rules `fuse-p2p-23` introduced Nitro and Snail (#240). Riders, presentation snapshots and checkpoints require two integer lists, `nitroUntilTicks` and `snailUntilTicks`: one absolute deadline per collection, kept ascending, holding at most `MAX_SPEED_EFFECT_STACK` (32) entries each, with spent deadlines dropped at the start of every playing tick so replicas never carry stale ones. ## Round shot log

Fold rules `fuse-p2p-15` introduced the following, retained in rules 17 and 18. Game state requires `shots`, the current round's trigger pulls: each entry
is `{ shot, shooterId, weapon, elapsed, bombs, power, extraBombs, fuseLevel, grip, kills: [{ victimId, elapsed }] }`,
where `shot` is the id of the first bomb the pull launched, `weapon` is one of `bomb`, `triple`, `five`, `target`,
`gun`, `shell`, `elapsed` counts ticks into the round, and `bombs` through `grip` record what the pull
launched and the shooter's upgrades at that moment. A bomb carries an optional `shot` naming its pull. Game state
also carries an optional `decidedRound` — `{ matchId, round, tick, shots, rating? }` — written when a round is decided and
kept until the next round is decided, through a rematch and a return to the lobby. Its `shots` leave out pulls
that killed nobody and still had a bomb in the air at the decision, which the round's end interrupted. Nothing in
the simulation reads any of this; it exists so product analytics can report one `Kill` per kill and one `Miss`
per pull that killed nobody (see [product analytics](../ANALYTICS.md)).

`shots` is cleared at the start of every round, because bomb ids restart there, and capped at 512 pulls. Public
snapshots carry only `decidedRound`, never the round in play; the reporting device waits until its runtime's
`confirmedTick()` — every connected rider's input confirmed — reaches `decidedRound.tick`, because the snapshot it
renders is its own prediction. A bomb's `shot` reaches no
snapshot; it travels only in checkpoints, and the shot of a blast lives on the copy `resolveExplosions` hands its
caller for one tick's kill attribution.

Checkpoint decoding rejects, in either log, an unknown weapon, a zero or duplicated pull id, a rider killed by its
own pull or twice in a round, a kill logged before its pull, more than four kills on one pull, a pull of zero bombs
or more than a volley can hold, upgrades outside their caps, and more than 512 pulls. The round in play must also
name issued pull ids and riders with match statistics, and be empty in the lobby; a bomb may not name a pull issued
after it. `decidedRound` may name riders and bomb ids that no longer exist, since it outlives the round and the
match, but may not be decided after the current tick, or name a round of this match not yet played. A bomb with
no `shot` is accepted so a missing one never becomes a wrong one — its kill is simply not logged. Both logs enter
the canonical state hash, so rule equality rejects older peers and snapshots: refresh all peers together, and use
fresh rooms after rollback. Room-service and transport envelopes are unchanged.

### Detached trail decay (#213)

Fold rules `fuse-p2p-17` combined the shot log, eight-second Power trails and slower detached-trail decay. Ordered trail segments carry optional
`detached: { id, decayStartTick }`; absence means the living, age-limited active tail.
The required game-state `nextTrailPieceId` issues positive, round-scoped piece ids across
all riders. Segments in each detached piece are consecutive, touching, ordered history,
with one clock and owner. Crossings never reconnect pieces. Portal transit preserves
active logical continuity, but separate drawable runs become separate pieces on death

Each rider is bounded to 2,048 total segments/pieces; saturation drops oldest detached
segments before touching active capacity. Runtime validation rejects unknown metadata,

history and over-limit arrays before atomic snapshot installation. The existing byte and

## Instant Gun

Fold rules `fuse-p2p-20` introduced Instant Gun. Heads, living/dead trails and walls stop shots; the shooter’s own body is ignored. Body impacts cut a radius-14 disk. ## Projectiles through portal gates

Fold rules `fuse-p2p-22` carried projectiles through portals. A Green Shell and a Gun ray now carry through a portal gate the way a rider does, entering at the first gate met and leaving beside its partner at the same proportional height, keeping heading, speed and a shell's bounce count. Lobbed, Target and Singularity bombs do not: they resolve against a landing point rather than travelling, and are unchanged.

A shell's tick is integrated in two passes split at the gate, so a bounce falling on either side of it still resolves against the wall or trail it actually met, and the teleport itself is not swept for rider contact — a rider standing between two gates is not in the shell's way. A shell carries its own `portalCooldownUntilTick`, a new optional `BombState` and checkpoint field of the same shape as the rider's, so a pair it is aimed down cannot hold it in a loop. ### Deterministic iteration (`fuse-p2p-32`)

Player traversal uses slot then codepoint-ordered ID, bombs use numeric ID, and weighted pickup selection uses the fixed `PICKUP_TYPES` order rather than the object's insertion order. Pickups and arena obstacles are arrays the engine generates in id order; every read whose result depends on order (pickup collection and bot targeting, a rider's first scenery contact and with it the obstacle a shield turns away from, the scenery a gun ray stops at, the walls a shell reflects from) sorts by id first, because each contact bisection starts from the contact found before it and so decides its low bits. Locale comparisons and native exponentiation are excluded from engine source. Replicas restored from equivalent checkpoints therefore make the same first-wins choices even when their maps or weight objects were constructed in different orders.

Rules advance from 31 to 32; everything rules 25 to 31 introduced (history agreement metadata, arena maps, the Beer stagger, frozen rating standings, the final-round result pause and the aiming slowdown) is preserved. #270 added optional per-rider `combat` statistics to the folded and checkpointed match statistics under an unchanged `fuse-p2p-27`, so a rules-27 peer from before #270 and one from after it hash the same log differently; rules 28 was the first version to separate them from both, and the golden replay now fails any such change that arrives without a version of its own. No additional checkpoint fields or transport envelopes change. Existing rules-equality checks reject older peers and checkpoints; refresh all peers together and use fresh rooms after rollback. This change is not a production deployment.

Watchers still rank last, by id. Nothing on the wire changes; the fold does, so peers on rules 45 and 46 do not share a world.
Fold rules `fuse-p2p-42` add the `drift` and `trains` arena maps and scenery that moves. `ARENA_MAPS` gains `drift` and `trains` (both opt-in; `rotate` is unchanged) and `OBSTACLE_KINDS` gains `wall` and `train`. An obstacle may carry `motion`: `{ kind: "bounce", vx, vy }` (units per tick, reflected by the board's edges with the whole rectangle kept on the board) or `{ kind: "rail", track, along, speed, train }` (a car `along` units round loop `track` of the map, advanced `speed` a tick, belonging to train `train`). A new `moveScenery` phase runs after `fitField` and before `spawnPickups`, advancing every mover before any rider moves; the tracks are map data (`TRAIN_TRACKS`), not state. `drift` starts with `boundaryInset` 0 and open edges exactly as `wrap` does (`mapWraps`), with two `wall` obstacles spanning the board that start on its edges and drift at 2.4 and 1.8 units a tick; `trains` starts walled with twelve `train` cars on two loops, laid head first. `wall` and `train` obstacles are permanent: a blast does not remove them and the overtime walls do not crush them. Riders and gun rays now meet scenery across an open edge as they meet trails, and a rider is let out of scenery it already stood in only where that scenery stood before its step, so a train rolling onto a rider kills it. Checkpoint decoding admits `motion` of either shape only and only on `wall` and `train`; a `wall` only on `drift`, up to half the board in each half extent (other kinds stay bounded to a quarter) and with a `bounce` step no longer than the room it bounces in; a `train` only on `trains`, and a `rail` car only on a loop the map has and only within its length; speeds within ±`MAX_MOVER_SPEED`. Rule equality rejects older peers and snapshots. Refresh all peers together, and use fresh rooms after rollback. Room-service and transport envelopes are unchanged.

A `join` message from a member the room already lists is now a request to change sides rather than a no-op: the manager answers it with an ordered pair of these same entries at one tick — `SPECTATOR leave` then `JOIN` towards a seat, `LEAVE` then `SPECTATOR join` towards the watching list — which `applyManagement` applies in the order the manager wrote them. Nothing on the wire and nothing in the fold changed for it, so it carries no rules move: a switch is spelled entirely in entries that already existed. It waits for a pause, as a kick does, and the member that writes the pair may not be its subject, so a manager that is not the creator addresses its own switch to the creator's page instead (`RoomRuntime.switchWriter`, [design note](../design/spectators.md#changing-sides)).

Spectators are folded, hashed and carried in the snapshot payload, which grows from nine fields to ten; the tenth is `[[memberId, name, connected, generation], …]`, refused on decode for a sixth entry, a duplicate id, an id that is also a rider, an untrimmed or invalid name, a non-boolean presence or a negative generation. They never reach `step`, the leaderboard, the match report or `toView`: the screen receives them beside the world view, on the runtime's `Frame`. Nothing waits on a spectator's stream, so a silent watcher never stalls a round.

`successionOrder` gains the connected spectators, sorted by id, after the connected riders, and `actingCreator` reads presence from the seats and the watching list together, so a creator commentating from the list keeps the crown rather than making two members managers at once. The room service admits eleven sockets instead of six (`ROOM_LIMITS.maxGuests` 5 → 10): five riders, five spectators and a TV display. That is a capacity change, not a wire-protocol version change, and every service instance takes it.

Rule equality rejects older peers and snapshots: refresh peers together, and use fresh rooms after a rollback. Transport envelopes are unchanged except for the optional `role: "spectator"` on the existing `join` message; a manager on older rules never sees it, because the rules mismatch refuses that member first.

## Host succession by seat, and kick

Fold rules `fuse-p2p-46` change one thing in the fold: `successionOrder` ranks the connected human riders in seat order (`slot`, ties by id) instead of by member id. Seat order is what a player reads off the lobby list, so the room passes to the rider in the next seat down. Nothing else in the fold moves — the creator still ranks first and the connected spectators still rank last, by id — and no entry shape changes, so the rules move only because two peers ordering succession differently would disagree about which management entries are `permitted`.

The rest of this change is outside the fold. `RoomRuntime.command` now gates settings, start/rematch/lobby and bot changes on `RoomRuntime.managing` — the creator's own page, and the member `roomManager` names, which is the creator while the room counts it present and the acting creator otherwise — rather than on the creator alone; the fold already accepted those entries from either. The runtime's `Frame` carries `managerId`, derived from the same fold on every replica, so every screen names the same host.

Kick is `RoomCommand` `{ type: "kick", id }`: the manager appends an ordinary `LEAVE` for a human rider or a watcher, and once that entry has folded it sends the target a `{ type: "kicked" }` reliable message — a courtesy so the target's join card says why its seat went, accepted only from the creator or from the member the receiver holds as manager, retried while the link comes up and then given up on. The fold is what removes the member; nothing depends on the message arriving. No entry kind, snapshot field or checkpoint field changes.

A rider may be kicked in a `reclaimable` phase only (`lobby`, `roundOver`, `matchOver`), where `LEAVE` frees the seat outright; outside one it would only mark the rider absent, and the manager's own presence duties would log it present again on its next packet. Because the phase is checked against the fold while the entry is stamped a tick or more ahead, a kick issued at the very end of a pause can still land inside the round that follows, so the manager reads the outcome back from the fold rather than assuming it: the target is told only once it is gone, and a kick that did not take is reported to the manager instead of failing silently. A watcher holds no seat, so it goes in any phase. A peer on older rules that receives `kicked` ignores it as an unknown message type, and the `LEAVE` is refused with everything else that peer sends.

## Hidden members step away

Fold rules `fuse-p2p-47` let a member log its own presence. Its own `PRESENCE false` (kind 12, about itself, from a member that holds a seat or a place in the watching list and is not already away) is a **step away**, not a departure: the rider stays present to the game — its seat survives round and match boundaries and a return to the lobby, it is placed in the next round and rated like anyone present — while its controls fold neutral, its own entries go unread, and it leaves the succession order, so nothing waits on its stream and no manager judges its silence. Its own `PRESENCE true` while away brings it back. Nothing else an away member logs applies, the creator's entries included, with one exception: the absence of someone ahead of it in the succession order, ranked as if it were present, so a member whose last peer dies while it is away can still record that and then return. A `PRESENCE false` from anyone else, and a `LEAVE`, clear the mark and mean what they always did.

The state carries the mark where it belongs to the room rather than the game: a rider's fold gains an optional `away`, a watcher's record the same. In a peer snapshot each fold is `[id, generation, flags, activeGesture, latestGesture]`, with the ready vote as a sixth field and the away mark as a seventh `1` (a `false` vote fills the sixth when only the mark is set); a watching record takes an optional fifth `1`. A checkpoint is refused when the mark sits on a rider the game has absent, when it carries a ready vote beside it, or when either field holds anything else. A room nobody stepped away from encodes and hashes exactly as it did under rules 46.

Nothing on the wire changes except the `hello` message, which gains `hidden: boolean`. A hidden page announces itself so peers do not ask it for the world it has stopped advancing and do not follow its clock; an older build ignores the field. Rule equality rejects older peers and snapshots: refresh peers together, and use fresh rooms after a rollback. ADR-047 §12 and `docs/design/hidden-tab-policy.md` hold the policy and its limits.

## A rider's colour and head are its own, and unique

Fold rules `fuse-p2p-48` take colour off the seat. `RIDER_COLORS` (`games/fuse-riders/src/engine/tuning.ts`) holds ten colours instead of five, and a rider's `color` is no longer `RIDER_COLORS[slot]`: the fold gives a join the lowest colour no rider is wearing (`freeColor`) and keeps it unique from then on. The first five entries are the old seat palette in the order seats are claimed, so a room nobody recolours wears exactly what it always did — the golden recording's hashes are unchanged across the bump, only its rules pin moved. `slot` keeps its other jobs: seat order, bot names and the ink wobble.

One new player kind writes the choice, `COLOR` (kind 7): `[seq, tick, 7, colorIndex]`, with `colorIndex` a `uint32` below `RIDER_COLORS.length`. It rides the sender's own generation-scoped stream like `AVATAR`, and applies only if no other rider holds that colour when it folds; otherwise it is a no-op on every replica alike. `AVATAR` (kind 5) gains the same rule for heads, and a `JOIN` repairs a head another rider wears to the next free one in `AVATARS` order. Player entries fold in seat order, so two riders reaching for one colour in a tick resolve identically everywhere: the lower seat takes it, the other keeps what it had. The AI riders are exempt among themselves — they all wear `robot`, and it reads as taken to the humans in the room while one sits — but they take a free colour like anyone else.

The `JOIN` entry is unchanged, because its shape is the netcode's and shared with every other game; the colour a joiner asked for follows as its own `COLOR` entry once the room has seated it. A new entry kind is new wire content — a peer on older rules refuses kind 7 like any unknown kind — but no envelope, snapshot or checkpoint field changes. Checkpoint validation moves instead of growing: `gameInvariants` refuses a restored room whose riders share a colour or wear one outside `RIDER_COLORS`, where it used to require `color === SLOT_COLORS[slot]` (the array is renamed here), and `decodeRoom` refuses one in which two humans wear a head (it is the one place that knows which seats are the AI riders'). Rule equality rejects older peers and snapshots, so refresh peers together and use fresh rooms after a rollback.

## The room is the join screen

Fold rules `fuse-p2p-49` let a rider rename itself. `applyManagement`'s `JOIN` branch, for a member the room already seats, used to mark it present and drop the name the entry carried; it now takes that name (trimmed, and only when something is left of it). Nothing else about the entry moves — same kind, same shape, same arity, no snapshot or checkpoint field — and the seat, colour and head the rider already holds are untouched, so a rename is one ordinary `JOIN` over a seat rather than a leave and a re-join. A reconnecting rider re-sends `JOIN` exactly as it always did and now carries its own name back with it. The golden recording's hashes are unchanged across the bump, as they were across 48: its riders never rename.

Fold rules `fuse-p2p-50`, the current rules, integrate the shared prop catalog. Obstacle records keep the same fields, but a standing piece's `kind` is now `rock`, `building`, `crate` or `pyramid`; trees, bushes and cactuses are no longer valid. The movers a map lays (`wall`, `train`) are unchanged: they are shaped by their map rather than by the catalog, and checkpoint decoding validates them as it always did. The immutable `(kind, id)` selects a catalog variant with fixed half extents, validated on checkpoint decode. Variant ordering and dimensions are rules-owned. Rocks are circles (equal half extents) for rider, gun, blast, shell and spawn-clearance checks; other kinds are rectangles. Shell solid surfaces carry an explicit radius so rectangular walls do not inherit trail thickness. Placement uses conservative bounding-box gaps. Every scenery map shares the same variants; map-specific artwork stays client-only. The layout's random draw sequence changes and the golden workload is refreshed. Rule equality rejects older peers; refresh peers together and use fresh rooms after rollback. Room-service and transport envelopes are unchanged.

Names are deliberately **not** kept unique, unlike colours and heads (rules 48). Two friends called Sam could always both be Sam, nothing in the room breaks when they are, and colour and head are what tell riders apart on the board.

When a rename is allowed is the runtime's, not the fold's: a new optional `seating.renameable(room, id)` on the `RollbackGame` contract returns the line to show when it is refused, and Fuse Riders allows it in the lobby before that rider's own READY — the same line the AVATAR and COLOUR buttons leave on. A game that leaves the hook out never renames anyone and keeps the plain reconnection it had. A rename that slipped past the runtime would still fold identically on every replica, so this is a rule about when a player may choose rather than one the fold must enforce to stay consistent.

One netcode fix rides with it: `sendJoin` used to address every non-creator request to `managerId()`, which posts a member's own request into its own inbox when that member is the manager — which is every shared-screen room, where the creator takes no seat and the crown sits on the first rider. Such a request is now written where it is asked for. A side switch still never takes that path: its entry pair needs a writer that is not its subject, and is refused with `switchAsStandIn` instead.
