# Engine safety net (issue #253, stage A1)

This stage protects the current engine before the phase-pipeline migration. It does not move modules. The arena maps (#243) and the wrap and crossed maps (#248) have since merged and are covered here; #210 still needs reconciling before A2 rewrites `game.ts`.

The golden workload is a persisted, valid input log generated with `makeRecording(20260918, 30000, true)` (`tests/fixtures/replay-recorder.ts`): 12,779 ticks, 3,348 log entries, inputs only. The fixture holds `matchId`, `creator`, `ticks` and `entries` and the test rejects anything else, so nothing in it can write simulation state. An earlier recording sent the room back to the lobby on the tick after each pickup was collected, so it collected every mechanic and exercised almost none: over its 3,769 ticks a gun was armed for one tick, no tracer or shell ever existed, and one round and one match ended. This one uses what it collects.

Two scripted humans and three AI riders run through `applyTick`. The humans are flown by the bots' own planner, read from the state a player would be looking at, and everything they do reaches the room as the entries a device sends: steering flags, aim, press, release, cancel. On top of that they do what only a human stream does (a wandering thumb that tires as a round ages, a cancelled charge, a second press over a held one) and what only a human decides: holding a gun or a shell for a led, clean line, putting a bullet into scenery that has more scenery behind it, riding a Star straight at the wall. The creator directs the room through ordinary `SETTINGS`, `start`, `rematch`, `lobby`, `BOT`, `LEAVE`, `JOIN` and `PRESENCE` entries: the pickups that drop are whatever is still waited for, weighted by how much is waiting on them, and the map is the next one still to be played. Play runs in three stages. Five riders first, in two-round matches left in turn by rematch and by way of the lobby; the full-strength AI rides the opening match only and a second medium one has its seat afterwards, because its 32-tick lookahead is most of what a replayed tick costs after hashing. Then a three-round match the second human walks out of: it rides on absent, the round boundary prunes it, the next round is one rider short, a fourth bot takes the seat for the third, and the human takes it back. Then duels with the bots sent home, which cost about a third of a five-rider tick and so can afford to run long: one sat out without a bomb thrown until overtime stands walls around the `wrap` board and the second rider is given to them; one sat out on `forest` until the closing walls crush scenery (ridden twice here, the first ending at tick 761 of its round); and a broadside joust on `classic`, the creator holding a straight line and the second rider steering for where its head is going to be, until both die by `rider` on one tick — a shared place, a drawn round and a drawn match. It took six jousts of 40 to 100 ticks each; the second rider also holds its charges well past their reach until the aiming slowdown has once run out of budget, which no bot ever does. A duel that ends before its purpose is met is simply ridden again.

`tests/fixtures/replay-coverage.ts` reads everything it claims from the replayed state before and after each tick and from the tick's events, never from the fixture. `REQUIREMENTS` is the one list the recorder plays for and `tests/golden-hash.test.ts` asserts, so a fresh `--record` cannot write a fixture that fails its own test; the recorder stops only when every requirement holds and the match in play has been decided. `tests/fixtures/golden-hashes.json` pins every tick and its rules version. A refactor must preserve it. An intentional simulation change updates `RULES` and runs `npx tsx scripts/update-golden-hashes.ts --record` in the same `[rules N→N+1]` commit; **When the golden fails** below is the whole procedure. The updater refuses changed hashes or a changed workload under unchanged `RULES`, and refuses to pin any replay that no longer meets the coverage the golden test asserts, before writing either fixture. An identical refresh is a no-op. `--record` regenerates the input workload, formatted as the format gate expects. It is the ordinary path for a rules change, not a special one: the scripted riders react to what they see, so almost any change in behaviour plays the stored inputs into different rounds, and those no longer reach the coverage (changing `BLAST_VISIBLE_TICKS` from 8 to 9 loses pickups, among others). A golden assertion detects unintentional drift, not deliberate edits to both a test and its expected data.

## When the golden fails

`tests/golden-hash.test.ts` checks the rules version and the per-tick hashes first, and its message names the case and the first diverging tick. The coverage claims are checked after the hashes match. Every claim is listed in `tests/fixtures/golden-replay.ts`, which the test and the updater both read.

1. **`RULES` unchanged, hashes changed.** The simulation now behaves differently. Decide which it is:
   - _You meant to change behaviour_ (a mechanic, a constant, an ordering, anything a peer on the old code would disagree about): bump `RULES` in `src/engine/apply-tick.ts` and add what changed to its comment, then go to 2.
   - _You did not_ (a refactor, a cosmetic, tooling or test change): it is a determinism or behaviour regression. Do not refresh anything. The message names the first diverging tick; find what changed state there and fix it. A `[hash-identical]` commit leaves every tick as it is.
2. **`RULES` changed, golden not refreshed.** Run

   ```sh
   npx tsx scripts/update-golden-hashes.ts --record
   npx tsx --test tests/golden-hash.test.ts tests/order-independence.test.ts
   ```

   The first takes about a minute and is deterministic: the same source writes the same two fixtures on any machine, and running it twice changes nothing. Measured on a busy machine: 37 s under rules 32 (12,779 ticks recorded, then replayed once with the coverage observer), and 85 s for a trial change of `BLAST_VISIBLE_TICKS` from 8 to 9, where the recorder needed 20,102 ticks to see everything. The golden test takes about 20 s. Commit `tests/fixtures/golden-hashes.json` and `tests/fixtures/mechanics-recording.json` in the same commit as the engine change and the `RULES` bump. The measured table above describes the recording it was measured on; a fresh recording meets the same requirements with different counts.

3. **Hashes match, a coverage claim fails.** The engine is the pinned one and the recording is not: it was re-recorded or edited into something that no longer exercises requirement X. Restore both fixtures from main, or make the recorder reach X (below).

What `--record` does: it plays the scripted recorder (`makeRecording(20260918, 30000, true)`, `tests/fixtures/replay-recorder.ts`) under the new rules, two planner-flown humans and the bots, with the creator steering pickups, maps and roster towards whatever is still unmet, until every requirement in `REQUIREMENTS` (`tests/fixtures/replay-coverage.ts`) has been seen and the match in play is decided. It then replays the result, checks every claim the golden test makes, and writes both fixtures. It needs the rules bump: a changed recording under unchanged `RULES` is refused.

The plain updater (no `--record`) replays the stored inputs under the new rules. That is only enough for a rules change the stored workload does not notice; when the replay has lost coverage it says so in one line, writes nothing and exits non-zero, and the answer is `--record`.

If `--record` stops with `Coverage incomplete at 30000 ticks: <keys>`, the recorder could not bring those requirements about within its tick budget under the new rules, and nothing was written. The change made something harder or impossible for the scripted riders. Pass `makeRecording` a `report` callback to see each tick's outcome and which requirements were met when, and then, in order of preference: teach the recorder to play for it (`replay-recorder.ts`; the requirement's `pickups`, `map` and `stage` say how it goes about each one); or, when the change removed the mechanic from the game, remove its requirement in `replay-coverage.ts` and say so in the pull request as an explicit coverage change. Do not delete a requirement or raise a threshold's slack to get green, and do not raise the tick budget without looking: every extra tick is paid for in every run of the golden test.

Commit tags: an engine commit is `[hash-identical]` (the fixtures are untouched and the golden passes) or `[rules N→N+1]` (the bump, the engine change and both refreshed fixtures together), never both and never neither.

Two pull requests that bump `RULES` concurrently both claim the same number, and the fixtures of one do not describe the other. Whoever merges second merges main, takes the next free number (keeping both comments on the `RULES` line), resolves the two fixture files by taking either side, runs `--record` again, and commits that as its own `[rules N→N+1]` merge. The fixture conflict is the signal; a recording made before the merge is never valid after it.

Ordering becomes explicit where canonical hashing previously hid meaningful Map/object insertion order: player traversal is slot/id ordered, bombs are id ordered, and pickup weights use `PICKUP_TYPES`. The default-weight table (`pickup-weights.ts`, which seeds `defaultRoomSettings` and serves a game that has no room settings; the LAN server that once used it is gone) follows the same order, retaining its exact probabilities and matching room selection for the same roll.

Obstacles and pickups are arrays, whose order the canonical hash and a checkpoint both keep, and the engine generates both in id order. Reads that depend on order go through `sortedObstacles` or an id sort all the same: `firstContactTime` bisects from the contact found before it, so the order obstacles are visited in decides the low bits of a rider's scenery contact and of the point a gun ray stops at, and a shield is turned away from the last obstacle to match the earliest contact (since #289 `reflectAtObstacle` is handed that obstacle instead of searching for the nearest, so the sort it had is gone with the search). Order-free reads (`some`, `every`, `filter`) are left alone. The permutation replay reverses both arrays before every tick and restores id order after it, and asserts the engine itself never leaves them out of id order. Every Map, Set and id-keyed object — players, bombs, match statistics and the per-rival tallies inside them, the leaderboard, the round's participants, folds, bots, both copies of the weights — is rebuilt in descending key order before every tick. Rebuilt rather than reversed: a Map the engine leaves alone is back in its own order every second tick if it is only turned over, which is how the replay used to miss `roundParticipants`. Adding it exposed a real dependence: `rankRound` lists riders that share a place in the order it is given, `resolveRound` gave it the Map's insertion order, and `roundPlacements` — and since #299 the rating standings frozen from them — are compared state. `seatedParticipants` now hands it the riders in seat order. Each of the three scenery read sites and the round ranking has a focused constructed-state case in `tests/order-independence.test.ts`, each proved by reverting its sort on a clean tree and seeing exactly its own cases fail: a gun ray with two rocks in its line (stored far-rock-first, the unsorted loop stopped the bullet at x = 659.8000001747932 rather than 659.8000002298329); a rider reaching two abutting rocks in one step, and a shielded rider reaching two mirrored trees at the same instant, whose faces lean opposite ways; a shell that starts its tick against a rock's face and a crate's corner, where the first contact wins the tie and takes the shell off the other; and two riders dying on one tick. The recorded workload now also fires a bullet that stops at scenery with a higher-id obstacle behind it, which is what lets the permutation replay see the gun-ray sort reverted (tick 1,403), as it sees the ranking order reverted (tick 12,132); it still does not see the shell or rider sorts reverted, which only the focused cases pin. Blasts, portal pairs, gravity fields, trails, shots and moments are sequences whose order is what happened, and stay as they are. `splitWrappedSegment` sorts pieces by distance along the segment with no tiebreak: two pieces of one straight segment cannot start at the same distance, and the input order is a fixed array, not a Map. Codepoint ordering replaces locale-dependent tie breaks. The changes intentionally advance the rules version even where the ordinary workload's hash happens to stay stable.

AST tests reject nondeterministic math, powers, clocks and locale comparison in engine-owned source. Another AST import test classifies current and target directories and pins exact legacy violating edges. Removing an edge also requires removing its allowlist entry; adding an edge fails. The removed LAN server was application-layer code and never had an entry. The maps arrived on main before this guard did, with seven edges of the same kinds already pinned: the renderer reading engine geometry (`arena.ts`, `render-snapshot.ts`, and the newly classified render helpers `arena-maps.ts` and `arena-views.ts`, each to `arena-map.ts` or `wrap.ts`) and `wrap.ts` importing the `TrailSegment` type from `protocol.ts`. `self-locator.ts` (#277) is presentation code too — pure functions of a view snapshot that only the Phaser arena imports — so it is classified as a render helper like `reload-ring.ts`, which pins its two edges, to `snapshot-stream.ts` for the `ViewSnapshot` type and to `game.ts` for `TICK_HZ`. They are pinned exactly, 56 in all, with no wildcard; the voice chat, rating and ADR work merged since added none. This is a migration ratchet, not a claim that the current architecture already satisfies the target boundaries.

Seeded fake-network scenarios cover loss, duplicate delivery, reordering and repair with ordinary runtime commands. Cross-browser verification replays the same mechanic log in Node, Chromium and WebKit. The full browser matrix is not required for this stage; no browser UI or transport implementation changes are included.
