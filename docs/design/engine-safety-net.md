# Engine safety net (issue #253, stage A1)

This stage protects the current engine before the phase-pipeline migration. It does not move modules. The arena maps (#243) and the wrap and crossed maps (#248) have since merged and are covered here; #210 still needs reconciling before A2 rewrites `game.ts`.

The golden workload is a persisted, valid input log generated with `makeRecording(20260915, 30000, true)`. Two scripted human streams and three ordinary bots run through `applyTick`. The creator uses normal lobby/start/settings entries to select each pickup in turn, on the room's default rotation of obstacle maps, and finally the `wrap` map. Coverage observes actual collection events, portal exit grace plus a cross-arena displacement, and a surviving shield absorption. For the maps it observes rounds played on `desert`, `forest`, `city` and `wrap`; obstacles cleared by a blast on the tick it opened (31, overtime rubble excluded); riders killed under `wall` standing against scenery (11); a living rider carried through an open edge with no gate used (2); and a blast opened over an open edge, stored once per side (1). No fixture writes simulation state. Persisting the successful 3,769-tick log keeps the unit test fast and fixes the workload across refactors and rules updates.

Not reached, and not asserted: a shield absorbing a scenery crash (`reflectAtObstacle`), a shell or gun ray crossing an open edge, a shell bouncing off scenery, and the `cross` and `classic` maps (`cross` folds exactly as `classic`; the focused suites `tests/arena-obstacles.test.ts` and `tests/wrap-map.test.ts` cover these with constructed states). The recording may well pass through some of them; nothing observes it, so nothing is claimed.

`tests/fixtures/golden-hashes.json` pins every tick and its rules version. A refactor must preserve it. An intentional simulation change updates `RULES` and runs `npx tsx scripts/update-golden-hashes.ts` in the same `[rules N→N+1]` commit. The updater refuses changed hashes or a changed workload under unchanged `RULES`, before writing either fixture. An identical refresh is a no-op. `--record` regenerates the input workload, formatted as the format gate expects, and is only for an explicit coverage change; inspect coverage before accepting it. A golden assertion detects unintentional drift, not deliberate edits to both a test and its expected data.

Ordering becomes explicit where canonical hashing previously hid meaningful Map/object insertion order: player traversal is slot/id ordered, bombs are id ordered, and pickup weights use `PICKUP_TYPES`. The default-weight table (`pickup-weights.ts`, which seeds `defaultRoomSettings` and serves a game that has no room settings; the LAN server that once used it is gone) follows the same order, retaining its exact probabilities and matching room selection for the same roll.

Obstacles and pickups are arrays, whose order the canonical hash and a checkpoint both keep, and the engine generates both in id order. Reads that depend on order go through `sortedObstacles` or an id sort all the same: `firstContactTime` bisects from the contact found before it, so the order obstacles are visited in decides the low bits of a rider's scenery contact and of the point a gun ray stops at, and `reflectAtObstacle` keeps the first of two exactly equidistant faces. Order-free reads (`some`, `every`, `filter`) are left alone. The permutation replay reverses both arrays before every tick and restores id order after it, and asserts the engine itself never leaves them out of id order. The recorded workload does not happen to put two rocks in one bullet's line in the telling order, so a focused test in `tests/order-independence.test.ts` does: stored far-rock-first, the unsorted loop stopped the same bullet at x = 659.8000001747932 rather than 659.8000002298329. Blasts, portal pairs, gravity fields, trails, shots and moments are sequences whose order is what happened, and stay as they are. `splitWrappedSegment` sorts pieces by distance along the segment with no tiebreak: two pieces of one straight segment cannot start at the same distance, and the input order is a fixed array, not a Map. Codepoint ordering replaces locale-dependent tie breaks. The changes intentionally advance the rules version even where the ordinary workload's hash happens to stay stable.

AST tests reject nondeterministic math, powers, clocks and locale comparison in engine-owned source. Another AST import test classifies current and target directories and pins exact legacy violating edges. Removing an edge also requires removing its allowlist entry; adding an edge fails. The removed LAN server was application-layer code and never had an entry. The maps arrived on main before this guard did, with seven edges of the same kinds already pinned: the renderer reading engine geometry (`arena.ts`, `render-snapshot.ts`, and the newly classified render helpers `arena-maps.ts` and `arena-views.ts`, each to `arena-map.ts` or `wrap.ts`) and `wrap.ts` importing the `TrailSegment` type from `protocol.ts`. `self-locator.ts` (#277) is presentation code too — pure functions of a view snapshot that only the Phaser arena imports — so it is classified as a render helper like `reload-ring.ts`, which pins its two edges, to `snapshot-stream.ts` for the `ViewSnapshot` type and to `game.ts` for `TICK_HZ`. They are pinned exactly, 56 in all, with no wildcard. This is a migration ratchet, not a claim that the current architecture already satisfies the target boundaries.

Seeded fake-network scenarios cover loss, duplicate delivery, reordering and repair with ordinary runtime commands. Cross-browser verification replays the same mechanic log in Node, Chromium and WebKit. The full browser matrix is not required for this stage; no browser UI or transport implementation changes are included.

Integration: main `6950ef1` brought the arena maps (rules 26), the wrap and crossed maps (rules 27), the removal of the LAN server, and player statistics with Elo history (#270). #270 added per-rider `combat` counters to the folded match statistics without a rules version of its own; they are written and never read back by the simulation, their id-keyed objects are hashed and decoded in sorted key order, and rules 28 is the first version that names them. Its `elo.ts` raises 10 to a fractional power, which the source guard rejects in engine-owned code. `elo.ts`, `rating.ts` and `career-stats.ts` are the history service's settlement and the account panel's view of it, computed once by one authority and folded by no replica, so the guard now classifies them as shared non-engine modules; the import guard fails if engine-owned code ever imports one. `combat-stats.ts` stays engine-owned and guarded. The merge keeps both and advances the combined rules to 28. Map rotation is a room's default, so the old inputs no longer reached the old coverage; the workload was re-recorded with `--record` under the new rules by the same seeded generator, extended with the map goals above.

Earlier integration: upstream #249 landed at `d600756` with rules 25 and frozen match finishers while A1 was in progress. The merge from main `14654da` preserves that feature, advanced the combined rules to 26 and replayed the exact original input workload to update the golden. Those rules-25 and rules-26 commits belong to the pre-merge branch history; main claimed 26 and 27 for the maps, and the delivered rules version is 28.
