# Independent review: direct actions and world rollback

Date: 2026-09-14. Scope: proposed [ADR041](../adr/041-direct-actions-and-world-rollback.md), the direct-action brief, existing shared action reducer/game phases, and current WebRTC/signalling boundaries. This is a design review, not implementation or release evidence.

## Recommendation

The proposed architecture matches the requested online replacement: ordinary actions go directly from their origin to every subscribed simulator, each view advances independently, and the coordinator finalizes/reconciles lifecycle without approving or relaying each input. Approve implementation of independently testable direct-input, stream and rollback modules with the contract clarifications below incorporated first. Runtime activation additionally requires the integration amendments and evidence below. Keeping a host relay as the final design would not meet this approval.

The 40-tick speculative bound is a safe-failure limit, not a promise of mobile performance. The 32 MB encoded snapshot/history bound is an enforceable application storage budget; actual JavaScript heap and temporary clone/replay peaks must be measured separately. No public release is approved.

The amended ADR041 was subsequently inspected and the core contract is approved. It chooses exact-cut watermarks: all sequences at or below the named sequence have ticks at or below the named tick, and later sequences have later ticks. This is stricter than the initially discussed last-issued watermark and remains implementable: origins wait until the clock reaches their latest issued action tick before publishing the next cut. The other core clarifications and the signalling/offer-initiation amendments are incorporated. Implementation must preserve earlier accepted cuts until their constraints are subsumed by finality; a newer cut must not erase an earlier promise or previously established completeness proof.

## Required core clarifications

1. **Watermark promises and reordering.** For watermark `(T,N)`, actions with sequence greater than N must have tick greater than T. Missing actions at sequence at most N remain admissible at or before T; otherwise a watermark arriving first would make repair impossible. Validate both existing buffered actions and future arrivals against promises. A dominated older watermark is stale, not a fault merely because an unreliable channel reordered it. Equal coordinates are idempotent; incomparable progress or conflicting same-tick promises are faults. Origins must honor the chosen equal-through-tick sequence rule when publishing future actions.

2. **Finality and checkpoint prefixes.** Distinguish the sequence named by a completeness watermark from the exact applied prefix at finalized tick F. A watermark can name already-issued actions after F. Checkpoint prefix for each stream must be the last sequence whose action tick is at most F; restore must leave later actions available for replay, rather than considering them applied. Certification needs contiguous possession through the watermark's named sequence and its promise through F. Computing a hash at F must exclude later actions, while retaining all held controls and gesture state produced through F.

3. **Gesture replacement and aim.** The existing shared game ignores a bare press while already charging. A replacement gesture must therefore fold to `cancel` followed by `press`, and each command must capture the aim applicable at that action's position in the same-tick sequence. Folding final held aim into every earlier command can change targeting. A nonmatching release/cancel must never cancel the currently active newer gesture. The current shared operation validator permits at most 128 bomb commands per slot/tick; either choose a compatible explicit input bound or use an independently bounded direct-input reducer without silently discarding transitions.

4. **Pruning and stale duplicates.** Retain immutable duplicate identities for the rollback/repair window. After finalized history is pruned, retain a baseline sequence fence and reject/ignore older records without replaying or allocating for them. Do not require an unbounded lifetime identity table. An action above the finalized sequence fence that claims a tick at or below finality is a fault. Fresh stream bootstrap includes initial sequence/gesture state explicitly, including the neutral sequence-zero baseline.

5. **Fast message schema.** Freeze distinct action/progress and receipt discriminators, exact tuple arity, numeric bounds and segment binding in the first implementation. Receipts acknowledge validated contiguous possession only. The decoder must enforce the encoded 512-byte limit before MessagePack allocation. Finality arriving before its required fast records stays pending within a bound; it must not prematurely hash the speculative state or classify ordinary cross-channel reordering as divergence.

## Required integration amendments

Both `src/service/gateway.ts` and `worker/index.ts` currently reject guest-to-guest signalling. Opening that routing is necessary for the real topology. Preserve current room incarnation, membership, connection-replacement, SDP/ICE validation, target connection and quota fences. Add provider and Worker tests proving permitted same-room guest signalling and rejection of stale/foreign targets. The service remains signalling-only.

`PeerTransport` currently has host-only offer/restart initiation and one channel field. Specify a deterministic initiator for each peer pair or a tested glare policy, separate reliable/fast channel registration and send gates, connection-scoped alias readiness, and a bounded restart policy per required link. Preserve the current WebKit closing-state send protection for both channels. Test subscription changes and direct guest-to-guest traffic in the actual browser runtime, not merely a fake broadcast interface.

Coordinator-blocked gameplay proof is bounded: peers should continue receiving one another's actions and advancing before the finality horizon, then explicitly pause if finality remains unavailable. This is not unlimited host-free continuation. In shared-TV mode, the creator keeps service lease/management ownership while a fenced TV coordinator simulates; a controller-only creator must not retain hidden HostSession physics. The exact clock estimator, input stamping, readiness barrier, role/connection replacement and delegated coordinator state machine require deterministic tests before runtime activation.

Keep tentative derived scores/deaths and irreversible presentation separate. The current shared step mutates these fields before round finalization; render adaptation must choose provisional geometry and finalized outcome UI deliberately. Finalized event IDs must survive duplicate finality and recovery without duplicate sounds/notices. Round transition must wait for the finalized outcome and create the new scoped segment exactly once.

## Acceptance evidence still required

The listed real-code MessagePack, permutation/loss/idle-release, gesture, watermark/finality, overflow, atomic recovery and six-replica convergence tests are appropriate core gates. Add explicit regressions for every clarification above. Runtime proof must include direct guest links, blocked coordinator traffic within and beyond the horizon, independent ticking, clocks, TV delegation, lightweight controllers, bots, role/connection changes and reliable-checkpoint competition with the fast channel.

Measure both directions and all payload classes under the same active five-rider-plus-TV workloads as the baseline, along with input-to-render/finality latency, corrections, replay/frame time and retained/peak memory distributions. Exact mixed-engine replay, sustained impairment runs, LAN regressions and independent implementation review remain required. Passing core tests cannot establish the final online replacement, physical-phone feel or wire-bandwidth savings.
