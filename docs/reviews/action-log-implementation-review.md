This approval applies to the inspected implementation and documented desktop test scopes; it is **not public-release approval**, physical-phone qualification or a guarantee of determinism on every engine/platform. The log explicitly records completion of mixed-engine five-rider-plus-TV play, application-level delivery impairment, guest reconnect and role transitions.

The prototype retains reliable ordered WebRTC, host coordination, upstream held-input refresh and local movement prediction. It does not implement full-world speculative rollback, edge-only upstream delivery, mesh agreement, durable replay archives, WAN/OS packet-loss acceptance or physical-phone performance qualification. ## Initial disposition

Changes required before claiming reliable prototype acceptance. The simulation capture boundary and atomic candidate replay are sound foundations, but protocol compatibility, decoder allocation and baseline validation need corrections. Findings below describe the inspected working tree; resolution requires regression evidence and a follow-up review. Browser acceptance and the complete suite remain the implementing agent's responsibility.

## Findings

1. **P1 — MessagePack decoding lacks a nesting/allocation budget.** `unpackMessage()` bounds each collection independently, while `PeerTransport` decodes before validating envelope authority. The pinned decoder allocates `new Array(size)` on each nested array header. Repeated array16 headers declaring length 1024 can allocate very large nested capacity within the 200 KB wire bound, before the eventual malformed record is rejected. A harmless 3,001-byte payload containing 3,000 nested single-element arrays was experimentally accepted. Add pre-decode depth, node and total declared collection-capacity limits, or use an equivalent decoder capability that actually enforces these limits before allocation. Test nested valid/truncated arrays and maps, declared lengths, extension payloads and ordinary real envelopes.

2. **P1 — Prototype negotiation does not prove compatibility or fail legacy peers visibly.** `actionHello` contains only wire version and display role, without `REPLAY_RULES`; old code silently ignores it. The opt-in guest then drops ordinary worlds forever with a generic waiting status, rather than reporting incompatible mode. Add explicit accepted capability/rules acknowledgement and a bounded negotiation deadline; wait for accepted mode before interpreting binary prototype traffic. Bind an `actionUnsupported` reply to the current host and active negotiation: the initial implementation processes it before checking sender identity, allowing a guest to terminal-stop the host UI. Test old/unsupported/no-response peers and wrong-sender replies.

3. **P1 — Replacement checkpoints can roll back same-tick lifecycle history.** `ActionReceiver.chunk()` checks candidate tick but not candidate operation sequence. A newer generation can install an older checkpoint at the same tick, erasing accepted avatar/settings/join changes. Reproduced with baseline sequence 1, an accepted avatar change at sequence 2 without advancing tick, then the original baseline relabeled generation 2: receiver reports accepted and restores the old avatar. Require sequence monotonicity within the outer authority scope as well as tick/generation rules. Test stale lower-sequence checkpoints at both equal and greater tick, and preserve healthy state on rejection.

4. **P2 — Action admission permits states rejected by checkpoint admission.** `validOperation([1, ...])` accepts a 128-character name and arbitrary color; the shared `addPlayer()` does not normalize these, while `decodeGameState()` requires a trimmed name of at most twenty characters and slot-matched color. Repeated accepted join/remove operations can also grow historical collections beyond the 128-entry checkpoint bound. Apply consistent semantic identity and aggregate state validation before publishing the candidate as healthy. Add malformed identity and history-boundary tests, alongside legal slot reuse and normal complete-match replay.

5. **P2 — TV invite silently drops requested replication mode.** The share dialog's OPEN TV VIEW link uses only room and display parameters. An action-mode room therefore opens the TV through the snapshot path. Preserve `replication=actions` on this link and verify the opened TV actually reports accepted action batches, rather than only proving that it renders. This directly affects the shared-TV role acceptance promised by ADR040.

6. **P2 — Hash cadence depends on successful transmission at one exact tick.** `ActionSender` supplies a hash only when the current game tick is divisible by twenty. If backpressure prevents those sends, later repair batches carry no hash and may allow arbitrarily long unverified replication. Track the last included/acknowledged comparison position and include a current-position hash once the maximum interval is reached, with replayable tests that block precisely the twentieth-tick sends. Compare hashes only against the complete included operation suffix.

## Positive observations and remaining evidence

HostSession routes joins/removals, connection changes, settings, avatars and round management through the reducer. Human scheduling and bomb transition sequencing remain unchanged; bot outputs are captured rather than independently recomputed on replicas. Replica candidate state is cloned before operations and only assigned on successful validation/hash comparison. Live reducer events are not dispatched to UI callbacks, leaving the existing authoritative event path single-sourced. Checkpoints preserve game connection/charge fields and exclude host admission capabilities. Chunks have explicit count/byte/time limits and send pumping is bounded.

The initial tests exercise real MessagePack round trips, lifecycle replay, some duplicate/drop/reordering paths and rejection without state mutation. The test named checkpoint chunk loss/reordering/corruption/timeout does not yet actually advance the clock beyond the assembly deadline or prove recovery after a missing middle chunk. Add explicit timeout, resync-rate, bounded send failure, old/new generation, retained-history expiry and multi-chunk recovery cases. Assertions should establish eventual accepted progress or terminal safe failure, not only a nonthrowing callback.

Role transitions need browser evidence that individual view to controller mode releases full replica history, controller to full view installs a new baseline, and stale earlier-mode messages cannot replace the newly selected view. Verify negotiation/sender state on connection replacement and repeated signalling welcome, while retaining old-client default snapshot compatibility. The currently retained upstream refresh and local-only movement prediction are approved prototype limitations, not defects or evidence of the final edge-only bandwidth estimate.

Measure cloning/hash/replay CPU and application bytes under sustained five-player-plus-TV workloads. A no-error browser smoke or one matching trace does not establish numerical determinism, smooth mobile behavior or public-release readiness.

## Follow-up inspection

The six original findings are addressed in the inspected working implementation:

- MessagePack receives a structural scan before allocation, capped at depth 32 and 20,000 nodes/declared child slots, in addition to byte and individual-container limits. Truncation, unsupported extension types and trailing data are rejected.
- Negotiation now carries rules and wire versions, requires an explicit welcome and has a five-second deadline. Unsupported replies are accepted only from the host by an opt-in guest. Failed action mode refuses new user commands.
- Replacement baselines enforce operation-sequence and tick monotonicity, including after controller-mode release retains anti-rollback fences.
- Identity admission matches checkpoint constraints, replay candidates undergo complete game validation before assignment, and host admission bounds historical identities.
- TV links preserve the requested action mode.
- Hash comparison remains due until acknowledged; the regression blocking exact twentieth-tick sends observes comparisons at ticks 21, 41, 61 and 81.

Independently inspected all 143 recorded execution inputs in `artifacts/action-math-dependencies.json`. The only reachable built-in Math references/aliases found are `floor`, `abs`, `round` and the shared `sqrt`; no native trigonometry or native-addon dispatch was found in that graph. The public notices contain both Sun and Go source notices. Game checkpoint JSON now tags negative zero, and canonical state distinguishes it. Checkpoint compatibility is `fuse-simulation-2` and replay rules are `fuse-actions-2`.

Completed-output inspection found 469 tests passed, zero failed, with 99.52% lines and 94.3% branches under existing enforced thresholds. Both saved LAN browser outputs state completion. The replay artifact reports three distinct 2,400-tick traces, including the weapon/portal fixture, with zero hash mismatches in Chromium and WebKit. These artifacts identify the parent revision with `dirty: true`; they qualify the recorded working implementation, not an immutable final commit. At inspection, the room artifact covers mixed-engine real WebRTC play, bounded application-level impairment and guest reconnect; role-transition checks were still being rerun after a harness modal issue.

### Remaining P2: signed zero in MessagePack aim tuples

The primitive MessagePack encoder turns `-0` into integer `0`, while canonical replay state now distinguishes them. An accepted host-local input with `aim: {x: -0, y: 0.5}` leaves negative zero in the journal's held aim. Its checkpoint game string preserves signed zero, but the separately encoded held tuple does not; the receiver consequently returns `resync` and never installs that otherwise legal checkpoint. Reproduced through real `packMessage`/`unpackMessage` and sender/receiver calls. Normalize zero components of held and transient bomb aim tuples at the shared capture boundary before applying them, or preserve signed zero in their wire encoding. Add encoded checkpoint and action-suffix regressions for this accepted boundary case. This remaining fix and completed role-transition evidence are required before closing prototype review.
