# Independent implementation review: direct-action core

Date: 2026-09-14. Scope: `src/shared/direct-input.ts`, `src/online/direct-stream.ts`, and `src/online/rollback-world.ts` against amended ADR041. Tests were still being written at initial inspection. Runtime, clock/coordinator integration and online release are outside this review's completion scope.

## Initial findings

1. **Earlier watermark constraints are discarded.** `DirectStream` retains only its newest watermark. Accepting `(5,1)`, then `(10,2)`, then actions `(sequence=1,tick=3)` and `(sequence=2,tick=4)` currently returns accepted throughout. The second action violates the earlier promise that no sequence after 1 can occur through tick 5. This was reproduced with actual exported module calls. Retain bounded unfinalized cuts or equivalent interval constraints; validate existing records and future arrivals against them, including when older cuts arrive late. Trim constraints only when their meaning is preserved by the finalized base or a truly stronger equivalent constraint.

2. **A newer incomplete cut erases earlier completeness.** With action 1 at tick 3 and cut `(5,1)`, `completeThrough(5)` is true. Receiving cut `(10,2)` before action 2 makes it false, even though completeness through tick 5 remains proven. This was reproduced through exported module calls. Select a retained certified cut that proves the requested tick, rather than requiring possession through the newest unverified watermark. Otherwise future packet loss unnecessarily delays finality and can force an avoidable pause.

3. **Bootstrap permits an impossible active gesture.** A valid game plus held bomb flag and gesture `{active:1, latest:2}` is admitted by `RollbackWorld.open(packBootstrap(...))`. The reducer can only produce `active=0` or `active=latest`: a newer press replaces the prior active gesture. Validate this invariant and retain rejection atomicity. The executable reproduction used an ordinary game with default room settings and a roster entry; no private state mutation was used.

## Positive observations and remaining gates

Per-tick folding preserves player iteration order, command-local aim, replacement cancellation, and matching release semantics. Stream admission builds a candidate before installing it, validates identities and tick order, and only exposes contiguous records. Rollback restores strictly before newly admitted actions; event storage is rebuilt for replayed ticks and only emitted on verified finality. Exact finalized prefixes are distinct from newer completeness cuts, and same-finality duplicates are checked without re-emitting events.

The initial findings require fixes and regressions before approving this core. Completed real-MessagePack tests must cover delivery permutations, last-release and receipt loss, same-tick gesture/aim order, watermark history/finality, bounds, corrupt bootstrap and six-replica convergence. These tests do not establish real WebRTC latency, full runtime replacement, mobile performance or release acceptance.

## Fix verification and disposition

Approve the inspected core as the foundation for integration. All three initial findings are resolved. `DirectStream` now retains at most 64 unfinalized completeness cuts, validates new and retained actions against every cut, rejects incompatible older cuts, and keeps earlier certified progress usable when a newer cut has missing records. Finality trimming preserves a baseline sequence/tick fence and later cuts; encoded cut storage is included in the world budget. Bootstrap admission now requires an active gesture to equal the latest gesture, or to be zero.

Independently ran `node --import tsx --test tests/direct-actions.test.ts` against the inspected working-tree sources: 19 tests passed, zero failed, zero skipped. Regressions reproduce both older-promise arrival orders, preservation of certified progress despite a newer gap, cut overflow/trimming, and rejection of a rehashed impossible gesture state. Additional tests cover full absolute ticks, bounded real MessagePack decoding, sequence gaps/conflicts, late whole-world rollback, all six same-tick packet permutations, replacement gestures, idle final-release repair, lost receipts, pending finality, exact checkpoint prefixes, speculative pause/resume, malformed boundaries, atomic encoded-history overflow, and six replicas across three seeds.

This approval is deliberately a core implementation disposition. The six-replica test uses in-process deterministic delivery and a short fixed workload; it does not establish sustained active gameplay, cross-browser behavior, actual WebRTC delivery, clock quality, TV/controller runtime roles, or measured latency/heap/wire costs. Complete repository checks, actual integration, sustained impairment evidence and independent runtime review remain required for the requested online replacement. No public release is approved.

## Initial browser transport inspection

Inspected `PeerTransport` mesh/fast-channel changes and `scripts/direct-mesh-browser.ts`; the parent was running the browser harness, so this review did not start another copy. The lexicographically smaller peer initiates offers/restarts. Compact binding records include the authority epoch/incarnation and both current connection identities; current-link callback checks reject callbacks from replaced RTC objects. Fast ingress checks the 512-byte packet boundary, exact action/receipt shape and alias before dispatch, with bounded receive tokens. Runtime bootstrap/ownership validation remains responsible for authorizing calls to `bindFast`.

Two corrections are required before transport approval. The reliable `game` channel currently checks its label but not its ordered/reliable delivery settings; admission must verify ordered delivery and absent retransmission/lifetime limits. Also its closing/close/error handlers drain only the reliable gate, while `sendFast` checks only the fast gate. That leaves a fast-send window after an early reliable closing signal during the known WebKit association shutdown ordering. Drain both required-channel gates on either terminal channel signal, or otherwise apply the reliable drain fence to fast sends. Preserve current-link checks so stale channel callbacks cannot drain a replacement.

The harness appropriately describes coordinator *application callback* blocking while lease/liveness traffic continues. Its all-direction sends can establish actual fast-channel delivery when completed, but its stale-alias check currently exercises sender rejection rather than forged stale ingress. It does not yet establish channel-close/restart recovery, connection/epoch replacement, sustained loss/rate behavior or integrated gameplay. Those remain distinct evidence gates. In particular, bot/aim workloads must be checked against the 100-message/second per-link limit; several streams owned by one coordinator share that limit.

The ordered/reliable channel validation and shared drain corrections were subsequently inspected and are resolved. Both required channels now drain both gates on terminal signals with current-link checks; `fastReady` and `sendFast` share the same readiness predicate.

Further membership/async inspection found a replacement race requiring correction. The welcome handler waits for ICE configuration, then emits peer-online callbacks and offers from its original roster without rechecking the current socket/admission and current peer connection identities. An offline or replacement message during that wait can therefore be undone by a late online callback. Likewise, `link(id)` checks the socket across its ICE await but not the remote connection identity. An old-source signal waiting for ICE can resume after replacement and construct a new RTC object using stale SDP, then route its response to the current replacement connection. Capture and validate current local/remote connection identities across async ICE/offer/description boundaries, and filter resumed welcome work against current membership. Object-identity callback checks alone cannot fence an obsolete operation that creates a new object after replacement. Add delayed-ICE/membership regressions before transport approval.

The subsequent identity-fence changes resolve this inspected race: resumed welcome processing checks the current socket/local admission and each original peer's current connection ID; link construction captures/rechecks local and remote connection IDs across ICE loading; signal processing checks the returned RTC object's current identity. A `linkReset` callback also permits fresh alias handshakes after RTC recreation. The expanded browser harness now includes stale-alias ingress, action-channel closure/recreation and a held ICE request during another peer's replacement. A removal-without-replacement test should additionally assert no obsolete online callback/offer after ICE release; merely observing eventual replacement convergence is weaker than asserting stale work was suppressed.

## Compact liveness probe design amendment

Approve replacing steady-state reliable-envelope probes with bounded fast tuples `[1,segment,8,probeId]` and `[1,segment,9,probeId]` after alias binding, provided the following rules are implemented. Third values 8/9 are reserved outside receipt slots 0–4 and use exact four-element validation, uint32 IDs, the same scope/512-byte/rate checks, and separate transport dispatch rather than application action delivery. Keep the existing 200 ms probe cadence, outstanding-ID bounds and 600 ms acknowledgement validity initially; measure their loss sensitivity now that delivery is unreliable. Count encoded bytes in both probe directions.

Probe and pong sends must bypass the current-health predicate used for ordinary gameplay sends, while retaining bound identity, open-channel, drain and small probe-buffer checks. Otherwise a short loss burst marks the link unhealthy and prevents the probes required to restore health. Deferred pongs capture and recheck both their RTC object and received segment after the macrotask, so a new binding cannot relabel an old request. Continue answering reliable bootstrap probes on their reliable lane even after local fast binding; asymmetric handshake progress must not deadlock. Reliable bootstrap probes remain available before binding. These probes establish link liveness only; they do not certify held controls, action possession or simulation completeness. Re-run blackhole/recovery, asymmetric binding, stale/deferred pong and channel-close evidence for this semantic change before transport approval.

An asymmetric-binding browser failure subsequently demonstrated that reliable replies alone are insufficient: a peer may bind locally before its own health allows the reliable bound acknowledgement, while the other peer still drops unbound fast probes. Approve the proposed correction to send both compact and reliable bootstrap probes until a validated incoming compact probe or pong proves the remote knows the exact current alias. Track this as remote alias readiness separately from health; only a valid pong for an outstanding issued probe establishes acknowledged delivery. Reset readiness for each new alias, authority scope or RTC association. Continue reliable-lane replies throughout. Stale aliases cannot confirm readiness. The parent retained the failing browser evidence as `artifacts/direct-mesh-browser-asymmetric-binding-failure.json`; successful rerun and code inspection remain required.

The implemented `remoteConfirmed` correction was inspected and matches this amendment. Exact-scope compact liveness marks remote alias readiness; only `LinkHealth.acknowledge` can turn a received issued-pong ID into delivery evidence. Fast probe sends bypass gameplay health gating while preserving scope, drain and probe-buffer checks. Reliable replies remain reliable, and deferred fast pongs retain their received segment. No additional protocol blocker was found in this inspection.

Transport acceptance remains pending: the inspected latest `artifacts/direct-mesh-browser.json` records `Error sending binary data through RTCDataChannel.` in its page-error list. The parent reports the expanded connectivity/blackhole/closure/membership assertions completed before that final gate failed and is collecting phase/stack diagnostics. Passing those assertions does not turn this run into a clean pass. Resolve or make an explicit independently reviewed scope decision about the browser error, preserve the failing evidence, and rerun the relevant acceptance gate before approving the transport implementation.

## Input-origin and clock amendment review

Reviewed the proposed input-origin/clock integration amendment before implementation. The origin direction is appropriate: separate UI revisions from wire sequences, omit unchanged resends, stamp absolute next-tick actions independently, preserve explicit gesture edges, and prepare an entire local update before publishing it. The clock remains separate from rendering and simulation mutation, with bounded outstanding probes/samples, monotonic progression and explicit stale/fault states.

One clock rule requires correction before implementation approval. The proposal accepts RTTs up to 500 ms but latches a recovery fault whenever a newest midpoint estimate differs by more than four ticks, before selecting the lowest-RTT sample. A valid 480 ms response whose delay is almost entirely on one leg can have 4.8 ticks of midpoint error, falsely faulting an otherwise accurately running client. Validate discrepancies using the sample's uncertainty interval rather than treating its midpoint as truth, and account for uncertainty in the current alignment; alternatively specify another bounded rule that proves accepted network jitter cannot cause this false fault. A noisy newest sample must not defeat the stated lowest-RTT estimator. Regression evidence must include this concrete asymmetric-delay case alongside a real clock discontinuity.

The amendment also needs these implementation clarifications:

- Sample a fractional coordinator tick immediately before sending the scoped reply. Define pre-start/readiness behavior explicitly: a future segment start cannot yield playable ticks before the bootstrap base or admit controls before activation.
- A stale/faulted clock must block both new controls and completeness advancement. A release that could not be timestamped must lead to visible cancellation/recovery and cannot be queued to fire when freshness returns. Define how local input state is neutralized and a fresh physical gesture becomes eligible after recovery.
- Reject or explicitly define contradictory local fields such as a press edge with `bomb:false`; otherwise separate origin adapters could interpret the same update differently.
- Prepare the origin, local stream and every required subscriber queue before publishing any group bytes. A later transport enqueue failure retains the admitted records for paced repair; it cannot undo actions already published to another peer. Existing `DirectDelivery.enqueue` publishes immediately, so runtime integration needs an explicit prepare/commit boundary or equivalent proven group preflight.

Clock/timestamp implementation approval is pending these amendments. They preserve the direct-action target and do not introduce coordinator admission for normal inputs.

The revised input-origin/clock contract was subsequently inspected and is approved for implementation. Discrepancy validation now compares the newest and previous selected sample uncertainty intervals at one observation time; a high-RTT midpoint cannot alone override jitter selection or trigger the four-tick fault. Pre-start followers require a reply sampled after the coordinator reaches the bootstrap tick. Input/completeness blocking, failed-release cancellation/recovery, contradictory-frame rejection and preparing every group candidate before publication are explicit. The stale-baseline greater-than-four-tick rebootstrap is a conservative recovery policy after missing clock history, not proof of a physical clock jump. Implementation tests must also show that later fresh samples cannot revive a failed release before its required lifecycle/control recovery completes. Runtime activation and implementation evidence remain pending.

## Runtime wiring amendment review

Reviewed the proposed runtime wiring amendment against the goal of replacing the actual online path. `DirectSegment` composition, a compact bound reliable lane, creator-owned management with delegated full-view simulation, and geometry-free controller status are the right direction. The compact reliable lane is acceptable with a closed discriminator set, exact per-message validation, the 2 KB bound, current authority/connection/alias fences and existing send gates. This does not authorize activation before the lifecycle clarifications below or qualify the outstanding native-send behavior.

One newly identified interaction requires amending the earlier origin cut rule. With continuous aim/steering changes, the latest issued action is usually stamped one tick ahead. An independently scheduled 100 ms progress pump using the current clock tick can repeatedly fail `tick >= lastActionTick`, causing a healthy active origin to hit the 500 ms silence barrier. Timer or render-event phase alignment cannot be a correctness prerequisite. Publish the exact cut `(currentTick, lastSequenceAtOrBeforeCurrentTick)` while preserving already-issued future records. The receiver's exact-cut rules already allow sequences after that cut at later ticks. Add a bounded per-tick origin frontier and a delivery API that accepts this exact cut, with an adverse-phase continuous-aim regression. Publishing cuts into the future instead would add avoidable input delay and is not the recommended correction.

Before lifecycle/runtime activation, make the following contracts explicit:

- Clock, finality and controller status come only from the exact delegated coordinator connection/generation; action slots are authenticated against immutable origin owners; receipts come only from subscribed simulators for their stream. Admission to the room alone does not confer these roles.
- Barrier prepare/ready/activate/applied messages carry explicit generation/transfer IDs with duplicate/stale handling, bounded retry/retention and timeout. A scheduled start that is no longer safely usable after all required readiness receipts must be rescheduled or aborted, never activated inconsistently.
- Same-match coordinator handoff cannot install a base older than any receiving simulator's finalized prefix/history. Otherwise an apparently valid older checkpoint can undo irreversible scores/events. Include all already finalized history or use the explicit fresh-lobby recovery path when it is unavailable.
- Neutralization clears simulation charge/target state as well as held flags and active gestures. Keep management intentions bounded and scoped; the existing one-recent-command/five-second policy is a suitable baseline rather than indefinite queuing while a display is absent.
- Controller status carries segment/tick/revision fences and distinguishes provisional availability/geometry from finalized outcome fields. Define change filtering and a rate bound so status does not recreate routine bulk metadata traffic. Stale status cannot disable controls for a newer scope or promote a speculative death to a finalized result.

These are integration contract requirements, not a request to retain a host relay or another permanent opt-in runtime. Approval of the new lifecycle orchestration remains pending their incorporation and evidence.

The revised runtime wiring contract was subsequently inspected and is approved for implementation: it now states delegated coordinator/slot/subscriber authorization, bounded management intentions, explicit barrier identity/deadline behavior, comprehensive neutralization, monotonic finalized-history handoff and scoped/change-filtered controller status. The origin's bounded current-tick frontier and delivery exact-cut API also match the progress-starvation correction. The new orchestration regression deliberately processes continuous input before every watermark pump. Integrated implementation approval remains pending its completed tests and the finality refinement below.

## Pending-finality starvation refinement

The parent found a second composition-level liveness defect: replacing the only pending certificate with each newer coordinator proposal can prevent a lagging replica from finalizing an already reconstructable earlier tick while later inputs remain incomplete. Approve replacing that single pending slot with at most 40 per-tick certificates, strictly after current finality and within its 40-tick horizon. Apply the highest currently complete/reconstructable certificate, retain newer ones, prune certificates at or below newly committed finality, and include encoded certificate storage in the byte budget. The ADR's earlier single-pending statement must be amended accordingly.

Retained same-tick certificates must be immutable; normalize prefix pair order for semantic duplicate comparison. A now-checkable invalid prefix/hash must not be silently bypassed because a newer certificate happens to be valid. Keep rejection/overflow atomic and emit each newly finalized event once. Required regressions cover a continuing stream of newer incomplete certificates while earlier finality advances, same-tick conflicts and reordered duplicates, retained-certificate bounds/budget behavior, and event deduplication across multi-tick finality advancement. This is a reviewed change to preserve useful progress under bounded loss, not a relaxation of finality correctness.

## Repair scheduling and publication refinement

Approve bounded rotating repair selection to avoid repeatedly spending every spare slot on the same early records while receipts lag. A fresh edge group remains first and immediate; include the earliest unacknowledged record unless already present, then rotate remaining repair slots by stable sequence IDs. ACK removal and candidate copying must not reset rotation to the same tail. Keep the four-record/512-byte packet cap, 50 ms repair pacing and 256-record retention bound. Add lost-receipt regressions proving both earliest-gap coverage and tail progress, not only eventual success after action loss. All records remain retained until receipt or explicit recovery; rotation does not weaken delivery semantics.

Approve finality publication as soon as a newly complete tick becomes eligible, at no more than 10 Hz. An unsuccessful attempt to propose finality must not consume the 100 ms publication opportunity. If a new eligible certificate arrives during the rate window, retain it and flush when due even if no further event arrives. A failed transport enqueue retains a certificate for bounded retry and cannot undo already committed local finality. These changes remove avoidable scheduling delay without publishing physics state every tick.

The existing combined 100-message/second fast bucket is insufficient for legitimate input, receipts, cuts and liveness. A replacement must be derived from explicit supported per-stream production bounds and the five authenticated slot ownership/subscription relationships on each link. For illustration, a declared 60 Hz new-input bound plus 20 Hz repair and 10 Hz cuts gives at most 450 messages/second across five action/receipt stream roles, plus 10 probe/pongs; a 500-message/second combined budget could cover that declared envelope with a finite burst. This is not approval to silently restrict the currently tested 100 Hz aim workload to 60 Hz. Specify its actual bound or reviewed UI coalescing policy first. Separate a small liveness allowance from action/receipt traffic, preserve an overall byte/message ceiling, validate stream ownership before using slot allowances, and measure bot/continuous-aim workloads before freezing the final limits.

### Clock uncertainty and future staging amendment

Approve a fixed global uncertainty contract as the simplest bounded correction, subject to implementation/regression inspection. A playable clock may have at most five ticks of uncertainty, measured as the selected sample's radius plus the distance from its projected midpoint to the current clock projection. A larger value yields an explicit `uncertain` state: no new actions, completeness advancement or world advancement until qualified again, with existing bounded progress/recovery behavior. This retains the stated 500 ms sample envelope without imposing a new 150 ms RTT readiness cutoff. Do not classify incoming action timestamps as corrupt using an unqualified stale/uncertain target; leave those packets for existing bounded repair. Latched clock faults still require visible recovery.

Derive the remote future-record staging bound from both participants' maximum uncertainty plus permitted origin lead. With five ticks for each clock and the existing at-most-four-tick origin lead, that is **14 ticks** beyond the local target. The current segment's strict next-tick path would need only 11, but adopting 11 without tightening the broader origin contract would leave an undocumented exception. No per-packet clock metadata is necessary when all admitted participants share this fixed bound. Preserve the origin's own four-tick limit, four-record/512-byte packets, 256-record queues, byte budgets and 40-tick execution/finality horizon. Future staging does not execute actions early or extend rollback history.

Required regressions compose actual origin/clock/stream delivery: the reproduced asymmetric coordinator/follower case, two followers with opposite accepted estimation errors, exact permitted/rejected future boundaries, and an uncertain sample that cannot issue controls/cuts or advance the world. A clock-quality recovery must not revive a failed release or an old segment. This is an explicit reviewed change to the earlier four-tick *remote admission* rule; it does not authorize silently weakening its old assertion without replacing that assertion with the new derived boundary evidence.

Approve a related initial-progress grace of 1,500 ms from the coordinator's segment start until each origin's first strictly newer validated cut (`throughTick > baseTick`). Post-start sender-time confirmation can consume a 500 ms clock RTT plus probe phase, followed by first-cut scheduling/transit; the normal 500 ms silence deadline cannot be assumed to start before that exchange finishes. After the first advancing cut, retain the existing 500 ms deadline since strictly advancing progress. Base/duplicate cuts and action packets cannot reset the initial deadline or count as initialization. Keep the independent 40-tick speculative ceiling. Regression evidence must cover successful delayed startup, failure when an origin never advances within the initial grace, and the shorter silence deadline after its first advancing cut.

The subsequent implementation inspection confirms the finalized death/placement fields, shared 5/4/14 uncertainty/lead/staging constants, qualified fast-ingress target, per-origin startup grace, controller finality conflict fence and stopped-state check after event callbacks. Independently reran the three direct-action/origin-clock/segment test files: 47 passed, zero failed or skipped. New evidence includes opposite follower estimation errors exceeding nine ticks, staging without early execution, the exact 14/15-tick admission boundary, unchanged 40-tick execution limit, provisional elimination visibility and startup/steady silence handling.

One residual correction is required: uncertainty currently becomes zero when every clock sample expires. Using the added test's accepted samples, `read()` reports uncertainty 14.5 and `canAdvance:false` at 970 ms; it remains uncertain at 1,500 ms, but at 1,980 ms returns stale, uncertainty zero and `canAdvance:true` without receiving another sample. Preserve uncertainty disqualification across sample expiry until a new bounded observation qualifies it. Previously qualified idle clocks can retain their separately allowed bounded stale advancement. A sample-expiry regression is needed before this correction is approved.
