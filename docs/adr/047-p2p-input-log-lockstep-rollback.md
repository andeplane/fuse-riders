# ADR-047: Peer-to-peer input-log lockstep with rollback

- Status: Accepted (describes what `main` implements; it proposes nothing)
- Date: 2026-09-17
- Supersedes: [ADR 028](028-online-authority-and-lifecycle.md), [029](029-online-simulation-time.md), [030](030-online-delivery-and-replication.md), [031](031-online-rooms-and-operations.md), [032](032-online-acceptance.md), [041](041-input-log-and-rollback-core.md), [042](042-controller-only-phones.md), and the protocol text of [035](035-direct-gameplay-only.md), whose direct-only policy (no gameplay relay, no TURN) this ADR carries forward unchanged
- Replaces [P2P-INPUT-LOG-BRIEF.md](../online/P2P-INPUT-LOG-BRIEF.md) as the description of the model. The brief keeps the original goals, the measurements and the review history.

The code is the source of truth. Every rule and number below was read from source and is cited as a path plus a symbol name. Where the reason for a number is not written down in the code or an existing document, this ADR says "rationale not recorded" instead of inventing one. `tests/p2p-adr-constants.test.ts` fails when an exported constant in the table below stops matching its source.

## Context

Fuse Riders is a small game for two to five friends. `AGENTS.md` sets the constraints this model answers to: responsive play, consistent outcomes, low hosting cost, no always-running simulation server where practical, a room service that "does not simulate or relay gameplay", and no silently added gameplay relay or paid service. [ADR 035](035-direct-gameplay-only.md) had already removed the gameplay relay and declined to provision TURN, accepting a visible connection failure when WebRTC cannot connect.

The earlier online design (ADRs 028–032, then the host-anchored log of ADR 041/042) made one browser the authority. [ROLLBACK-PLAN.md](../online/ROLLBACK-PLAN.md) §0 records why that failed in play: the host decided when an input applied, so scope changes and freshness rules dropped presses and releases. The peer-to-peer brief replaced it on 2026-09-15 with a model in which nobody decides when another member's input applies. Until this ADR that model had no decision record, and the brief had drifted from the code (issue [#258](https://github.com/andeplane/fuse-riders/issues/258), finding T6).

## Decision

### 1. Every member simulates one shared log

State at tick T is a pure fold of the seed and every log entry stamped with a tick ≤ T (`games/fuse-riders/src/engine/apply-tick.ts` `RoomState`, `applyTick`). Every member of a room runs that fold locally, including a display-only TV and a controller phone in shared mode, which merely does not draw the arena (`packages/fuse-netcode/src/room-runtime.ts` `RoomRuntime`). Solo play is the same runtime with no transport. Bots are not logged: `applyTick` calls `BotController.input` on every replica, so bots are part of the deterministic fold.

Lockstep only works if that fold is bit-identical on every JavaScript engine in the room, because replicas exchange inputs, never state. Today that is kept by convention in `games/fuse-riders/src/engine/`: trigonometry comes from the pinned pure-JavaScript `sin`, `cos` and `atan2` of `games/fuse-riders/src/engine/deterministic-math.ts` and distances from its `hypot2` (no `Math.sin`, `Math.cos`, `Math.atan2` or `Math.hypot`), randomness comes from the seeded stream in the game state, and nothing under `games/fuse-riders/src/engine/` reads `Date.now` or `performance`; `scripts/determinism-replay.ts` replays one seeded log in Node, Chromium and WebKit. Nothing on `main` enforces the convention: [PR #267](https://github.com/andeplane/fuse-riders/pull/267), in review and not merged, adds AST source guards and a cross-engine golden hash.

The simulation runs at `TICK_HZ` = 20 (`games/fuse-riders/src/engine/tuning.ts`), one tick per `TICK_MS` = 50 ms of clock time (`packages/fuse-netcode/src/clock.ts`). `RoomRuntime.start` schedules `tickLoop` every 10 ms.

### 2. Streams, sequence numbers and generations

Each member owns one append-only stream (`packages/fuse-netcode/src/stream.ts` `StreamLog`). An entry is `[seq, tick, kind, ...args]` (`games/fuse-riders/src/engine/input-log.ts` `Entry`, `isEntry`): `seq` starts at 1 and increases by one; `tick` is absolute and never decreases within a stream. Player kinds are `STEER`, `PRESS`, `RELEASE`, `CANCEL`, `AVATAR`, `READY`, `COLOR`; management kinds are `JOIN`, `LEAVE`, `PRESENCE`, `SETTINGS`, `ACTION`, `BOT`, `SPECTATOR`. Since rules 49 a `JOIN` for a member the room already seats renames it rather than only marking it present. Kind 1 (Target Bomb's `AIM`) was retired in `fuse-p2p-40` and is refused. Press gesture ids must strictly increase along a stream (`StreamLog.append`, `StreamLog.receive`).

A member stamps its own entries `max(floor(clock) + 1, lastOwnTick)` (`RoomRuntime.ownTick`), so its own input applies on the next tick with no round trip. Input is edge-filtered: an unchanged frame produces no entry (`RoomRuntime.input`).

A stream is identified by member id and generation. The generation is the page load, in 100 ms units since 2020-09-13 (`pageGeneration`), so a reload starts a new stream at seq 1. A packet from an older generation than the one already seen is dropped (`RoomRuntime.fast`). The stream a newer generation replaces is kept as retired until nothing it holds can be replayed (`packages/fuse-netcode/src/rollback.ts` `World.stream`, `World.retain`); the reducer takes a rider's player entries from the generation its fold currently holds, and management entries from every generation (`applyTick`).

### 3. The per-tick packet

Every member sends one packet to every other member whenever its clock reaches a new tick. A new own entry triggers another: immediately for input and avatar entries, on the next 10 ms loop pass for the rest (`RoomRuntime.tickLoop`, `sendPackets`, `input`, `append`). It travels on the unreliable channel as a MessagePack array of twelve fields (`packages/fuse-netcode/src/packet.ts` `Packet`, `encodePacket`):

`[PACKET_VERSION, room, from, generation, through, lastSeq, entries, sentAt, echoSentAt, echoHeld, clockTick, hash]`

- `room` is a 32-bit FNV-1a hash of `code:creatorId` (`roomHash`, `RoomRuntime.welcome`); `from` is the sender's member id.
- `entries` holds **the sender's own entries only**, at most `PACKET_ENTRIES` = 6: the two newest plus a rotating share of the retained window, so every retained entry recurs with no acknowledgement (`StreamLog.packetEntries`). Nobody forwards anybody else's entries.
- `lastSeq` is the highest seq the sender has issued; `through` is `max(own through, floor(clock))` (`RoomRuntime.sendPacket`). Together they are a promise receivers enforce (§6): every entry the sender issues after `lastSeq` is stamped after `through`.
- `sentAt`, `echoSentAt` and `echoHeld` make every packet a round-trip sample; `clockTick` is the sender's fractional clock.
- `hash` is `[tick, hash]` or null (§8).

A packet is at most `MAX_PACKET_BYTES` = 1100 bytes, "one datagram under the 1,280-byte IPv6 minimum MTU with DTLS/SCTP headers to spare; a SETTINGS entry is ~230 bytes" (`packet.ts`). `encodePacketTrimmed` drops the oldest entries until the packet fits; `decodePacket` refuses anything larger before decoding, and the transport refuses it again in both directions (`packages/fuse-network-fe/src/peer-transport.ts` `maxFastBytes`, set to `MAX_PACKET_BYTES` by `games/fuse-riders/src/online/ui.ts`).

A sender retains its own entries stamped within the last `RETAINED_TICKS` = 40 ticks of its `through`, at most `RETAINED_ENTRIES` = 64 (`StreamLog.retained`).

### 4. The tick clock and its authority

`TickClock` (`packages/fuse-netcode/src/clock.ts`) computes `tick = base + (now − t0) / TICK_MS` plus a slewed offset, from an injected monotonic clock, and never steps backwards. It has one rate in every phase of play: the clock counts **log ticks**, and a game that runs faster runs more simulation steps per log tick (§11), never a faster clock.

The **time authority** is the creator for as long as the room service lists the creator as a member; otherwise it is the lowest id among this member and the members it has heard within `CREATOR_SILENCE_MS` (`RoomRuntime.authority`). Each replica computes this from its own observations; it is not a log entry. An authority that opens a fresh world starts its clock at 0 (`RoomRuntime.createWorld`); a returning creator is the time authority as soon as the roster lists it, and starts its clock when it installs a peer's snapshot, from the freshest peer `clockTick` projected to now, else from the snapshot tick plus half the request round trip (`RoomRuntime.acceptSnapshotChunk`, `TickClock.started`). Once started, the authority never adjusts its clock: it takes no samples. A follower feeds every authority packet's `clockTick` and measured RTT to `TickClock.sample`, which assumes the authority is `rtt / 2` further on, keeps the lowest-RTT sample of the last `SAMPLE_WINDOW_MS`, and slews toward it at no more than `SLEW_TICKS_PER_SECOND`; an offset beyond `SNAP_TICKS` snaps instead. A follower with no fresh sample free-runs. Packets from members other than the authority feed only per-link RTT.

The time authority is a different role from the acting creator of §9: the first is chosen from the service roster and local silence, the second from the log, and the two can be different members at the same time.

### 5. `completeTick()`, speculation and the stall rule

For a stream, `StreamLog.completeThrough` is the owner's declared `through`, capped one tick before the first entry waiting behind a gap. `StreamLog.confirmedThrough` is stricter: with a gap open it is the highest `through` declared while the stream had no gap, or one tick before the last contiguous entry, whichever is later.

`World.completeTick` is the minimum `confirmedThrough` over every connected human rider. Ticks up to it are final on this replica; it gates the desync hash, snapshot serving and `RoomRuntime.confirmedTick` (used by analytics).

Simulation does not wait for completeness. The world advances toward `floor(clock)`, at most `CATCHUP_STEPS` = 8 simulation steps per 10 ms loop interval, and no more than `CATCHUP_MS` = 6 ms of them (a log tick is one step, or `BOTS_ONLY_STEPS_PER_TICK` in the fast phase, §11; C8), predicting that a rider whose entries have not arrived keeps its held controls. It may run at most `STALL_TICKS` = 40 ticks past the least complete connected remote human (`World.stallBound`, which uses `completeThrough`); beyond that it stops and shows "Waiting for <name>". A disconnect already logged for that rider (`World.pendingDisconnect`) lets the bound move to the disconnect tick. Deaths, pickups and scores are rendered from this speculative world; events are emitted once per `(matchId, round, tick, index)` across rollbacks (`World.step`).

Presentation draws one tick behind the clock, interpolating the two newest simulated ticks, with the local rider led by up to one tick of its held controls (`RoomRuntime.view`, `games/fuse-riders/src/online/prediction.ts` `presentWorld`).

### 6. Rollback, retention and bounds

`World` clones the state every `SNAPSHOT_INTERVAL` = 4 ticks and keeps `SNAPSHOTS_RETAINED` = 12 of them; applied entries and event keys at or before the oldest retained snapshot are pruned (`World.retain`, `StreamLog.prune`). A newly contiguous entry stamped at or before the current tick restores the newest snapshot before it and re-simulates to the tick the world had reached (`World.rollback`), within the same step budget as catch-up (C8): what the budget leaves is owed to the next loop passes, which run it before any new tick and without the stall bound (those ticks were reached once already). The re-run is private to `World` (`work`): until it reaches that tick, `World.state`, `tick` and `view()` stay on the newest state the world had reached, so nothing outside it (the runtime's own seat and held gesture, the manager's presence duties, the stall rule) ever sees history go backwards; the re-run's events are held and delivered with its frames. `World.settled` says whether a re-run is owed. A later entry at or before the re-run's current tick starts it again from an earlier snapshot (dropping held events after that snapshot, which the new re-run decides afresh), and one after it is simply folded when the re-run gets there. Only the re-run's own snapshots are hashed or served (`hashAt`, `servable`); an install drops it. Nothing about the result changes: every tick folds the same entries whenever it is simulated.

`StreamLog.receive` validates a whole packet before touching the stream and rejects the whole packet on any fault, with a reason (`Refusal` in `packages/fuse-netcode/src/stream.ts`). A `violation` is something no unmodified client sends: more than `PACKET_ENTRIES` entries, a malformed entry, a seq above `max(lastSeq, known lastSeq)`, a changed entry under a known seq, ticks or press gestures out of order, or a broken `through` promise. A `window` refusal is the receiver's own limit and says nothing about the sender: a `lastSeq` more than `SEQ_AHEAD` = 4096 past the contiguous prefix, an entry stamped more than `FUTURE_TICKS` = 400 ticks past the receiver's clock, or more than `BUFFERED_ENTRIES` = 256 entries waiting behind a gap. §9 says what each costs the sender.

**The `through` promise.** A packet declaring `through` = T with `lastSeq` = S promises that every entry its sender issues with seq > S is stamped with a tick > T. It says nothing about entries up to S, which may sit at or before T and still be in flight; a repeat of a held or pruned entry is a no-op whenever it arrives. The sender keeps the promise by construction: an own entry is stamped `max(floor(clock) + 1, lastOwnTick)` (`RoomRuntime.ownTick`), `TickClock.tick` never steps back, and a snapshot install raises `lastOwnTick` past the installed tick (`RoomRuntime.acceptSnapshotChunk`). An entry may therefore ride in the very packet whose `through` has reached its tick, because that packet's `lastSeq` names it. The receiver records the promises per stream generation — the highest T whose S the contiguous prefix has reached, plus the pairs still past a gap (`StreamLog.promise`) — and refuses a new entry stamped at or before any T declared with a lower S (`StreamLog.promisedBefore`). The check reads only sender-side facts, so loss, duplication and reordering of an honest stream cannot trip it. Without it a member could declare completeness `ROLLBACK_TICKS` ahead, watch two seconds of play, and commit input inside ticks every replica held final, which also falsified `completeTick()` (§5). What it cannot catch: a sender may announce a seq and deliver it up to the rollback window late, which is indistinguishable from loss — but that is a visible gap, not a silent one (§7).

**The seq bound.** A `lastSeq` out of reach opens no gap: the packet is refused and the stream is flagged `StreamLog.ahead` until a packet is taken again. An honest stream can get there — a replica cut off from a busy rider for minutes on the same page and generation — and no NACK can repair that distance, so the flag sends the replica to a snapshot (§7). `FUTURE_TICKS` is deliberately wide: "clocks converge by slewing, so a live peer may legitimately stamp a few seconds ahead for a while; the bound only keeps an absurd tick from parking entries forever" (`stream.ts`).

An entry is `unrepairable` when it is at or before the stream's base tick, when it is `ROLLBACK_TICKS` = 40 or more ticks behind the current tick, or when no retained snapshot precedes it. That forces a resync (§7).

### 7. Gaps, NACK, repair and resync

A gap is `contiguous < lastSeq`. The receiver sends a NACK `[NACK_VERSION, room, from, firstMissingSeq]` on the unreliable channel, at most once per `NACK_INTERVAL_MS` per stream, from both the receive path and the tick loop. The owner answers with up to `PACKET_ENTRIES` retained entries from that seq (`StreamLog.repairEntries`), or nothing when the seq has left its retained window.

A member asks a peer for the world (`RoomRuntime.requestSnapshot`) when:

1. it has no world (join, reload);
2. a received entry is `unrepairable`;
3. a gap has stayed open longer than `STALLED_GAP_MS`, or a stream has been `ahead` (§6) that long — the same throttled path without the NACK. Once the owner no longer counts as heard (§9) the `ahead` requests back off to one per `WINDOW_GRACE_MS`; they never stop, and a request that could not go out, for want of a link fit to carry it, does not use up the wait;
4. catching up would cost more than `BEHIND_STEPS` = 400 simulation steps, estimated as the log-tick backlog times the step count the world's state runs at now (`RoomRuntime.behind`; C8), counted from the world's tick, so a rollback's owed re-run (at most the rollback window) never adds to it: in the tick loop the backlog is what the stall rule lets it reach (`min(clock, stallBound) − world tick`), and on returning from a hidden tab the raw `clock − world tick`;
5. its state hash differs from the authority's (§8).

One request is tracked at a time, on the reliable channel. The tick-loop triggers (1, 3 and the first half of 4) wait for a tracked request to finish; an `unrepairable` entry, a hash mismatch and the return from a hidden tab call `requestSnapshot` without checking, which discards the transfer being assembled and may rotate to another peer. The target is the peer that just greeted, else the time authority, else the linked peers in rotation, skipping for `SNAPSHOT_RETRY_MS` any that answered `noWorld` and always any refused for its `RULES` (§10). A request is retried after `SNAPSHOT_RETRY_MS` with the next peer; `SNAPSHOT_FAILURES` = 3 failures show "Could not load the game — reload this page" and the retries continue. A peer serves at most one snapshot per requester per `SNAPSHOT_SERVE_MS`.

The served state is `World.servable`: the newest retained snapshot no later than `completeTick()`, or the current state when everything is complete or the server is itself stalled. `packages/fuse-netcode/src/snapshot.ts` `encodeSnapshot` packs `[rules, room, tick, ...leading game fields, streams, hash, ...trailing game fields]`, which for Fuse Riders (`games/fuse-riders/src/online/fuse-game.ts`) is `[RULES, room, tick, game, settings, folds, bots, streams, hash, spectators]`; each stream carries its base seq, base ordinal (the press gesture) and up to `MAX_SNAPSHOT_ENTRIES` entries after the tick (retired generations first), and splits the base64 text into chunks of `ceil(SNAPSHOT_CHUNK_BYTES × 4 / 3)` = 21,334 characters, which is `SNAPSHOT_CHUNK_BYTES` = 16,000 bytes of snapshot per chunk. `SnapshotAssembler` accepts chunks in order from the one peer asked and enforces `MAX_SNAPSHOT_BYTES`, as `encodeSnapshot` does on the serving side. `decodeSnapshot` checks the bounded MessagePack preflight (whose own size cap is `MAX_MESSAGE_BYTES`), `RULES` equality, the room hash, the game state's shape and invariants (`games/fuse-riders/src/engine/codec/checkpoint.ts` `decodeGameState`), folds and bots against the seated riders, the state hash and stream ordering — all before `World.install` replaces the world. The installer keeps its own stream's seq numbering and re-applies its own entries after the snapshot tick (`RoomRuntime.acceptSnapshotChunk`).

A creator opens a fresh world only when the roster is empty or every linked member has answered `noWorld`, counting members refused for their `RULES` as nobody (`RoomRuntime.compatible`); a member that is not the creator never opens one (`RoomRuntime.tickLoop`).

### 8. The desync hash

`hashRoomState` (`apply-tick.ts`) hashes the canonical JSON of the whole room state — game, settings, folds and bots, with map entries and object keys sorted — with two 32-bit FNV-1a lanes, as 16 hex characters. It is a diagnostic, not a proof.

Every member attaches a hash to its packets when its clock tick is a multiple of `HASH_INTERVAL` = 20 and `tick − HASH_LAG` (40) is at or before its `completeTick()`; the hash is of the retained snapshot at `tick − HASH_LAG` (`RoomRuntime.sendPacket`, `World.hashAt`). Only the time authority's hash is compared (`RoomRuntime.fast`, `compareHash`). The comparison is skipped when the tick is past the receiver's `completeTick()`, when any stream has a gap, or when the receiver no longer retains a snapshot at that tick.

On a mismatch the replica logs both hashes with `console.warn`, shows "Simulation corrected · resyncing" and requests a snapshot. `DIVERGENCE_LIMIT` = 3 mismatches within `DIVERGENCE_WINDOW_MS` set `outOfSync` and show "Simulation out of sync — reload this page" instead of requesting a snapshot. That holds only while three mismatches sit inside the window: once they age out, a later mismatch requests a snapshot again, although `outOfSync` is never cleared. The replica keeps simulating throughout.

### 9. Membership, seats, presence and succession

**Service.** The room service admits members by token, derives the member id from the token (`packages/fuse-network-be/src/room-store.ts` `peerId`), names the creator (`hostId` in `welcome`), publishes roster changes and forwards validated SDP/ICE (`packages/fuse-network-be/src/gateway.ts`, `signal.ts` `validSignal`). It answers a `relay` frame with an error. It holds no game state. A room admits its creator plus `ROOM_LIMITS.maxGuests` = 10 others (`service/room-limits.ts`): five riders, five spectators and a display. Admission and every valid `time` heartbeat, from any member, extend the room by `ROOM_TTL_MS` = 90 s and the member's connection by `CONNECTION_TTL_MS` = 30 s (`RoomStore.admit`, `RoomStore.time`); a member's departure also extends the room by `ROOM_TTL_MS` when its own connection lease and the room are still live (`RoomStore.leave`); the client sends that heartbeat every 2 s (`PeerTransport.connect`). Only the creator's token can end a room (`RoomStore.end`). Since [#262](https://github.com/andeplane/fuse-riders/pull/262) a room therefore lives while any member keeps its socket, not only while its creator does ([design note](../design/member-kept-room-lifetime.md)). The authority lease (`packages/fuse-network-protocol/src/authority.ts`) only fences a duplicate creator tab (close code `CLOSE_AUTHORITY_REPLACED`); gameplay does not consult it.

**Handshake.** On a confirmed link each side sends `hello` with its generation, whether it is a full view, its `RULES` and whether it holds a world (`RoomRuntime.greet`). A member that wants a seat sends `join` to the manager and retries every `JOIN_RETRY_MS`; a member that wants to watch sends the same `join` with `role: "spectator"`.

**Seats.** The manager validates the name, claims one of five slots — between rounds it may first free a disconnected rider's seat with `LEAVE` — and appends `JOIN` carrying the joiner's generation (`RoomRuntime.join`, `claimSlot`).

**Spectators.** A member may instead take a place in the watching list: `RoomState.spectators`, at most `MAX_SPECTATORS` = 5, written by the `SPECTATOR` entry (kind 16) and folded, hashed and carried in snapshot payloads like everything else the room agrees on ([design note](../design/spectators.md)). A spectator is a named, listed member with no seat, no colour, no fold and no inputs: it never reaches `step`, the leaderboard or the match report, and `completeTick` and `stallBound` never wait on its stream, so a silent watcher cannot stall a round. It is otherwise an ordinary member — it serves and requests snapshots, echoes the clock and ranks in the succession order. A member is a rider or a spectator, never both: `JOIN` is refused for a listed spectator and `SPECTATOR join` for a seated rider. A member changes sides without leaving the room by re-sending its ordinary `join` or `spectate` command: the manager answers it with an ordered pair of those same entries at one tick — `SPECTATOR leave` then `JOIN`, or `LEAVE` then `SPECTATOR join` — which `applyManagement` applies in the order the manager wrote them, so no entry kind and no fold rule changed for it (`RoomRuntime.join`, `spectate`, `switchable`). A switch waits for a pause, as a kick does and for the same reason, and the member that writes the pair may not be its subject: `permitted` is re-evaluated per entry, and between the two the member is in neither map, so `successionOrder` cannot rank it and the second entry would be refused on every replica. The creator is exempt, since `permitted` answers for it without ranking it, so a manager that is not the creator sends its own switch to the creator's page instead of writing it (`RoomRuntime.switchWriter`) — which is what the shared-screen configuration needs, because a creator with no record leaves the crown on the rider in the first seat for the room's whole life. Only a room whose creator's page has left has nobody who may write the pair, and that member is told so. A pair is decided against one manager's fold and its own `pending()`, so in the two-manager case above a same-tick `JOIN` or `BOT add` from the other manager can take the slot a switch claimed; the second entry is then refused, the member is in neither list, and its page asks again as an ordinary joiner. A `?display=1` TV stays what it was, an unlisted viewer that takes a socket and no place in the list.

**Presence.** A member is heard when a packet of its is taken, or is refused only as outside this replica's `window` (§6) — the latter for at most `WINDOW_GRACE_MS` = 10 s, counted from the first such refusal since a packet was last taken. A packet refused as a `violation`, and anything from a member refused for its `RULES`, is not hearing it (`RoomRuntime.fast`). Without the first rule a member sending only packets no replica can fold stayed heard and stalled the room for good; without the grace's end an inflated `lastSeq` would do the same. The manager logs `PRESENCE false` for a seated rider that has been silent for `DISCONNECT_MS` = 1000 ms, unless its own loop stalled for more than half of that, and `PRESENCE true` when a rider logged absent is heard again (`creatorDuties`, `ensurePresence`, `logPresence`). Silence is measured (`RoomRuntime.silent`) from the member's last packet, or from the moment the link to its current connection was first seen usable (`Member.linkedAt`, set in the tick loop from `RoomTransport.linked`) if that is later. A page that has just loaded has heard nobody, and a page that has just loaded cannot be heard yet; neither is silence. That covers a member this runtime has not heard yet; it does not cover every way a runtime can go deaf to a member it has heard (the manager's own socket reconnect, under Known limitations). A member never heard whose link has never come up is silent once `LINK_WAIT_MS` = 5000 ms have passed since this runtime learned of its current connection (`Member.since`, set again when the service replaces that connection) or since this runtime first held a world (`RoomRuntime.judgingSince`, set when the first world is installed from a snapshot or created, never on a resync), whichever is later: before it has a world a runtime judges nobody, so a creator whose own first link or snapshot took five seconds has only then begun to wait for the others — counted from the announcement alone, the wait had already run out when the world arrived and every rider not yet linked was logged absent in the second pass. So a rider this runtime has never heard is logged absent `DISCONNECT_MS` after its link came up, and no later than `LINK_WAIT_MS` + `DISCONNECT_MS` = 6 s after the later of those two moments; a rider it has heard is judged exactly as before. The cost of the anchor: a rider that died while the creator was reloading, and that the service still lists, holds the creator's own replica for `LINK_WAIT_MS` after it recovered the world rather than after its page loaded. The link counts once per connection: a second `peer` online event for a known member (the service replaced its connection without an offline event) clears it, a link that merely flaps does not, so a link can never stand in for packets for longer than one `DISCONNECT_MS`, which is inside the `STALL_TICKS` speculation window. `PRESENCE true` still needs a packet. Before this rule a reloaded creator created every member record with last-heard `-Infinity`, recovered the world from its first linked peer and, in its second loop pass, logged every rider whose link was still coming up as absent; a round boundary or a `lobby` action inside that window pruned healthy riders (`games/fuse-riders/tests/reload-presence.test.ts`). The price is an honest stall: a creator that cannot hear a connected rider waits for it (§5) instead of unseating it. A rider that arrives with a new generation is re-logged present at once only by the creator (`RoomRuntime.ensureStream` checks `this.creator`); an acting creator does it when that rider's `join` reaches it, or through `creatorDuties` once the rider has been logged absent. A service `peer` offline event is logged as `LEAVE` in the lobby, which frees the seat, and as `PRESENCE false` once a match is running, whatever its phase (`RoomRuntime.peer`, `applyManagement`). A reload always reaches the manager as that event, because the service retires the old socket before it admits the new page; logged as `LEAVE` during `roundOver` or `matchOver` it freed the seat at once, so a reload that landed just after a round ended lost the seat within that round and came back to the join card (`games/fuse-riders/tests/reload-presence.test.ts`). A disconnected rider folds neutral controls and is pruned at the next round or match boundary (`applyTick`, `pruneDisconnected`). Presence reaches a spectator by the same entries: its place is freed by `SPECTATOR leave` in the lobby and held by `PRESENCE false` once a match is running, and an absent spectator is dropped wherever an absent rider's seat is freed (`dropAbsentSpectators` on `start`, `rematch` and `lobby`).

**Creator and acting creator.** `successionOrder` is the creator, then the connected human riders in seat order (`slot`, ties by id), then the connected spectators sorted by id. Seat order is what a player reads off the lobby list, so the room passes to the rider in the next seat down rather than to whoever holds the lowest member id (fold rules `fuse-p2p-42`). Watchers rank last, because a room with a seat left in it should be managed from that seat, but they do rank, so a room whose riders all dropped is still run by whoever is left watching. `permitted` applies a management entry when it comes from the creator; from the acting creator (`actingCreator`: the second in that order, whenever the creator is not a connected seated rider — logged disconnected, or never seated, as when the creator drives a TV from an unjoined page; in that case the creator and the rider in the lowest occupied seat both run `creatorDuties` and joiners send `join` to the rider); or, for `PRESENCE false` alone, from any ranked member — a rider or a watcher — about someone ahead of it. When the creator has been silent for `CREATOR_SILENCE_MS` = 5000 ms and this rider is the first in the order still heard within `DISCONNECT_MS`, it marks absent everyone ahead of it that is connected and silent for five seconds (`actingCreatorDuties`). Silence is `RoomRuntime.silent` here too, so a rider whose page has just loaded does not judge the riders ahead of it before it could have heard them: five seconds from their link coming up, and no later than `LINK_WAIT_MS` + `CREATOR_SILENCE_MS` = 10 s after it learned of them and had a world. (A rider whose links are that slow has usually been logged absent by the acting creator meanwhile, and an unranked rider judges nobody.) A member with no record at all (the service reports it offline) is silent at once, as before. Delegation is re-evaluated per entry, so a seated creator's own return revokes it (`applyTick`).

`actingCreator` reads presence through `memberConnected`, which looks in the seats and in the watching list, so a creator that watches its own room is present and keeps the crown alone; the case below is a creator with no record of either kind.

A creator that never takes a seat and never joins the watching list has no record at all, so `actingCreator` names the connected rider in the lowest occupied seat for as long as that lasts. `RoomRuntime.manager` is then true on two members at once: the creator (always) and that rider. Both log presence and leaves, each tracking only its own pending seat claims (`RoomRuntime.pending`); `RoomRuntime.managerId` sends a joiner's `join` to the creator until the joiner holds a world and to the rider afterwards; and `permitted` accepts every management kind from that rider's stream. Its silence-based duties (`actingCreatorDuties`) stay idle while the creator is heard.

The acting creator carries the log duties — joins, presence, leaves — and the room commands with them: `RoomRuntime.command` gates settings, start/rematch/lobby, bot changes and `kick` on `RoomRuntime.managing`, which is true on the creator's own page and on the member `roomManager` names — the creator while the room counts it present, otherwise the acting creator. The fold already accepted every management kind from either (`permitted`), so this is a gate change rather than a protocol one. `roomManager` is deliberately the log's own answer and nothing more: any rule that kept the crown on a creator the room has no record of would also keep it on one that has left, and a room whose crown sits on a member no device answers for could not be started, rematched or emptied by anyone. The price is that beside a creator that took no seat the first rider wears the badge and holds the controls as well, which is exactly what `permitted` has always allowed it there.

The frame carries `managerId` so every screen names the same host and shows that member's row a `HOST` badge (a word, not a crown: 👑 already marks the round leader in the standings); the manager's controls follow it, except that the creator's own page keeps them regardless. This is delegation, not transfer: the creator's token still owns the room code, the reserved seat and the only `END ROOM` capability in the room service, so the crown goes back the moment the creator is a connected member again. Rounds still progress on their own inside a match (`applyTick`).

**Kick.** `RoomCommand` `{ type: "kick", id }` is the manager appending an ordinary `LEAVE` for a human member, plus a direct `{ type: "kicked" }` message so the target's own screen says why its seat went. No new entry kind and no fold change: `LEAVE` already frees a seat in a `reclaimable` phase and a watching place in any phase. A rider is therefore kickable between rounds only, the same rule as removing an AI rider and for a sharper reason — outside a `reclaimable` phase `LEAVE` only marks a rider absent, and the manager's own presence duties log it present again as soon as they hear it (`creatorDuties`, `ensurePresence`), so the kick would undo itself. The phase is checked against the fold while the entry is stamped a tick or more ahead, so a kick issued at the very end of a pause can still land inside the round that follows; the manager therefore reads the outcome back from the fold (`RoomRuntime.settleKick`) instead of assuming it, tells the target only once it is actually gone, and says "that rider is in the round" when the entry did not take. Re-entry is allowed: the kicked device stays in the mesh as a viewer, exactly like a member that has not taken a seat yet. Service-level eviction, a ban list and room passwords are not part of it.

### 10. `RULES`

`RULES` names the simulation rules; see `RULES` in `games/fuse-riders/src/engine/apply-tick.ts` for the current value. It changes with every simulation change, so it is neither quoted here nor in the checked table. It travels in `hello` and in every snapshot chunk and payload; per-tick packets do not carry it.

A `hello` with different `RULES` marks its sender refused until a matching `hello` arrives (`RoomRuntime.message`). From a refused member nothing but a `hello` is read: its per-tick packets and NACKs are dropped before last-heard, the clock or a stream sees them (`RoomRuntime.fast`), its `join` is answered with an `error` and not seated, its snapshot requests are not served and its chunks not assembled. To a refused member nothing is sent on the unreliable channel (`RoomRuntime.sendPackets`), it is never asked for a snapshot (`RoomRuntime.compatible`), and no `join` goes to a manager this replica has refused (`RoomRuntime.sendJoin`). A snapshot chunk or payload with different `RULES` is refused as before (`SnapshotAssembler.accept`, `decodeSnapshot`).

The silence matters for tabs that predate the refusal. A creator that reloads onto later rules has nobody compatible to ask, opens its own world (§7) and would otherwise send packets under the same room hash: an old tab still takes the creator for its time authority, would sample a clock near tick 0 and be handed entries it can only call `unrepairable`. Hearing nothing, the old room succeeds the creator after `CREATOR_SILENCE_MS` and plays on. When both sides run the refusal the outcome is a version partition: two worlds under one room code, neither folding the other, until the stale pages reload.

The status names the side that is behind, by the number in `fuse-p2p-N` (`rulesAge` in `packages/fuse-netcode/src/room-runtime.ts`, `RULES_MISMATCH` in `games/fuse-riders/src/online/fuse-game.ts`), as one verdict over every refused member whatever order they arrived in: any build ahead of this page makes this page the stale one ("This page is out of date — reload this page"); a current page with a world gets a passing notice that a rider is on an older version; a current page that can get no world because the room is older is told to start a new room. The stale and older-room lines stay up as the recurring status while the page has no world. Only the stale page's line carries "reload this page", which `games/fuse-riders/src/online/status-copy.ts` turns into the reload button; "start a new room" is an actionable phrase there and in `games/fuse-riders/src/online/connect-hint.ts` so the boot card shows that line instead of its network hint. `hello` is a claim, not proof: this keeps an honest stale build out of the fold, not a modified client.

### 11. Game speed when only AI survive

`stepsPerTick` (`games/fuse-riders/src/engine/tuning.ts`) returns `BOTS_ONLY_STEPS_PER_TICK` = 3 while a round is playing, at least one human is seated, every human is dead and a bot is alive; otherwise 1. `applyTick` evaluates it once per log tick on the state the previous tick left, before the tick's entries, and `driveGameTick` runs that many `step`s inside the one log tick: the first with the tick's inputs, each later one with the riders' held controls (no bomb commands) and the bots asked again, and only while the round is still playing. The clock, the log, the packet cadence and every tick-denominated bound are unchanged; only the game's own clock (`game.tick`) advances three steps per log tick. `RoomState.tick` counts log ticks apart from it: entries, snapshots, rollback, the stall rule, the hash and `completeTick()` count in log ticks, and everything inside the game (phase ends, fuses, statistics, moments) in game ticks. Presentation interpolates between two frames one log tick apart, which in the fast phase are three game ticks apart, so the game looks three times as fast.

Because the count is a pure function of folded state, every replica takes the same count at the same log tick, a rollback that changes whether a human is alive re-simulates the ticks after it with the right count, and a hidden member needs no estimate of anyone's pace. `games/fuse-riders/tests/fixed-clock-game-speed.test.ts` covers a late human input that keeps a rider alive across the boundary on every replica. Design note: `docs/design/fixed-clock-game-speed.md`. Before `fuse-p2p-38` the speed-up changed the shared clock's rate from each member's speculative world, with packet-rate heuristics for hidden members (#258 N2); that is gone.

### 12. Hidden tabs

`RoomRuntime.visibilityChanged` runs on `visibilitychange`.

- **On hide**, a seated member appends `STEER 0` if it held a turn and `CANCEL` for an active gesture, so a held charge never fires. Solo then folds those entries, pauses the clock and publishes; time spent hidden is removed on resume.
- **While hidden online**, `tickLoop` runs whenever the browser fires its timer. It still raises the member's own `through`, sends its packets and runs creator or acting-creator duties, and received packets are still validated and stored. Its hellos, tick-loop NACKs and snapshot requests stop about 600 ms after hiding, because they need `transport.linked(id)`, which lapses with link health (below); only the NACK sent from the receive path (`RoomRuntime.fast`) still leaves. It does **not** advance the world, and `RoomRuntime.input` refuses commands.
- **On show**, solo resumes its clock. An online member whose backlog is more than `BEHIND_STEPS` estimated steps requests a snapshot; otherwise it catches up at `CATCHUP_STEPS` per loop interval. A rollback's owed re-run finishes while hidden (it is history the world had reached); new ticks wait.

In the transport, `PeerTransport.checkLinks` returns early while `document.hidden`: a hidden page sends no link probes and starts no ICE restart, so its own `LinkHealth` lapses, `linked()` turns false and `send()` refuses reliable messages. A hidden member therefore sends no `hello`, `join` or snapshot, although it still answers the other side's probes (the pong is deferred through a `MessageChannel`, which background timer throttling does not delay) and still sends per-tick packets, because `sendFast` does not consult link health. The transport's own visibility handler invalidates the authority-lease clock and samples service time on return.

On `pagehide` the runtime stops; a page restored from the back/forward cache reloads instead of reviving (`packages/fuse-network-fe/src/room-lifecycle.ts` `installRoomLifecycle`).

Browser timer throttling of hidden tabs is not modelled anywhere: `games/fuse-riders/tests/fixtures/fake-room.ts` `FakeNetwork.step` runs every runtime every 10 ms, hidden or not.

### 13. Transport

`PeerTransport` builds a full mesh: one `RTCPeerConnection` per member pair, negotiated through the room service; the member with the smaller id offers and owns any ICE restart (`initiator`). Each link has two data channels:

| Channel | Options                               | Carries                                                                                                                                           |
| ------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `game`  | default: reliable, ordered            | JSON envelopes `{id, data, sender, receiver}`: `hello`, `join`, `snapshotRequest`, `noWorld`, `snapshot`, `error`, and the transport's own probes |
| `input` | `ordered: false`, `maxRetransmits: 0` | binary per-tick packets and NACKs                                                                                                                 |

`sendFast` skips a send once `FAST_BUFFER_LIMIT` bytes are queued ("a stale packet is worse than none"). `send` refuses above `GAMEPLAY_BUFFER_LIMIT`, or above `SNAPSHOT_BUFFER_LIMIT` for snapshot chunks, and requires a healthy link.

Link health is path-specific: `checkLinks` probes every 200 ms on the `game` channel; two consecutive acknowledgements, each within 600 ms, make a link healthy (`packages/fuse-network-fe/src/link-health.ts` `LinkHealth`). After 8 s of continuous ill health the initiator restarts ICE on the same connection, at most four times per link with the budget restored by fresh health (`link-restart.ts` `LinkRestartPolicy`). A link opening is only a hint, so the runtime retries hellos, joins and snapshot requests from its tick loop.

WebKit/libwebrtc workarounds, in summary: a monotonic per-link send gate that drains on the first closing signal, because WebKit reports a dead channel as open for a task hop and fails the send as a console error rather than an exception (`link-send-gate.ts` `LinkSendGate`); `sendFast` also checking the peer connection state; the probe pong deferred by one macrotask so a queued closing state change runs first; a `linkBye` farewell with a 150 ms grace when a page leaves on purpose; a restart recognised by its unchanged DTLS fingerprint, with a drained link replaced instead of restarted (`ice-signal.ts` `sameCertificate`); and early trickle candidates buffered per link (`remote-signal.ts` `RemoteSignal`).

ICE is STUN only: `DEFAULT_ICE_SERVERS` (`packages/fuse-network-protocol/src/ice-servers.ts`) lists two STUN hosts, the service's `/ice` route returns the same list with `relayConfigured: false`, the fetch is bounded by `ICE_FETCH_TIMEOUT_MS`, and `parseIceServers` drops any URL that is not `stun:` or `stuns:`. There is no TURN and no gameplay relay: two members that cannot reach each other directly do not get a link.

### 14. Trust model

Every member is trusted with the shared log (`AGENTS.md`). The mechanisms below bound accidents and malformed input; they are not cheat resistance.

- **Sender identity is bound to the link.** A member's connection is negotiated through the service for one member id and connection id, and DTLS secures it. `RoomRuntime.fast` drops a packet or NACK whose `room` or `from` differs from the link it arrived on, so a member can write only its own stream. Reliable envelopes are checked against the service-issued connection ids and de-duplicated (`PeerTransport.receive`).
- **Whole-packet rejection.** `StreamLog.receive` validates every entry before changing anything; a rejected packet changes no stream or world state beyond the `ahead` flag (§6). `RoomRuntime.fast` has by then already taken the sender's RTT, clock sample and generation from any well-formed packet for the right room and link from a member it has not refused; whether the packet also counts as hearing its sender depends on the refusal (§9).
- **Bounded decoding.** `decodePacket` applies the byte cap and then MessagePack limits (strings ≤ 128, arrays ≤ 16, maps ≤ 32, no binary or extension types). Snapshots go through `unpackMessage`, whose `preflight` walks the bytes before anything is allocated (depth ≤ 32, ≤ 200,000 nodes, arrays ≤ 4,096, maps ≤ 64, ≤ `MAX_MESSAGE_BYTES`).
- **Snapshots validate before install**, exhaustively (§7), and a rejected one leaves the healthy world untouched.
- **Declared completeness is held to.** A member cannot land a new entry in a tick it already declared complete (§6), so `completeTick()` is not falsifiable by its own subject. A member can still withhold an announced seq.
- **Scope.** Packets carry the room hash; stale generations are dropped; events carry match, round and tick.
- What a member may write in its own stream is limited only by `permitted`, which trusts any ranked member's claim that someone ahead of it is absent (see presence forgery below).

### Couplings

These are the relations the code establishes. The test asserts the ones marked ✔.

- **C1 — rollback reach.** `STALL_TICKS` is defined as `ROLLBACK_TICKS` ✔: speculating further past a rider than the rollback window would turn that rider's late entry into an unrepairable one. `RETAINED_TICKS` has the same value but is not linked: resending an entry older than `ROLLBACK_TICKS` is useless, because the receiver would find it unrepairable. A stream first seen from a hello or a packet is based at `world.tick − STALL_TICKS` (`RoomRuntime.ensureStream`).
- **C2 — the snapshot ring must cover the rollback window.** With world tick W, `StreamLog.receive` accepts a late entry only at tick W − `ROLLBACK_TICKS` + 1 or later, and `World.rollback` needs a retained snapshot strictly before it, so at or before W − `ROLLBACK_TICKS`. The oldest retained snapshot is at `floor(W / SNAPSHOT_INTERVAL) × SNAPSHOT_INTERVAL − SNAPSHOT_INTERVAL × (SNAPSHOTS_RETAINED − 1)`, which is latest when W is a multiple of the interval, so the condition is `SNAPSHOT_INTERVAL × (SNAPSHOTS_RETAINED − 1) ≥ ROLLBACK_TICKS`: 44 ≥ 40 ✔. The margin is one snapshot (4 ticks): 11 retained would still cover the window, 10 would not. Nothing in the source asserts this.
- **C3 — hashes exist only at retained snapshot ticks.** `World.hashAt` reads the ring, so `HASH_INTERVAL` and `HASH_LAG` must both be multiples of `SNAPSHOT_INTERVAL` ✔, and `HASH_LAG` must lie inside the ring ✔. With world tick W the oldest retained snapshot is `floor(W / 4) × 4 − 44`, so a hash for tick H can be checked only while W ≤ H + 47. The authority sends it at clock tick H + 40, leaving 7 ticks — 350 ms at every game speed — for one-way delay plus clock offset. Beyond that the comparison is skipped without a trace (N6).
- **C4 — one cap, three constants.** `MAX_PACKET_ENTRIES` = `PACKET_ENTRIES` ✔ and `DEFAULT_MAX_FAST_BYTES` = `MAX_PACKET_BYTES` ✔ are separate constants with equal values; `ui.ts` also passes `MAX_PACKET_BYTES` to the transport. The byte cap was raised from 512 so SETTINGS entries fit (brief, review fixes of 2026-09-16).
- **C5 — tick bounds are wall-clock bounds.** `TICK_MS × TICK_HZ = 1000` ✔. The clock has one rate (§4, §11), so every tick bound means the same wall time in every phase: `STALL_TICKS` is 2000 ms, above `DISCONNECT_MS` 1000 ms ✔, and a silent rider is logged absent before anyone stalls on it, bots-only endgame included. (Before `fuse-p2p-38`, the 3× clock shrank `STALL_TICKS` to about 667 ms, below `DISCONNECT_MS`, and `ROLLBACK_TICKS`, `RETAINED_TICKS` and the C3 margin with it.) The fast phase costs CPU instead: a log tick there is `BOTS_ONLY_STEPS_PER_TICK` steps. The bounds that exist for correctness stay in log ticks (a rollback must still reach back `ROLLBACK_TICKS`), and the ones that exist to bound work are in steps (C8), so the work per loop interval and the snapshot threshold cost the same CPU in every phase. `MAX_STEPS_PER_TICK` = `BOTS_ONLY_STEPS_PER_TICK` ✔ ≤ `CATCHUP_STEPS` ✔, so a fast log tick always fits in one budget window.
- **C6 — the liveness ladder**, in wall time: `LAG_INDICATOR_MS` 250 < link-probe acknowledgement 600 < `DISCONNECT_MS` 1000 < `STALLED_GAP_MS` 1500 < `STALL_TICKS` 2000 = `SNAPSHOT_RETRY_MS` 2000 < `CREATOR_SILENCE_MS` 5000 = `LINK_WAIT_MS` 5000 < ICE restart 8000 < `WINDOW_GRACE_MS` 10000 < `CONNECTION_TTL_MS` 30000 < `ROOM_TTL_MS` 90000. A silent creator stalls its peers after `STALL_TICKS` and is not logged absent until `CREATOR_SILENCE_MS`, so at 1× the room waits about three seconds. `LINK_WAIT_MS` 5000 sits beside `CREATOR_SILENCE_MS`: both are how long one side waits for the other before judging it gone, so a rider that died while the creator was reloading, and that the service still lists, holds the creator's replica for at most that long after the creator's new page learned of it and recovered the world; it is below the ICE restart, so a link that needs one is logged absent first and present again on its first packet. A link just up holds off `PRESENCE false` for one `DISCONNECT_MS`, which must stay below `STALL_TICKS` ✔ so that it never stalls anyone by itself (§9). The graces chain additively and stay bounded: a member never heard whose link comes up at the end of the link wait and whose packets are then all refused as outside the window is logged absent `LINK_WAIT_MS` + `WINDOW_GRACE_MS` + `DISCONNECT_MS` = 16 s after the runtime learned of it and had a world (plus one packet interval), against about 11 s before the link wait existed; the entry is one log entry, so every replica drops the seat at the same tick (`games/fuse-riders/tests/reload-presence.test.ts`). The runtime reads two liveness signals: the per-tick packet, whose only sender is the tick loop, and the service's `peer` offline event, which the manager logs as `LEAVE` in the lobby and as `PRESENCE false` during a match (§9). A packet refused as a `violation` is not the first signal; one refused as outside the receiver's `window` is, for `WINDOW_GRACE_MS`, which must hold a stalled-gap wait plus a snapshot retry (`STALLED_GAP_MS` + `SNAPSHOT_RETRY_MS`) ✔ so that an honest out-of-reach stream resyncs before its owner is logged absent; past it the `ahead` resync continues at one request per `WINDOW_GRACE_MS`.
- **C7 — clock convergence.** A follower within `SNAP_TICKS` of the authority slews at `SLEW_TICKS_PER_SECOND`, so it can stamp entries up to 200 ticks off for minutes. `FUTURE_TICKS` must exceed `SNAP_TICKS` ✔ or such a peer's entries would be rejected as too far ahead.
- **C8 — catch-up against resync, in steps.** A step is what costs CPU (with bots seated, `BotController.input` per bot per step dominates: about 6–8 ms per step with four bots on the developer's Mac, #349's review and `scripts/bench-catchup.ts`), and a fast log tick is `BOTS_ONLY_STEPS_PER_TICK` of them. So both limits count steps. `CATCHUP_STEPS` = 8 is one budget window per 10 ms loop interval, shared by the loop's catch-up and by rollback re-runs in packet handlers (`World.refill` after every pass); a log tick starts only if its steps fit, and only while the window's steps have taken less than `CATCHUP_MS` = 6 ms between them (idle time between a packet handler's re-run and the loop pass does not count), except the first of a window, so a device too slow for eight steps a pass still paints between passes instead of running 100–200 ms passes. At 1× that is the 8 ticks per pass it always was; in the fast phase it is 2 log ticks (6 steps), where counting log ticks ran 24. A rollback's re-run is split across windows the same way (§6), and a burst of late packets re-runs once, not once per packet. `BEHIND_STEPS` = 400 keeps the snapshot threshold at the CPU cost it had when a tick was a step: 400 log ticks (20 s) at 1×, 133 in the fast phase (6.7 s, what the 3× clock gave before `fuse-p2p-38`); counting log ticks would have let a fast backlog cost 1,200 steps (7–10 s of CPU here, seconds more on a phone) before resyncing. The estimate uses the step count of the world's current state, so a backlog that crosses a phase change is misjudged by at most that factor. At 8 steps per 10 ms a backlog just under `BEHIND_STEPS` takes at least 0.5 s of loop passes, and in practice as long as the CPU needs (below one pass per 10 ms whenever a pass runs longer). `BEHIND_STEPS` and `FUTURE_TICKS` share a value but nothing links them; the choice of 400 is not recorded.
- **C9 — snapshot sizes.** `MAX_SNAPSHOT_BYTES`, `MAX_MESSAGE_BYTES` and `MAX_CHECKPOINT_BYTES` are three unlinked constants with one value. `SNAPSHOT_BUFFER_LIMIT` must exceed the base64 of a full snapshot (`MAX_SNAPSHOT_BYTES × 4 / 3`, about 2.67 MB) ✔ or serving stops midway; a chunk (about 21,334 characters plus its envelope) must stay under the transport's 200,000-character reliable frame cap, which is an unexported literal and so is not asserted. `SnapshotAssembler` refuses a transfer whose declared chunks exceed `MAX_SNAPSHOT_BYTES × 1.4`.
- **C10 — retired.** The clock-rate heuristics it described (`RATE_WINDOW_MS`, `RATE_DEFER_MS`, the rate classifier) were deleted with N2 in `fuse-p2p-38`.
- **C11 — divergence.** Each mismatch below `DIVERGENCE_LIMIT` costs one snapshot transfer; hashes arrive at most every `HASH_INTERVAL` ticks (1 s).
- **C12 — service lifetimes.** Heartbeat 2 s against `CONNECTION_TTL_MS` 30 s against `ROOM_TTL_MS` 90 s (= `ROOM_RECONNECT_GRACE_MS` ✔) against `LEASE_MS` 10 s. The heartbeat is a page timer.
- **C13 — the seq bound.** `SEQ_AHEAD` is defined as `BUFFERED_ENTRIES` × 16 ✔. It must exceed `RETAINED_ENTRIES` ✔, or a gap a NACK could still repair would be refused as out of reach, and be at least `BUFFERED_ENTRIES` ✔, or the buffer limit could never be the binding one. An honest rider logs tens of entries a second, so 4096 is minutes of input nobody heard.

## Consequences

**What this buys.** No simulation server and no gameplay traffic through the service: hosting cost is signalling and room metadata. A member's own input applies on the next tick; another member's one network hop later. There is one log, one steady packet and one runtime for solo and online play. Any member can serve the world, so a reload — the creator's included — recovers the running match from a peer, and nothing is persisted. Gameplay packets follow the ICE candidate path, which for players on one LAN is normally that LAN (ADR 035: the application cannot guarantee it). The brief's §15 records measured per-link traffic of about 3–3.6 kB/s on one machine.

**Known limitations.** These describe `main`. The issues hold proposed directions; none is decided here.

- **N2 — resolved** ([#258](https://github.com/andeplane/fuse-riders/issues/258), `fuse-p2p-38`). Game speed is steps per log tick decided from folded state (§11); the clock never changes rate.
- **N3 — a partially connected mesh deadlocks** (#258). Packets carry only the sender's own entries, nobody forwards, and there is no TURN. If A and B cannot link while both link to the creator, A never receives B's entries: it stalls on B at `STALL_TICKS`, and the creator, which hears B, never logs B absent.
- **N4 — hidden-tab timer throttling is unmodelled** (#258; unverified on devices). The tick loop is the only sender, and browsers throttle a hidden page's timers. `FakeNetwork` ticks hidden runtimes every 10 ms, so no test exercises this. At one pass per second a hidden member sits at the `DISCONNECT_MS` boundary, and one packet spans about 20 ticks, half of `STALL_TICKS` (60 ticks, more than `STALL_TICKS`, while the clock still ran at 3×). A hidden member also cannot serve snapshots (§12). A reproducer — not a fix — is on branch `codex/arch-hidden-policy` (`docs/reviews/hidden-tabs-reproduction-wip.md`).
- **N5 — host migration is partial** (#258; owner decision). Since #262 a room outlives its creator for as long as any member renews it, and succession now covers the room commands as well as the log duties: the member `roomManager` names — the acting creator, once the creator is not a connected member — starts, rematches, returns to the lobby, changes settings, manages bots and kicks (§9). What has not moved is ownership — the creator's token still holds the room code, its reserved seat and the only `END ROOM` capability — so this is delegation that the creator's return revokes, not migration. A creator that means to leave for good has no way to hand the room over permanently. Observed on `main`: when the creator is not seated (it drives a TV from an unjoined page), the room has two managers at once — the creator and the connected rider in the first occupied seat both run `creatorDuties`, joiners send `join` to the creator and then to the rider, and every management kind from that rider's stream is permitted (§9). Elections are local: each replica picks the time authority and decides to act as creator from its own silence timers, so two sides of a partition can elect differently and log conflicting presence. A member with no world in a room whose creator is gone and whose peers hold no world waits indefinitely, because only a creator opens a fresh world (§7).
- **N6 — desync is hard to diagnose in the field** (#258). The check is skipped silently beyond the C3 margin, whenever any stream has a gap, and past `completeTick()`. A mismatch leaves two hashes in `console.warn` and nothing else; telemetry is off in production unless `?telemetry=1` (`games/fuse-riders/src/online/telemetry.ts` `telemetryEndpoint`). `World.install` clears the emitted-event keys, so a resync can re-emit sounds, analytics and moments for ticks still in the replayed window. `outOfSync` is never cleared and the replica keeps simulating.
- **N7 — ingest hardening** (#258). Closed: a new entry inside a tick its owner declared complete is refused (§6); an inflated `lastSeq` opens no gap and costs each replica one snapshot request per `STALLED_GAP_MS` for `WINDOW_GRACE_MS`, then one per `WINDOW_GRACE_MS`, while the room plays on without its sender (§6, §7, §9); a `RULES`-mismatched peer is neither folded, seated, served nor sent packets (§10); a member sending only packets no unmodified client sends is logged absent like a silent one (§9). Still open: a member that announces a seq and never delivers it holds a real gap open, which pauses hash comparison and resyncs every replica each `STALLED_GAP_MS` — closing that needs a rule for abandoning an unrepairable gap, which belongs with N3; `actingCreatorDuties` has no equivalent of `creatorDuties`' guard against its own stalled loop (that guard covers one loop pass; what a throttled hidden page may judge is N4's question, and who may open succession is N5's), and a creator whose packets are refused as violations, or as outside the window for longer than the grace, now looks silent to it; and presence forgery, below. A refusal judged from what each replica received can differ between replicas only when a member sends them different packets, which the trust model (§14) already allows; the desync hash (§8) is the backstop.
- **A manager's own socket reconnect logs everyone absent** (#258; open, also true before the link-wait rule). When a member's room socket reconnects, its transport closes every RTC link and the new `welcome` announces every peer again (`PeerTransport`, the `welcome` handler). On the creator or acting creator each member record keeps its finite last-heard time, the links take longer than `DISCONNECT_MS` to come back, and every seated rider is logged absent a second after its last packet, then present again on its first packet over the new link; a round boundary or lobby reset in between prunes them. The own-loop stall guard does not cover it, and neither does `RoomRuntime.silent`, which starts a fresh wait only for a member it has never heard. #279's reconnect path and #307's no-close change make the reconnect rarer; they do not remove it.
- **Presence forgery** (#258 N7; open). `permitted` accepts `PRESENCE false` from any ranked member about anyone ahead of it and re-evaluates the order per entry, so one packet from the last member can mark everyone ahead absent, make its sender the acting creator and carry any management entry behind it in the same tick; with a `lobby` action the reset also drops everyone just marked absent. `games/fuse-riders/tests/net-hardening.test.ts` pins this under a `KNOWN GAP` title. When the creator is not seated, the lowest-id rider already holds that position with no forgery at all (§9). Absence is a local observation with no evidence in the log, so this belongs to the N5 decision. Spectators widen who can do it rather than changing what it is: the succession order now runs to ten members instead of five, and a watcher ranked last can forge its way to the front exactly as the last rider could. Nothing new is reachable — the same entries were already available to any admitted member that took a seat — but the population that can reach it is twice as large, which is another reason to settle N5.
- **No traversal of symmetric NAT or CGNAT** (ADR 035). Two members that cannot connect directly get an explicit failed-link status, not a relay; with N3 that stalls the room.

## Open owner decisions

- **N5 migration model** ([#258](https://github.com/andeplane/fuse-riders/issues/258)): real migration of the creator's role, or pause until the creator returns (which would let most of succession go). Presence forgery and partition elections hang on it.
- **S2 admission model** ([#256](https://github.com/andeplane/fuse-riders/issues/256), epic [#259](https://github.com/andeplane/fuse-riders/issues/259)): room codes are enumerable by design and every admitted member is a trusted mesh peer whose ICE candidates expose player addresses; whether an invite secret should gate admission is a product decision.

### Ready checks (#364)

Online lobby starts and rematches now follow unanimous connected-human readiness in the deterministic room fold. `READY` (kind 6) carries a boolean, match id and lobby/results phase, and uses its sender's ordinary generation-scoped stream. At least two connected riders are required, counting AI; bots, spectators and displays need no vote. The check runs after the tick's entries, consumes votes on start, and derives rematch ids deterministically. Settings and presence changes clear votes. Solo still uses ACTION start/rematch. This supersedes N5's host-only start/rematch UI limitation; the other management actions retain their ownership. See [ready-check design](../design/ready-check.md) for scopes and checkpoint validation.
