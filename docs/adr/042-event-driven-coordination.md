# ADR042: Event-driven actions with combined quiet-period coordination

Date: 2026-09-14. Status: accepted for implementation after independent review; runtime cutover is implemented with local regression and full-match evidence; sustained impairment and release acceptance remain pending. Extends ADR041 on branch `codex/deterministic-action-log`; tracking #82. No deployment authorization or release qualification.

## Problem and alternatives

Actions already send immediately, but steady 10 Hz cuts/receipts, 5 Hz link probes, 2 Hz clock probes and up-to-10 Hz finality undermine the intended event-driven architecture. The user explicitly wants changed controls, brief repair after loss, then roughly one heartbeat per second. A 20 Hz simulation does not imply a 20 Hz network schedule.

Merely increasing existing intervals is unsafe: the current 600 ms link freshness, 1 s clock freshness, 500 ms origin silence and 40-tick speculation bound depend on those intervals. Keeping independent low-frequency timers would also retain redundant packets. Replace them with one paired heartbeat exchange that combines exact input cuts, receipts, clock sampling and latest finality; retain immediate action/repair and demand-driven confirmation.

## Packet and ownership invariants

Actions remain absolute-tick MessagePack records in the existing <=512-byte fast packet. They send immediately on a real edge with recent unacknowledged records. Prepare a fresh exact current-tick cut with the whole local update before committing/submitting any bytes; never cover an already-issued future action. The action and cut candidates remain atomic across subscribers. Pending action repair remains at most every 50 ms and stops on receipt; an empty delivery queue has no periodic send timer. A duplicate action packet can elicit another receipt to repair ACK loss, but idle progress does not create a standalone receipt exchange.

New combined fast heartbeat tuples are `[1, alias, 10|11, id, acknowledgedReply, body]`:10=request,11=reply. Every endpoint owns a monotonic positive uint32 ID sequence scoped to the exact RTC association/segment; a reply's `acknowledgedReply` identifies the request it answers, while a request's field acknowledges the last accepted reply (zero before any reply). `body` is `[cuts, receipts, clockOrNull, finalityOrNull]`. Cuts are at most five unique `[slot, throughTick, sequence]` triples. Receipts are at most five unique `[slot, contiguousSequence]` pairs. Clock fields use the existing exact clock/time tuples; finality uses the existing exact certificate tuple. On a coordinator pair, the follower request contains a clock nonce equal to that heartbeat request ID, and the coordinator reply contains the same nonce as its acknowledged request ID. Accept it only against that peer's pending heartbeat attempt and pending clock sample. Non-coordinator pairs require a null clock field; finality can come only from the coordinator. The complete encoded message remains <=512 bytes. Reject malformed, oversized, foreign-alias, unauthorized-slot/role, stale and conflicting identity data before installing it or refreshing health. A cut is allowed only from that stream's immutable owner to a subscribed simulator; a receipt only from that owner's named subscriber. A heartbeat never proxies another player's actions or completeness.

One endpoint initiates a pair: the follower on a coordinator pair (so its request gets an immediate clock sample in the reply), otherwise the lower stable peer ID. Replies are immediate. Healthy requests occur once per 1000 ms; bootstrap clock qualification may request every 100 ms. An unanswered request may produce a fresh attempt at 250 ms, with at most eight outstanding IDs and 2.5 s retention; retries have new IDs and fresh clock samples, avoiding retransmission ambiguity. Duplicate/reordered replies cannot refresh health or consume actions twice. Old requests can be ignored; the initiator repairs a lost response with a fresh request. Sequence exhaustion requires a fresh scope. No response depends on the healthy-send gate: pulses retain the existing bounded probe escape path, while authority, visibility, channel state, drain and buffer gates still apply.

Pulse mode has an explicit local adapter flag, set only after the current segment is installed at activation, and a remote-proof flag, set only after the application accepts a current pulse on that exact association. Stop legacy probes only when both flags are true. Receiving a syntactically valid pulse before local activation cannot set remote proof. Bootstrap probes run at the existing 200 ms cadence only for the cross-channel/alias startup dependency, bounded by the existing 5 s setup/activation deadline; incomplete repeated attempts remain subject to the 15 s episode bound. Mode changes, pending IDs and receipt proof reset with connection/alias/epoch changes. Bidirectional health refreshes only when a newly accepted reply acknowledges a local request, or the next request acknowledges a locally sent reply; arbitrary incoming traffic and duplicate IDs do not prove outbound delivery. Switching to the2.5 s pulse freshness window preserves the timestamp of the last actual acknowledgement; it does not manufacture fresh evidence. Native channel/authority/visibility failure remains immediate and the existing8 s continuously-unhealthy restart policy remains separate.

### Freezing an installed segment

While either local or remote pause is latched, also send the existing association-scoped reliable JSON bootstrap probe, regardless of prior alias confirmation. The other endpoint may already have bound the new alias while this endpoint still needs healthy delivery to acknowledge its checkpoint header; an old-alias compact probe cannot break that dependency. Existing authenticated association envelopes, pending probe IDs, 200 ms pacing and setup/episode bounds apply. Fresh alias bindings resume ordinary confirmation rules. Independent review approved this extension after the mixed-browser `heartbeat-01` full-match run exposed the transition deadlock; that failed run remains evidence.

The startup bound applies to active segment preparation. A shared-screen lobby intentionally waiting for its TV has no installed segment and can retain legacy bootstrap probes indefinitely; the one-second steady cadence describes active segments, not this waiting state.

Freeze explicitly deactivates pulse participation for that alias before destroying the segment. Otherwise checkpoint preparation could outlast pulse freshness while no installed segment is generating heartbeats. The adapter resumes its existing 200 ms bootstrap schedule with pause probes `[1, alias, 12, probeId]`; the receiver echoes the existing `[1, alias, 9, probeId]` acknowledgement. The first valid current-association pause probe irreversibly latches remote pause for this alias and resumes ordinary bootstrap probes. Local pause and remote pause cannot be undone by delayed heartbeats or ordinary probe packets; only a new binding/alias resets them. Ordinary probes never imply a pause. Pause probes use the existing size, authority, reserved ingress, pending-ID and send gates, so rejected/lost sends retry on the same bounded bootstrap cadence without another timer. Actual acknowledgement age is retained across the switch; phase and overall recovery-episode deadlines remain unchanged. This explicit pause transition was independently reviewed before implementation.

## Clock and simulation bounds

Clock replies still require a pending nonce, <=500 ms round trip, monotonic accepted samples and explicit coordinator role. Retain samples for 2500 ms and add uncertainty for both in-flight duration and sample age under a documented supported relative oscillator drift budget of500 ppm (0.01 simulation ticks per second). Grow both interval radii used for best-sample/discrepancy decisions and the remembered uncertainty bound; expiration cannot make an uncertain clock usable again. Preserve the five-tick uncertainty cap, four-tick origin lead,14-tick remote future allowance, monotonic slew, pre-start coordinator confirmation and >1 s local observation-gap fault. A 500 ms sample exceeds the five-tick boundary once in-flight drift is included and cannot qualify play even on receipt. The drift budget needs physical-device qualification.

Keep the 40-tick execution cap,256-record/stream and32 MB encoded-memory limits. The one-second heartbeat is a healthy quiet cadence, not a ceiling during actions, loss, outcomes or endangered rollback headroom. Late actions still rollback inside the retained window; absence of a heartbeat is never interpreted as neutral input.

## Finality and confirmation

Publish cuts on first clock qualification, real action edges, pulse/reply and explicit demand. Coordinator finality is eligible immediately when a complete frontier advances at least 20 ticks since the last certificate, or on any positive progress while an outcome/headroom demand is pending. Piggyback an already-due pulse when possible; otherwise send a compact reliable certificate immediately. Do not wait another one-second phase after cuts become complete. Controllers retain only the certificate/status, not a world.

A new unfinalized simulation event (including deaths and phase transitions) requests confirmation immediately. A simulator nearing24 ticks beyond known finality requests it early; the coordinator asks owners for fresh exact cuts. Use exact compact reliable tuples `[1, alias, "settle", targetTick]` from a non-coordinator member to the coordinator and `[1, alias, "confirm", targetTick]` from the coordinator to an input owner. Admit only positive-progress uint32 targets above receiver finality, at most 40 ticks beyond it and at most 14 ticks beyond the receiver's current qualified clock. A simulator/controller can ask about its own endangered finality frontier; only the coordinator can request another player's cut. Retain one earliest unsatisfied target per requesting peer and one per origin owner (at most six/five); a newer target never postpones the existing target or its original deadline. On admission publish any currently available progress immediately, then complete the target once reachable. Enforce at most one admitted request per peer per 250 ms, including duplicate/newer targets. Outbound requests/responses share that pacing; never reset it on duplicate input. A demand expires after 1500 ms unless satisfied/replaced by a new scope, causing visible synchronization failure rather than silent disposal/recreation; earlier execution-cap failure remains possible. Owners respond with a current exact cut, to their subscribers, once their qualified clock reaches the target; future targets must be within the existing clock/future bounds. Missing actions remain gaps and use normal repair; a confirmation request cannot authorize missing input or bypass finality validation. Duplicate demands do not flood extra responses or move deadlines. Finality/new scope retires satisfied demands.

The24-tick trigger reserves 16 ticks before the hard cap; it is an operating choice, not a proof of uninterrupted play at every permitted500 ms RTT/opposite-clock-error combination. This first implementation uses the fixed 24-tick trigger and fails visibly at the unchanged cap if the available reserve is inadequate. Adaptive earlier demand based on conservative delay bounds is deferred, not implicitly implemented. The first complete cut has a 1500 ms grace after the observer/coordinator's own clock qualification (remote qualification is not an authenticated observable event); thereafter an origin must advance its cut within 2500 ms. New request IDs with unchanged cuts do not refresh that progress deadline. Urgent certificates are capped at one new frontier per 50 ms, with one coalesced pending certificate per peer and failed-enqueue retries no more often than 250 ms. Ordinary certificates still need 20 ticks of frontier advancement. A one-sided blackhole, lost last release, unavailable coordinator or exhausted bound must still pause explicitly. Do not erase a failed performance profile by widening bounds silently.

## Acceptance and rollout

1. Independent review before implementation; final source review before any release. Bump direct protocol rules on runtime cutover so old clients fail explicitly; no permanent compatibility mode.
2. Serialized boundary tests for pulse role election, exact shapes and byte caps, unauthorized slot/clock/finality fields, reply and responder acknowledgements, loss/reorder/duplicate IDs, stale epoch/association, exhausted sequences, bounded retries and no empty action-queue timer.
3. Deterministic six-world tests with five independent origins, held/released/cancelled inputs, continuously changing aim, clock skew/uncertainty, opposite delays, last-packet loss and one-sided failures. Compare final world/outcome hashes and ensure committed effects emit once.
4. Quiet fixed-input gameplay must show approximately one elected request/reply exchange per pair per second, no separate steady cut/receipt/liveness/clock loops, and bounded occasional certificate/demand traffic. Count messages as well as bytes by class; bootstrap, action/repair, outcome and failure bursts are separate windows.
5. Actual mixed Chromium/WebKit full-match and shared-TV/reconnect browser tests, plus meaningful input-to-render/finality, rollback/frame/memory measurements and sustained impairment acceptance. Preserve all failed runs and exact source/bundle identity. Match traffic workloads before asserting a reduction percentage; wire headers and physical phones remain separate evidence.


## Behind-peer progress repair (independently approved bounded correction)

A participant's settle target may already be finalized by the coordinator while that participant still lacks another origin's completeness cut. Local finality is not proof of delivery to every view. Continue authenticating/rate-limiting requests and enforcing the current alias, target above the segment base, qualified clock, future envelope and 40-tick upper bound. For a valid settle target at/below coordinator finality, resend the latest certificate to the requesting peer and request fresh cuts from all origins, including publishing the coordinator's own cuts. A valid confirm target at/below an origin's local finality must publish its current complete cut rather than being discarded. No authoritative watermark is invented or relayed on behalf of another origin.

Use existing `settle`/`confirm` messages and per-peer 250 ms admission limits. Coalesce emitted work with the same per-origin/self confirmation gates across requesters and both paths; retain the last per-recipient certificate tick, attempt time and enqueue outcome. Duplicate certificate repair and failed enqueue retries share the 250 ms gate; a genuinely newer frontier after successful enqueue retains the existing 50 ms urgent publication cadence. At most one own-cut fanout and one confirm per origin are attempted per 250 ms. Duplicate requests never reset these timestamps; a repeated request retries failed enqueue. Do not move finality, widen speculation, extend the 1,500 ms confirmation deadline or change quiet heartbeat cadence. Requests above local finality retain the existing pending-demand behavior. Regressions must cover an already-finalized target, lost quiet-heartbeat progress with working direct repair, rate/role/scope rejection, and successful versus unavailable recovery.
