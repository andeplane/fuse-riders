# ADR 041: Direct player actions and continuous world rollback

Date: 2026-09-14. Status: core contract and initial core implementation independently approved; runtime integration remains in progress. Reviews: [design](../reviews/direct-actions-design-review.md), [core implementation](../reviews/direct-actions-core-review.md). Tracking: [#82](https://github.com/andeplane/fuse-riders/issues/82).

## Decision and scope

Replace the online host-star snapshot/replay path with direct player-owned input streams. Every full view continuously runs the shared deterministic simulation. An input origin immediately applies its own action and sends the same MessagePack record to every subscribed simulator, without coordinator admission or forwarding. Controller-only phones own input streams without retaining the world. A full-view coordinator owns setup, lifecycle barriers, finality and recovery. Keep LAN unchanged. The prototype toggle is a development artifact to remove when the replacement is integrated, not a permanent product mode.

This explicitly supersedes ADR028's star topology and ADR029's rejection of whole-world speculation for the new online protocol. It replaces ADR030/040's routine reliable host world stream. The existing accepted lease fences, validated boundaries, signalling-only services, deterministic math and presentation-only renderer remain. Shared outcomes have one finalized history even though all views compute provisional outcomes. There is no per-action coordinator hop.

Alternatives: retaining the current prototype leaves both a relay hop and a wait for accepted batches; binary snapshots still send world growth; input-delayed lockstep saves bandwidth but stalls on the slowest stream; a dedicated simulation server changes cost/hosting requirements. Select direct streams with bounded rollback for this trusted-friends, five-player product. Full mesh is ten links for five players, fifteen with a TV; controllers subscribe only to simulators. No new paid service, TURN or gameplay backend relay.

## Deterministic stream contract

Bootstrap binds protocol/rules version, room incarnation and authority epoch, a fresh segment ID, match/round, initial game/held state, stream IDs and immutable player-slot/connection owners. A segment has a frozen roster; scopes are never inferred from packet arrival. Bind a compact non-reused uint32 segment alias on each authenticated RTC connection before accepting compact packets. Old connections and aliases cannot submit actions into a new segment. Reaching alias/sequence/tick exhaustion requires a fresh bootstrap, never wrapping integers.

Each player stream starts at sequence 1. Action ticks are absolute simulation ticks, monotonically nondecreasing within that stream. Multiple actions on one tick keep sequence order. Tuples:

```text
[sequence, absoluteTick, 0, steeringFlags]      // bits left=1, right=2
[sequence, absoluteTick, 1, gesture]            // press
[sequence, absoluteTick, 2, gesture, aimOrNull] // release
[sequence, absoluteTick, 3, gesture]            // cancel
[sequence, absoluteTick, 4, aimOrNull]          // public simulation aim update
```

Sequence, tick and gesture are uint32; gesture IDs start at 1 and strictly increase on press. A press cancels/replaces any older gesture by emitting cancel then press into the shared reducer; a bare press would preserve the existing charge timer. Release/cancel affects only the matching active gesture; a missing or old gesture is a deterministic no-op. A release never invents a press. Aim is null or the existing finite normalized coordinate pair, with negative zero normalized by the origin and rejected at ingress. Preserve current target-marker semantics by recording aim changes; final release includes its target. No periodic aim record if unchanged. Bots have one designated owner, emit these same ordinary inputs, and are not rerun during rollback.

Per slot/tick there are at most 256 actions (the stream retention cap) and 512 derived bomb commands including replacements. The direct reducer applies this independently bounded list; it does not pass it through ADR040's smaller serialized operation validator. Each bomb command captures the aim at its own action position. The receiver validates packet shape, scope, ownership, tick/sequence bounds and immutable duplicate identity before mutation. Out-of-order stream suffixes are buffered; only the contiguous prefix enters simulation, so a release cannot execute before a missing press. Distinct streams may arrive in any order. At tick T fold each slot's actions in sequence order into held controls and ordered bomb commands, then call the existing shared turn-then-move game step once. Across players use the existing stable game player order. Arrival order never changes collisions, RNG consumption or same-tick targeting. Retain full held controls, active gesture and latest gesture ID in rollback snapshots.

Reviewed `fuse-direct-3` correction: after each direct simulation step whose resulting phase is not `playing`, clear every player's executable bomb charge and target while retaining stream held flags and gesture IDs. This includes the exact round/match-ending tick. The shared LAN step ignores bomb commands outside play; without direct-layer normalization, a later release clears the gesture but leaves an orphaned charge, making a finalized checkpoint unreadable. No LAN behavior changes. Before committing finality, require its reconstructed state and encoded checkpoint roundtrip to exist and preserve the certified replay hash; rejection must precede final tick mutation, snapshot trimming and event publication.

## Time, speculation and finality

Keep 20 Hz physics initially to preserve gameplay, with an independently scheduled monotonic tick clock and fractional presentation. Event sends do not wait for this clock's next network publication. Map local input to the next simulation tick at the input event, no earlier than the origin's last action tick or published completeness watermark plus one. Render a cosmetic fractional local preview while that tick is pending; measure whether a higher simulation rate is needed before changing all time-dependent rules.

The coordinator's clock probe binds tick/time to the current segment. Use bounded RTT samples, never Date.now in simulation; no more than one tick adjustment per second, and pause/rebootstrap on a >4-tick discrepancy, >1-second sample age during active controls, suspension or a clock jump. Full views advance independently between samples. Exact estimator and scheduler tests are required before runtime activation.

Each origin publishes `[throughTick, lastIssuedSequence]` at most every 100 ms (or piggybacks it). This is a promise never to issue another action through that tick. A receiver records it but cannot certify completeness until it possesses the named contiguous prefix. A strictly newer watermark must not decrease either coordinate; equal throughTick cannot change its sequence. Older watermarks dominated in both coordinates are stale no-ops. For every retained action, sequence <= lastIssuedSequence requires tick <= throughTick, and sequence > lastIssuedSequence requires tick > throughTick. Missing older records satisfying the promise remain admissible. Already-buffered later actions must obey the promise. Retain up to 64 exact watermark cuts within the unfinalized window and validate all retained cuts against existing/new actions. A later incomplete cut cannot erase previously proven completeness; a delayed older cut still constrains retained actions. Trim cuts at finality, retaining the applied baseline fence. A watermark cannot hide missing input, and an action conflicting with an already accepted promise is a stream fault, not a retimed input.

Coordinator finality includes a tick and the exact prefix sequence for every required stream, plus a canonical state hash at that tick. Each finality prefix is exactly the last action sequence at or before that tick, distinct from a later completeness watermark that can name actions after the finalized tick. Receivers advance finality only after possession/completeness and hash checks against their own reconstructed state. Finality arriving before fast records or local simulation progress is retained in a bounded per-tick certificate map: at most 40 distinct future ticks within finalized tick + 40. A newer incomplete certificate must not erase an earlier one that can become complete, which otherwise starves finality during continuous input. Validate every now-reconstructable complete certificate for exact prefix/hash agreement, reject conflicts at each retained tick (normalizing prefix pair order), then apply the highest valid complete certificate and prune all certificates at or below it. Include retained certificate bytes in the encoded storage budget; reject budget growth atomically. Ordinary cross-channel reordering is not a hash fault. Lost finality does not stall each gameplay tick: allow up to 40 speculative ticks (2 seconds) beyond local verified finality. At that bound visibly pause for recovery. Finalized ticks cannot be changed. Trim action identities at/below each finalized prefix and retain that prefix as a permanent segment fence; delayed duplicates below it are stale and never execute. New sequences at/before finalized time are faults. A conflict, action older than finality, exhausted history, hash mismatch or stream overflow requires bounded recovery, never silently dropping an input and continuing to claim agreement.

Retain a full rollback snapshot every five ticks, including one at finalized time when trimming. Restore the most recent snapshot strictly before the earliest newly admitted action, then replay to the current provisional tick. Bound the window to 40 ticks, encoded snapshots and logs to 32 MB (JavaScript heap overhead is measured separately), retained remote future actions to 14 ticks beyond the local target (the composed clock/issuance bound below), records to 256 per stream and 1,280 total, and advance calls to eight new ticks. Validate/replay into a temporary candidate before installation. If CPU/memory bounds cannot be met, pause and request a checkpoint. Measure replay CPU and memory with actual long-trail five-player worlds; these are limits, not proven mobile performance guarantees.

Provisional geometry and poses update immediately, while committed deaths/scores remain final. Retain derived events by tick and replace provisional events during rollback. Deliver irreversible audio/notices once on finalization with IDs `(segment,tick,eventIndex)`; speculative visual effects must be reversible and must not be rebroadcast as host events. Local control feedback can be immediate and cosmetic. Do not replay sounds for all resimulated ticks.

## Delivery and loss recovery

Use a separate RTC channel `{ordered:false,maxRetransmits:0}` for action/progress/receipt messages. Keep bootstrap, lifecycle/finality and checkpoint repair on a reliable channel, with explicit cross-channel dependencies. Compact fast packets are `[version, segmentAlias, streamSlot, records, watermarkOrNull]`; receipt tuples are `[version, segmentAlias, streamSlot, contiguousSequence]` (arity four versus five for actions). Reliable finality tuples are `[version, segmentAlias, "final", tick, slotPrefixPairs, hash]`. Each lane validates its exact shape before dispatch. The first implementation uses contiguous receipts and earliest-gap repair instead of a selective bitmap: with at most 256 retained records, a bitmap is optional optimization, not required for correctness. Never run the transport's old greatest-envelope-sequence rejection on unordered packets.

Reviewed compact liveness amendment: after alias binding, probe/pong tuples are `[version, segmentAlias, 8, probeId]` / `[version, segmentAlias, 9, probeId]`, distinct from receipt slots 0–4. Preserve the existing 200 ms probe cadence, 600 ms reply validity and two fresh replies for health; this is liveness, never a completeness promise. Probe sends bypass the healthy-link condition so an unhealthy link can recover, while retaining scope, channel/gate checks and the 4 KB probe backpressure budget. Defer pong one macrotask and recheck both received segment and captured RTC association before sending. Before binding use the existing authenticated reliable probes. After local binding, send both fast and reliable probes until a validated current-segment compact probe/pong proves the remote has bound the alias too; this readiness flag resets on alias/epoch/RTC replacement and does not itself establish link health. The initial browser test exposed a deadlock when locally bound peers switched too early, because their application handshake acknowledgement could still be health-gated. Retain this two-lane bootstrap until remote binding is confirmed; always answer a reliable probe on its reliable lane even if the local fast alias is already bound, avoiding asymmetric-handshake deadlock. Count control bytes separately when reporting payload classes; no repeated long-ID probe envelopes once both peers bind.

Send a new action group immediately, retaining its records first in the packet. Always include the earliest unacknowledged record unless already present, then rotate remaining repair slots across the retained suffix using stable sequence IDs. A lost or delayed receipt must not make every repair repeat the same earliest few records; acknowledgement and candidate queue copies preserve the rotation cursor. Keep at most four distinct records per packet. Retain all unacknowledged records separately for each subscriber until its receipt, within the shared bounds. Retry pending records every 50 ms even if no new input occurs. Repeat watermark/receipt at 100 ms while needed; no per-tick unchanged controls/settings/world envelopes. Receipts prove validated contiguous possession, not final application. New duplicates elicit the same receipt when the original receipt was lost.

Cap the entire encoded fast application packet at 512 bytes, and cap datachannel bufferedAmount at 16 KB for fast traffic. Do not enqueue old history behind congestion; retain records in bounded application state and retry, pausing when the two-second bound expires. Support up to 100 new input groups per second per origin stream, plus 20 repair packets and ten progress cuts. Each RTC pair has at most five disjoint incoming action/receipt slot flows, authorized from the immutable roster during binding. Give each flow a 140/s budget with a 280-message burst, liveness a separate 20/s budget with a 40-message burst, and the whole association a 750/s budget with a 1,500-message burst. Preserve the association bucket across alias changes and do not refill any bucket on a duplicate bind. Unauthorized slots/directions never consume another flow's budget. Rate failure is a transport recovery condition, not corrupt gameplay. UI/bot emission and browser stress must stay inside the declared 100-groups/s-per-stream envelope; receipts mirror incoming accepted packet rates. Checkpoint chunks are at most 12 KB with at most one transfer/peer, a 2 MB total cap and five-second timeout, throttled to 24 KB per 50 ms and suspended while fast-channel backpressure is present. Actual SCTP/DTLS/IP overhead and fragmentation are measured separately.

Liveness probes do not prove controls fresh. Origin progress includes current input revision; verify it against its stream prefix, and stop advancing that stream's completeness if its author is silent. After 500 ms without origin progress, coordinator proposes a lifecycle barrier that cancels controls/excludes or pauses the silent origin at a specified tick after existing finality. A barrier names exact retained prefixes and is installed via validated checkpoint/new segment, so old release packets cannot fire afterward. While preparing a barrier, other views remain bounded by their finality horizon. If coordinator or a required direct link remains unavailable, pause explicitly; no hidden gameplay relay or indefinite split-brain continuation.

## Mesh establishment

Both GCP `src/service/gateway.ts` and local `worker/index.ts` currently reject guest-to-guest signalling. Open same-room peer signalling while retaining current incarnation, connection/target, SDP/ICE and quota checks; add boundary tests for permitted guest links and rejected foreign/stale targets. Use lexicographically smaller peer ID as the sole offer/restart initiator per pair. Register reliable and fast channels separately, bind compact aliases only after reliable handshake, and preserve closing-state send protection/backpressure on both channels. Subscription changes determine which links are required; missing required direct links give bounded retry then an explicit pause, never an implicit host relay.

## Lifecycle, roles and recovery

Start/rematch/round transition, slot/connection replacement, settings and full-view ownership changes use reliable coordinator barriers. The coordinator chooses an agreed finalized base, neutralizes old controls, and distributes a new validated segment checkpoint with a future clock start. Ready receipts from required simulators gate segment activation; no ordinary input goes through this barrier path. Confirm round completion before progressing to the next round; tentative roundOver cannot open a new input scope. Room settings and identities are event-driven reliable metadata, never repeated in tick packets.

A controller becoming a full view receives checkpoint + complete suffix before subscribing/acknowledging finality. In shared mode select a ready TV/full view as simulation coordinator while the creator retains room-management/lease ownership. If none exists, offer an explicit waiting-for-display state; do not secretly run full physics on controller phones. Coordinator delegation is fenced by the service authority epoch and a creator-issued monotonic delegation generation. No automatic cross-person authority takeover is implied.

Recovery requests coalesce to one per peer, at most twice/second; after three corrupt/hash-failed recoveries in 30 seconds stop with a reload message. A checkpoint is a temporary fully validated candidate with scope, sequence prefixes, game, controls/gestures and hash from the same finalized tick. It cannot rewind same-segment finality or install a stale generation. A replacement segment is an explicit visible lifecycle discontinuity. Reconnect requires fresh controls and never retries an old gesture into the new scope. Storage is best effort, not durable failover.

## Implementation and acceptance

### Runtime wiring amendment (independently approved; acceptance pending)

`DirectSegment` owns one immutable segment's clock, optional full world, locally owned origins and subscriber queues. A full view advances from its clock without waiting for gameplay packets; a controller retains its own stream/delivery and compact status only. Prepare every subscriber candidate, then admit the local world group, then install origins/queues synchronously before publishing. Failed transport enqueues leave immutable records queued. Every 100 ms, a fresh started clock may advance exact origin cuts; receivers reply with possession receipts. Only a newer validated cut refreshes origin progress, so replayed old packets cannot indefinitely conceal silence. Until the first cut strictly beyond the segment base, allow 1,500 ms from the coordinator's started clock for post-start clock confirmation and first-cut delivery (500 ms clock RTT, up to 100 ms probe phase, up to 500 ms first-cut transit and scheduling margin). After that first advancing cut, retain the 500 ms progress-silence deadline. Duplicate/base cuts or action packets do not reset either deadline. The two-second speculation limit remains independently enforced. The coordinator proposes the latest complete tick at most every 100 ms and sends exact-prefix/hash finality. A poll without a complete candidate does not consume this publication allowance; newly complete cuts should not wait another whole polling interval. Retain the latest eligible certificate per subscriber when reliable enqueue fails and retry at most ten times per second without undoing already verified local finality. Provisional geometry is rendered from the local world; outcome UI and effects come from finalized state. Exceeding the finality horizon, input scope/clock faults or required-origin silence requests a visible barrier/recovery; never continue silently or invent an old release.

The existing reliable RTC channel may carry bounded compact tuples after its reliable alias handshake. `sendBound`/receive retain the same current association, authority epoch, connection, alias and drain fences as fast messages, but use the ordered/reliable lane and a 2 KB application limit. This lane carries clock requests/replies and finality without repeated long identity envelopes. Reject unknown tuple discriminators before application dispatch; each application decoder still validates its exact schema. Bootstrap and lifecycle transfers retain the full reliable envelope and existing chunk/timeout limits. Alias installation alone does not establish peer readiness; the two-way reliable handshake and channel liveness remain prerequisites. There is no global sequence filter on fast packets.

Room creation/management remains with the creator. Devices mode selects the creator as simulation coordinator; shared mode selects a ready display peer and gives it a creator-issued delegation generation, scoped to service epoch and exact connection. The creator can keep lightweight lobby/status metadata before a display exists, but must not run or retain a hidden full world in controller mode. Keep at most one recent management command for five seconds while a coordinator is unavailable; later commands explicitly supersede it, and expiry is visible. Commands remain queued until a coordinator is ready. Management commands, membership/role changes, round transition and recovery freeze origin scope, select a finalized base, clear held controls and install a new segment. A prepared checkpoint is validated by each required simulator; ready receipts gate a scheduled start and applied receipts gate retirement of the transfer. A coordinator switch transfers a validated finalized base between full views; if none is available, show an explicit paused/waiting or fresh-lobby recovery choice. No automatic trust/lease takeover or lossless failover is implied. Every role/delegation record is authenticated as coming from the current creator connection, binds service incarnation/epoch and a monotonically increasing delegation generation, and names the exact coordinator connection and per-slot owner connections. Clock/finality/status are accepted only from that coordinator generation; receipts only from the named stream subscriber.

Reviewed plan-delivery amendment: guests retry setup hello only until a validated current plan confirms their own service connection and display role. The creator retains one bounded per-current-member delivery record for its current plan and retries unacknowledged plans at most every 250 ms, independent of repeated hello or delegated plan-request arrivals. `{type:"directPlanAck", revision}` proves delivery only, never preparation, activation or clock permission. Guests acknowledge identical current-plan duplicates without reinstalling state; stale/conflicting plans cannot earn acknowledgements. Accept ACK only from the exact current member/connection/authority scope. Replace delivery records on plan/epoch changes. Failed enqueue and lost ACK remain pending; no steady full-plan/hello traffic after acknowledgement.

Reviewed preparation-header amendment: retry `directPrepare` at the existing 100 ms cadence only until the current member acknowledges its header with exact `{type:"directHeader", revision}`. A duplicate identical header elicits another header ACK to recover ACK loss. Header delivery remains distinct from checkpoint possession, `directReady` and applied activation; stalled chunks cannot generate repeated acknowledged metadata. Current alias/member/connection fences, checkpoint backpressure and five-second preparation deadlines remain unchanged. The regional application-impairment fixture exposed acknowledged headers saturating its 512 kbps sender budget before this correction.

Independently reviewed shared transfer pacing: count native `bufferedAmount` across every reliable and fast RTC lane before management/checkpoint enqueue, including the prospective encoded envelope. Management and compact reliable finality/demand control use a 12,000-byte aggregate admission ceiling, checkpoint data a 6,000-byte ceiling, reserving room for small control traffic. Checkpoint payload chunks become at most 2,000 bytes. The runtime attempts recipients in round-robin order and sends at most one successful chunk per 10 ms scheduling callback, preserving existing per-recipient 50 ms pacing and advancing its offset only on successful enqueue after rechecking the exact outgoing transfer and plan identities against synchronous callback replacement. Skip ineligible recipients; rotate after each successful chunk. A destination with pending fast bytes still blocks bulk. Fast actions, pulses and association health probes retain their independent health/lifecycle/authority/buffer gates; the small bounded probe escape path can exceed the ordinary aggregate admission ceiling. bulk cannot claim their remaining capacity. These are browser queue budgets, not an estimate of hidden SCTP/IP queues. At 256 kbps, 6 KB takes 187.5 ms to serialize and 12 KB takes 375 ms before latency, while five former 12 KB chunks took 1.875 s. Keep the existing five-second attempt and 15-second episode bounds; oversized transfers that cannot fit the supported link budget must fail explicitly. Reuse of a locally retained validated base is a separate future architectural decision.

Barriers use fresh monotonic segment aliases as prepare/ready/activate/applied IDs; duplicate phases resend the same acknowledgement without reinstalling state, and stale IDs cannot change a newer segment. Coalesce recovery requests to one active barrier, rate-limit them to twice/second and stop after three corrupt recoveries in 30 seconds. Prepare/ready has a five-second deadline; activate is sent only after all required simulators are ready and includes a future start. A missed start deadline aborts/reschedules the attempt with a fresh ID, never silently activating a subset. New-segment checkpoints neutralize game charge/target, held input and gesture state together. Each receiving view fences its prior finalized tick/hash: same-match replacement cannot start before that fence or conflict with it. Coordinator handoff must collect/fetch a base satisfying the highest such finalized fence; if unavailable, remain visibly paused until explicit fresh-lobby recovery. Controller status binds segment alias, tick and monotonic status revision; geometry/cooldown fields are provisional, death/score/phase fields finalized. Change-filter it at no more than ten updates per second and never include trails/world geometry.

The reviewed runtime composition additionally binds creator-authorized initialization separately from an existing-base handoff. A replacement coordinator without its required base must request an explicit fresh lobby. Lobby-only catalogs preserve tick, seed, player order and raw leaderboard order; a lobby transition explicitly applies selected room settings before catalog reconstruction. Full views compare derived phase/round/status, owners and catalog with the preparation header, then publish UI/cache state only at activation. Slot ownership is a mapping, independent of snapshot presentation order.

Recovery requests retain one scoped retry every 500 ms with a five-second response deadline; delegated coordinator plan requests also expire after five seconds. Availability retries share a 15-second unsuccessful episode deadline across new aliases. Running recovery clears that episode only after applied activation, clock qualification and finality beyond the new base; stationary lobbies require applied activation and a qualified clock. Keep the separate three-corrupt-attempts/30-second history across successful routine recoveries, charge each alias/epoch attempt once, and classify checkpoint/finality disagreement explicitly rather than from general invalid-input errors. Once timeout is latched, current-alias activation, status and ordinary control cannot resume it. A newer authorized lifecycle decision is required. A setup attempt begins at coordinator-bearing plan adoption, including the wait for its first preparation header. Superseding any never-settled plan starts/retains the same unsuccessful episode; an exact adopted-plan success marker prevents reused aliases from inheriting success. Coordinator-null waiting-for-display plans remain idle: adopting that validated lobby boundary cancels an inherited simulation recovery episode and obsolete delegated plan request, while preserving corrupt-state history. This is cancellation of an abandoned attempt, not proof of simulation recovery. These deadlines are tested runtime behavior, not a claim of lossless failover.

Controller status must include enough own-player state for cooldown, availability and target aiming without streaming trails/world geometry. This is separate from direct input traffic and must be reported as its own measured payload class. UI input scheduling uses the new segment clock directly, rather than waiting for the old host-motion prediction ledger. The old snapshot and accepted-action online branches are removed when the direct runtime is activated; offline solo and LAN keep their existing authority implementation. Full runtime activation requires deterministic orchestration tests and actual mixed-engine browser play, not just the component fixture.

### Input origin and clock contract (independently approved; runtime integration pending)

Use one fresh input origin per immutable segment/slot. Its local UI revision is distinct from its wire sequence. Ignore revisions already consumed; an unchanged held-control resend consumes the UI revision but produces zero wire actions. At a changed input, stamp every resulting record with `max(floor(clockTick)+1, lastActionTick, watermarkTick+1)`, rejecting uint32 exhaustion or more than four ticks ahead of the current clock. Steering and aim are edge-filtered; normalize local negative zero. Each explicit press allocates the next gesture ID, including a replacement press. Only an explicit release fires the active gesture; a neutral input or explicit cancel cancels it. A held-bomb resend never invents a missed press. Release carries its own final aim. Validate the whole local update and return a candidate origin plus at most three records (steering, aim, gesture); the caller installs it only after all local stream/delivery queues admit the group. Prepare all origin, local stream and subscriber queue candidates before publishing any bytes. Install the complete group atomically; a subsequent RTC enqueue failure retains the admitted records for repair and does not undo an action already visible to another peer. No partial acceptance or per-recipient retiming. Reject contradictory local frames (`press` with bomb false, or release/cancel with bomb true), nonboolean controls, invalid aim, and invalid revisions without consuming their revision. Watermark advancement is also a candidate operation. Maintain a bounded frontier of at most 64 tick/prefix entries and publish the exact prefix whose action tick is at or before the current clock tick, excluding already-issued future actions. Trim old entries into the published cut. Delivery queues accept that exact cut even when a later action is queued. Waiting until the current tick catches the last issued action can starve progress under continuous aim updates; adversarial event/pump ordering must be covered by a regression. New segment origins start neutral, with sequence/gesture zero; same-segment reconnect requires checkpoint/suffix recovery, never silently resetting a live origin.

Inject a monotonic millisecond clock into `DirectTickClock`; no render-frame or wall-clock dependency. The coordinator starts a segment clock at its agreed local start instant, at most one second in the future. Clock replies carry the fractional tick sampled immediately before replying; timing may be as low as the bootstrap tick minus 20 while waiting for that future start. World advancement and actions remain at the bootstrap base until the start: a follower additionally requires an accepted reply whose sender-side tick has reached that base, rather than starting solely because extrapolation crossed it. This initial start confirmation costs a probe exchange, not a per-action admission hop. Followers initialize from a matching outstanding scoped probe reply, estimating tick-at-receive as reply tick plus half measured RTT divided by 50 ms. Keep at most eight outstanding probes, expire replies older than 500 ms, and ignore older accepted probe IDs. Retain at most eight valid samples for one second and use the lowest-RTT sample extrapolated to the present. After initial alignment, slew at no more than one tick per second in either direction, with positive, monotonic progression; never snap a running clock backward. Treat each RTT sample as an interval: at receive time the coordinator tick lies between `replyTick` and `replyTick + RTT/50`, rather than being known exactly at the midpoint. Before adding a new sample, extrapolate its interval and the previous lowest-RTT sample interval to the same observation time; only a gap greater than four ticks between these uncertainty intervals latches a recovery fault. A high-RTT midpoint alone must never override the jitter filter or force recovery. Initial synchronization retains its sample uncertainty; if all prior samples age out, treat the new valid reply as a fresh estimate, still slew from the running projection and remain input-paused until the discrepancy from that projection is at most four ticks after accounting for the new sample uncertainty. A larger discrepancy in this stale-baseline case requires a fresh segment rather than guessing across the missing clock history. A backward/nonfinite clock reading or a gap greater than one second between scheduler observations also latches a fault, including on the coordinator. A fresh segment is required to clear these faults. After one second without a valid sample a follower cannot originate controls or advance completeness watermarks; independent provisional simulation may continue within its finality horizon. Existing active controls additionally make that stale sample a pause condition for runtime advancement. Faults and pre-start waiting also block both action issuance and completeness advancement. A release that cannot be timestamped is reported as failed and triggers a cancellation/recovery barrier; it must never be queued to fire when clock freshness returns. Return freshness/fault reasons explicitly so the runtime can distinguish waiting for a sample from mandatory rebootstrap. Tests must exercise asymmetric RTT uncertainty, jitter selection, bounded slew, reordered/unsolicited replies, time jumps, expiration and action/watermark boundaries. Playable clock uncertainty is capped at five ticks, measured as half the best RTT plus the distance between that sample's projection and the current local projection. If greater, report `uncertain` and permit no new actions, progress cuts or world advancement until a qualified sample. Aging out an uncertain sample does not restore readiness; retain its disqualification until a bounded valid sample qualifies the clock again. Untimestampable releases still suspend the origin. A receiver without a qualified local clock leaves action packets for bounded repair rather than calling a valid future action corrupt. The remote future-record envelope is 14 ticks: five ticks of uncertainty for each participant plus the existing four-tick maximum origin lead. This is staging only: records remain sequence/byte bounded and execute only at their stamped tick; simulation still stops 40 ticks beyond verified finality. Test opposite request/reply asymmetry between two followers, not only follower-to-coordinator samples. RTT symmetry is an estimate, not a guarantee that browser clocks are exactly synchronized.

Implement independently testable stream/rollback and delivery modules first, then mesh/clock/coordinator integration and the online replacement. These are parts of one target, not alternative opt-in endpoints. Independent design review precedes runtime changes; independent implementation review and release checks remain required before public use.

Core boundary tests use actual MessagePack: all arrival permutations, duplicate/conflicting IDs, gaps, missing press/final release, idle retry, lost receipts, burst loss, same-tick opposing actions, overlapping gestures, illegal watermarks/finality, future/expired input, stale scopes, invalid checkpoint atomicity and every bound. Six replicas must converge at finalized ticks regardless of delivery order and produce each finalized effect once. Inject clock/delivery/storage; no sleeps or private mutation in unit tests.

Integration must prove actual direct guest-to-guest sends with coordinator traffic blocked, independent advance without game packets, lightweight controllers, TV delegation, bots, role switches, round/lifecycle barriers, connection replacement, overflow and explicit partial-mesh failure. Compare original snapshot runtime against five active riders + TV under the same seeds/workloads and record all bidirectional payload classes, traffic windows, correction distances, local/remote input-to-render and finality latency, frame/replay CPU and retained memory p50/p95/p99/max. Retain ADR032's stated budgets and scope distinctions. Target healthy human action traffic under 2 KB/s per receiving full view excluding bootstrap and wire headers; bot/continuous aim workloads are reported separately rather than forced into the human estimate. Keep raw failures.

Run typechecks, full tests/coverage/build, exact Chromium/WebKit replay, mixed-engine real WebRTC loss/reorder harness and LAN regressions. A sustained 30-minute six-context run and declared network profiles qualify software behavior; physical phones, real packet impairment and wire counts remain separately unverified until measured. No deployment is part of this implementation authorization. Replay UI/export is a follow-on capability of this foundation, not necessary to finish the network replacement.

## Coordinator pause propagation (independently approved bounded correction)

The existing authenticated, association/alias-bound fast pause probe (`kind: 12`) means its sender stopped its segment. During an explicit rematch, transport-only handling leaves a receiving world running toward its 40-tick limit while the coordinator prepares and sends the replacement plan. Surface that existing notification to the runtime.
