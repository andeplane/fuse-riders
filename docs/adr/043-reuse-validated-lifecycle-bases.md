# ADR043: Reuse validated local state at lifecycle transitions

Date: 2026-09-14. Status: independently approved design; first implementation passes unit regressions and the regional browser fixture. Implementation review at 2024f5d is approved; remaining acceptance is pending. Extends ADR041/042 on `codex/deterministic-action-log`, tracking #82. No release authorization.

## Problem and alternatives

Every full view already reconstructs the same finalized game, yet an ordinary round transition currently sends a complete copy of that base to each view before applying a small list of management operations. The regional application-impairment fixture still exceeds the five-second preparation bound after acknowledged-header delivery, fair chunks and shared uplink budgets. The final observed failure has no browser exceptions or queue overflow. Increasing deadlines would preserve the interruption; increasing bulk queues would reintroduce control latency. Reuse an exact validated local base when available, retaining the current checkpoint path for misses. Do not introduce another online simulation mode.

## Authority, identity and validation

The optional preparation field is `reference: [baseAlias, baseTick, baseHash, operations]`, an exact four-element MessagePack tuple: positive uint32 alias, uint32 tick, exactly 16 lowercase hexadecimal hash characters, and an array of at most 64 existing valid non-tick `GameOperation` tuples. The 4,096-byte reference limit counts `packMessage(reference)` including tuple/container markers. The replacement header ACK has the exact three keys `{type: "directHeader", revision: positiveUint32, needsPayload: boolean}`; unknown/missing fields are rejected. A full view uses `needsPayload: false` only for a validated reuse candidate; a controller uses false without retaining any world. Bump rules to `fuse-direct-4` when implementing these incompatible shapes.

A preparation may include an optional bounded reference describing its pre-neutralization base: prior segment alias, exact finalized tick, canonical replay hash, and the same deterministic management operations otherwise included in `transitionBytes`. It is bound to the authenticated current room incarnation/authority epoch, source connection and new plan revision. Keep the installed segment's original plan scope alongside its world; adopting a new plan must not relabel that world as belonging to the new alias. Reuse is eligible only inside the same room/authority epoch and for the exact prior alias. Authority/connection replacement invalidates eligibility and uses the existing validated transfer/handoff path.

Specifically compare the retained installed plan's room incarnation/epoch, its local member connection and its member entry for the newly authorized source with the current authenticated local/source connections. The source must have belonged to that installed segment; use its prior member/coordinator identity, not blindly the old preparation's `plan.source` (a TV may coordinate a segment originally prepared by the creator). A source or local connection replacement invalidates reuse. An unrelated participant joining/leaving/replacing does not invalidate other peers' exact local bases; deterministic management operations still validate the roster transition. New participants naturally have no eligible retained base.

A full view can reuse only when its retained world's finalized tick and hash exactly match the reference. No speculative state, earlier prefix, approximate match, render snapshot, inferred seed or out-of-scope cache qualifies. For the initial implementation, a behind/ahead local finality is a cache miss; do not replay an unproven suffix or retain additional full worlds. The source offers the same base and operations to all peers, regardless of whether each peer transfers bytes or reuses its copy.

A cache miss never bypasses the reference proof: a fallback payload must decode to the exact offered base alias/tick/hash and canonically identical operations before derivation. If local finalized state is ahead, the existing fence can reject the older transferred base; fallback does not authorize a downgrade. An equal-tick local hash mismatch similarly retains existing fence/corruption handling after fallback validation.

Refactor transition derivation so both paths use one validation routine: verify base scope/tick/hash and existing finalized fence, clone and neutralize held/gesture/charge/target state, apply the validated non-tick management operations, produce the replacement bootstrap, validate its roundtrip, then compare every existing preparation field (result hash, match/round/tick, thin status, owners and optional lobby catalog). A failed candidate leaves the retained healthy world unchanged. Reuse never skips output validation or readiness/activation barriers.

The reference uses at most 64 existing valid non-tick operations and at most 4,096 encoded MessagePack bytes. Offer it only if the complete preparation envelope also fits the ordinary 12,000-byte management admission ceiling. If it does not fit, omit the reference and use the existing full payload. The source still retains one bounded complete fallback payload (maximum 2 MB) for the current preparation; reuse adds no unbounded cache or replay history.

Choose one immutable header for the whole preparation. Size admission uses the largest encoded envelope across the known current recipients, including all namespace/connection fields and a maximum-width safe-integer message ID. It is independent of current buffered bytes and cannot vary by recipient or retry. Temporary queue pressure merely delays enqueue of the same header.

## Delivery and failure behavior

Bump the direct rules identifier for the new closed protocol shapes; old peers fail explicitly. Extend the exact header acknowledgement to include whether payload is required. A controller-only member always requires no world payload. A full view reports no payload only after its local reuse candidate has passed all validation; the source accepts that claim only for a preparation that offered a reference. Otherwise the member requests payload in its first header acknowledgement, using the current transfer immediately without an extra request exchange.

Header delivery, payload requirement, `directReady` and applied activation remain distinct. A duplicate identical preparation returns the same header acknowledgement without re-deriving or reallocating its candidate. Payload requirement is immutable within one peer/connection/preparation; conflicting acknowledgements cannot restart, skip or retarget an in-progress transfer. The source sends chunks only to acknowledged members requiring payload, preserves offsets on failed enqueue, and retains fair scheduling and aggregate budgets. Cache hits still bind the new alias and pass the scheduled-start/applied barrier.

On a conflicting current-member payload-requirement ACK, reject it without changing the accepted mode, header delivery, offset, readiness or deadline, and fail that preparation explicitly through the existing synchronization/corruption path. Stale/foreign-scope ACKs remain harmless rejections. A full-view no-payload claim without an offered reference is invalid and cannot advance its barrier.

Header delivery starts immediately. After a successful reliable enqueue, wait 500 ms before retrying the same immutable header; after a failed enqueue, retry after 100 ms. A validated header acknowledgement stops retries. Keep this per-peer deadline separate from activation retries and readiness: queued bytes are not application acceptance. This bounded pacing refinement was independently approved after the mobile-01 trace showed 21–23 repeated headers (73–80 KB) per five-peer setup attempt under constrained uplink.

All existing five-second preparation and 15-second unsuccessful-episode bounds remain. Cache mismatch is a normal bounded fallback, not a corruption charge. Invalid resulting state, conflicting same-scope metadata or a false base proof retains the existing corruption/safe-failure handling. A peer that cannot complete fallback within the supported network budget fails visibly. No lossless host migration, durable replay storage or physical-phone qualification is implied.

## Acceptance

1. Independent design review before implementation and implementation review before any release.
2. Exact MessagePack/reference/ACK shape, size, operation and namespace tests; stale connection/epoch/alias, altered base/result hash, duplicate/conflicting ACK and retained-fence rejection.
3. Identical derived bootstrap/hash/outcomes for local reuse and full transfer, including neutralized held bomb/aim state, round/match completion, settings and roster changes.
4. Serialized runtime tests proving zero checkpoint chunks for exact cache hits, selective transfer for a missing or mismatched participant, no full-world retention on controllers, retry after lost header/ACK, and unchanged ready/applied/timeouts. Include source/authority replacement during send and atomic rejection.
5. Repeat the current mixed Chromium/WebKit three-round local and regional fixtures under unchanged network profiles and deadlines; count setup/transition bytes separately and assert no hidden recovery, browser errors or divergent outcomes. Preserve failed runs and exact loaded-source hashes.
6. Then continue sustained impairment, reconnect/TV/LAN and latency/resource qualification. The adaptive 50–100 ms presentation proposal remains separate; this change does not implement rendering delay.

## Implementation checkpoint

The `fuse-direct-4` candidate implements reference-based preparation and selective payload acknowledgements. All 615 tests pass. `regional-07` completes three rounds across six Chromium/WebKit simulators under the unchanged regional profile, with matching outcomes and no hidden recovery or browser errors. This is a short application-impairment result, not full release or physical-phone qualification. See [implementation evidence](../online/direct-actions-evidence/lifecycle-reuse/manifest.json).


## Reconstruct a retained lifecycle reference (independently approved bounded correction)

Sustained mobile-04 completed two matches, then the third rematch required five full checkpoint fallbacks: the coordinator's finalized base was tick1599, while guests had finalized1589 but already simulated1614–1615. Exact-finalized-tick-only reuse discarded their useful retained history and the transfers exceeded unchanged setup bounds.

Local reuse may reconstruct the authenticated source's reference tick inside the existing interval from local finalized tick through resident simulation head. Return a fresh copy from retained snapshots/actions only when its full canonical DirectState hash equals the source fingerprint, including held controls, gestures and pending settings. Never lookup below the finalized fence, advance beyond the resident head, create another cache or mutate old simulation/history/events/prefixes/finality. Alias, original source/local connection and authority eligibility remain unchanged. Missing actions/history or hash mismatch take the existing validated full transfer path.

This is lifecycle checkpoint equivalence: the already-authorized source can supply a complete checkpoint, and a matching local reconstruction substitutes for that payload. It does not establish ordinary stream completeness, issue cuts, or commit old effects. Therefore delayed completeness certificates alone do not prohibit this reuse. The full-transfer path still derives from its actual validated finalized bootstrap. Both paths share base alias/tick/hash, finalized fence, operations, neutralization, settings and every result-header check. Existing byte/history/deadline limits and ready/applied barriers remain. Regressions compare exact reuse/transfer bytes with delayed finality and missing cuts, reject missing actions/older/future references, preserve all resident state, and exercise serialized runtime transfer avoidance.
